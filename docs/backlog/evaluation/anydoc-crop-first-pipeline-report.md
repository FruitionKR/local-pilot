# AnyDoc crop-first 문서 복원 파이프라인 평가

## 결론

실험으로 검증한 제품 후보는 다음 경로다.

```text
원본 PDF
→ Heron 영역 검출·crop
→ 그림은 원본 asset 보존
→ 표·수식은 페이지 단위 Luna 묶음
→ crop을 가린 본문은 AnyDoc 변환
→ 확정 손상 및 차이 상위 30% 본문 page만 Luna
→ 180초 timeout·검증 탈락 항목만 단건 fallback
→ 원래 좌표 순서로 조립
```

AnyDoc은 본문 추출 속도와 보존율 때문에 첫 단계로 쓸 가치가 있다. 다만
표·수식 복원기나 PDF 구조 정확도 판정기로 쓰지는 않는다. 표·수식은 원본
crop을 모델에 보내고, 그림은 모델로 다시 설명하지 않고 원본 asset을
유지한다.

415페이지 실험에서 페이지 묶음은 표·수식 호출을 520회에서 fallback 포함
204회로 60.77% 줄였고, 측정 가능한 전체 운영 token을 2,672,884개에서
1,959,734개로 최소 26.68% 줄였다. 같은 520개 crop의 엄격한 exact는 기존
단건 47.12%에서 페이지 묶음+fallback 61.92%로 상승했다.

이 61.92%는 표·수식 crop 정확도다. 기존 5,817블록 전체 실사용 정확도
83.31%와 분모가 다르므로 새 전체 정확도로 합산하지 않는다. 최종 전체
정확도는 새 표·수식 결과를 넣은 5,817블록 blind를 다시 실행해야 확정된다.

## 제품 코드에 반영한 운영 경계

제품 기본 mode를 `crop-first`로 전환해 AnyDoc baseline과 Rust Heron crop을
제품 stage에 연결했다. 기존 `docling-only`, `selective-repair`, `full-repair`는
명시적 호환 mode로 유지한다.

- `figure`는 선택 복원 후보에서 제외해 원본 asset을 보존한다.
- 같은 페이지에서도 손상 본문과 표·수식을 서로 다른 lane으로 보낸다.
- 표와 수식은 같은 페이지 단위로 묶는다.
- Responses API timeout은 180초다.
- 묶음 timeout, 연결 실패, JSON/ID 불일치는 해당 묶음만 단건 재시도한다.
- 묶음 결과 중 Markdown 구조 검증에 실패한 항목만 단건 재시도한다.
- 단건 재시도도 실패하면 원문을 유지하고 summary에 `failed`로 남긴다.
- 인증·HTTP 오류는 항목 수만큼 반복하지 않고 기존처럼 단계를 실패시킨다.
- 확정 손상 본문과 문서 내 차이 상위 30% 본문 페이지를 text lane으로
  보낸다.

이 경계는 L102에서 확인된 type 혼합 위험, L103에서 확인된 lane 분리의
안전성, 이번 415페이지 실험에서 확인된 페이지 묶음의 호출 절감을 함께
반영한다. 문서별 키워드나 좌표 임계값은 추가하지 않았다.

## 415페이지 실측

대상은 PDF 25개, 415페이지다. Heron 검출 결과는 표 180개, 수식 340개,
그림 345개였다.

| 항목 | 기존 경로 | crop-first 페이지 묶음 |
| --- | ---: | ---: |
| 표·수식 호출 | 520 | 198 묶음 + 6 fallback = 204 |
| 그림 AI 호출 | 345 | 0 |
| 표·수식 token | 1,782,109 | 1,068,959¹ |
| 본문 포함 운영 token | 2,672,884 | 1,959,734¹ |
| 표·수식 exact | 245/520, 47.12% | 322/520, 61.92% |
| 표 exact | 115/180, 63.89% | 115/180, 63.89% |
| 수식 exact | 130/340, 38.24% | 207/340, 60.88% |

¹ 15분 후 종료한 표 묶음 3회의 미보고 token은 제외한 하한이다.

성공한 195개 묶음의 중앙값은 15.24초, p95는 59.70초, 최댓값은
120.23초였다. 실제 8병렬 wall은 timeout 3개 때문에 19분 30초였다.
성공 최댓값을 넘는 180초에서 끊고 단건 fallback하면 같은 꼬리가 전체
처리를 붙잡지 않는다.

운영 환산은 다음 범위로 본다.

| 조건 | 415페이지 예상 | 600페이지 예상 |
| --- | ---: | ---: |
| 본문·특수 lane 각각 8 worker | 약 13분 | 약 20~23분 |
| 전체 공유 8 worker | 약 20~21분 | 약 30~35분 |

이는 API rate limit과 재시도에 따라 달라지는 계획값이며 clean 600페이지
실측이 아니다. 현재 Luna 공식 API 단가를 적용한 계획 비용은 415페이지
약 `$0.8~$1.2`, 600페이지 약 `$1.1~$1.7`이며 보수적 상한은 각각
`$2.5`, `$3.5`다. 과거 Codex 실행 로그는 input/output token 분리가 없어
정확한 청구액을 역산할 수 없다.

## 같은 415페이지 기준 비교

| 경로 | 전체 실사용 정확도 | 시간 | 비고 |
| --- | ---: | ---: | --- |
| fresh Docling | 71.57% | 직렬 2,132.54초, 35분 33초 | 저화질 NACA OCR 1,307.71초 포함 |
| AnyDoc + 본문 상위 30% AI + 기존 단건 특수 | 83.31% | 모델 누적 15,134.89초 | 5,817블록 blind, 운영 token 3,347,864 |
| 전체 Luna | 91.92% | 선택 경로보다 고비용 | 같은 5,817블록 blind의 품질 상한 후보 |
| 새 페이지 묶음 특수 경로 | 전체 미측정 | 위 운영 환산 참조 | 표·수식 520 crop exact 61.92% |

따라서 현재 경로는 Docling보다 빠르고 실용적인 기본 후보지만, 새 전체
정확도가 83.31% 또는 91.92%라고 말할 수는 없다. 83.31%는 이전 단건 특수
결과를 쓴 전체 조립이고, 91.92%는 전체 Luna 경로다.

## 제품 baseline과 동일 445블록 직접 비교

L75부터 사용한 4개 PDF·30페이지의 fresh Docling primary 445블록을
공통 분모로 고정하고 변경 전 제품 fresh Docling과 L107 최종 page Markdown을
동일-call 2-way blind로 다시 평가했다.

| 경로 | strict exact | 실사용 정확도 | 읽을 수 있음 | 누락 |
| --- | ---: | ---: | ---: | ---: |
| 제품 baseline, fresh Docling | 193/445, 43.37% | 201/445, 45.17% | 99.10% | 4 |
| L107 crop-first 페이지 묶음 | 393/445, 88.31% | 400/445, 89.89% | 99.78% | 1 |

유형별 실사용 정확도는 제목 77.59%→100%, 본문 45.00%→91.07%,
표 3.85%→65.38%, 수식 2.27%→81.82%, 그림 75.68%→91.89%였다.
동일 block에서 L107만 정확한 사례는 212개, Docling만 정확한 사례는
13개였다. 직접 선호도 L107 244, Docling 19, 동률 182였다.
CMap 손상 `designing`을 제외한 353블록에서도 제품 baseline 56.94% 대
L107 88.95%로 +32.01%p였다. L107의 남은 실사용 실패 45개는 본문 25,
표 9, 수식 8, 그림 3이며 제목 실패는 없었다.

같은 445블록의 과거 4-way blind는 Docling 48.99%, 이전 30% route+단건
특수 92.58%였다. evaluator 구성에 따라 절대값은 약 3~4%p 변했지만,
pipeline의 paired 개선 폭은 과거 +43.60%p와 이번 +44.72%p로 비슷했다.
이 직접 비교는 30페이지에서 유효하며 415페이지·5,817블록 전체 blind를
대신하지 않는다.
기존 445블록 계약을 맞추기 위해 Docling figure도 source asset이 보존된
것으로 평가했다. 실제 `docling-only`가 placeholder만 게시하면 제품
baseline의 그림 점수는 이 결과보다 낮을 수 있다.

## CMap과 손상 본문 처리

PDF font에 정상 `/ToUnicode` 또는 복원 가능한 `cmap`이 있으면 코드로
Unicode 변환이 가능하고 AI가 필요 없다. 그러나 embedded subset에
`/ToUnicode`, 내부 `cmap`, 의미 있는 glyph name이 모두 없으면
`CIDToGIDMap`만으로 glyph의 Unicode 의미를 확정할 수 없다. 이 경우에는
알려진 원본 font outline 대조나 OCR/vision이 필요하다.

제품 본문 AI route는 문서 내용에 맞춘 임계값 대신 다음 결정적 실패를 먼저
선택한다.

- AnyDoc 비정상 종료 또는 빈 출력
- replacement character
- 사용 font의 `/ToUnicode` 결손
- crop 전후 token 불일치

나머지 페이지는 redaction PDF의 단어열과 AnyDoc 단어열 차이를 순위화해
문서 내 상위 30%까지 Luna에 보낸다. 고정 정확도 임계값이나 문서별 키워드는
사용하지 않는다. 415페이지 실험에서 코드로 확정한 손상은 20페이지였고,
나머지 395페이지는 정답이 확인된 성공이 아니라 `UNKNOWN`이었다.

## 비PDF 결과

공개 문서 31개 중 AnyDoc이 비어 있지 않은 출력을 만든 것은 22개였고
중앙 변환 시간은 0.28초였다.

| 형식 | 비어 있지 않은 출력 | 판단 |
| --- | ---: | --- |
| DOCX | 3/4 | 일반 본문·목록·표·각주는 양호, adversarial 중첩 표는 안전 제한으로 거부 |
| PPTX | 3/4 | 본문·notes 일부 보존, 표 전용 문서 1개는 빈 출력 |
| XLSX | 5/5 | 값 추출은 강하지만 여러 표 병합·수식·차트 손실 가능 |
| ODT | 2/3 | 일반 표는 양호, chart-only 문서는 빈 출력 |
| ODS | 3/3 | 대형 sheet 값 추출 양호 |
| ODP | 0/4 | 현재는 렌더+AI로 바로 우회하는 편이 안전 |
| EPUB | 3/3 | 본문은 양호, MathML 구조는 평문으로 손실 |
| legacy DOC/PPT | 0/2 | 렌더+OCR/AI fallback 필요 |

DOCX·PPTX 실패는 다운로드 파일이 손상돼서가 아니었다. package 무결성은
검사했고, DOCX 하나는 5,000중첩 표 안전 제한, PPTX 하나는 표만 있는
문서에서 빈 출력을 낸 parser coverage 문제였다. 비PDF에는 PDF 좌표 crop
코드를 그대로 적용하지 않고 package 구조 검사 후 slide/sheet/embedded
object 단위 렌더 fallback을 별도로 둬야 한다.
