## Backend — 빈 문서 생성 API 부재

### 기존 문제

- 문서 생성 API가 비어 있지 않은 multipart 파일만 받아, 사이드바에서 새 Markdown 문서를 만드는 기능을 연결하지 못했다.
- `documents.content_hash`가 필수라 내용 없는 placeholder row를 만드는 방식도 사용할 수 없었다.

### 해결

- 프론트엔드가 고유 식별 주석과 `# 새 문서` 제목을 가진 `새 문서.md`를 생성해 기존 `POST /api/workspaces/{workspace_id}/documents`로 업로드한다.
- 별도 빈 문서 endpoint나 nullable schema 변경 없이 새 노트 생성 요구사항을 충족했다.
- `npm run build`로 프런트엔드 타입과 production build를 검증했다.

### 남은 작업

- WYSIWYG 편집 결과를 저장할 본문 update API는 여전히 필요하다. `docs/issue/backend/2026-07-21.md`의 `2. 노트 본문 저장 API 부재`로 이관했다.

## Infra/AI — pipeline API lifespan의 DB 스키마 소유권 충돌

### 기존 문제

`llmPipeline/api.py`의 FastAPI `lifespan`이 `pipeline_runs`와 임베딩 테이블뿐 아니라 `documents`, `wiki_pages`, 링크 테이블까지 직접 생성했다. Spring Flyway보다 pipeline API가 먼저 기동하면 일부 테이블만 존재하는 schema가 만들어지고, Flyway가 기존 DB로 오판해 V1 baseline을 건너뛸 수 있었다.

API 계약 테스트가 `TestClient` startup에서 실제 `init_db()`를 호출해 `DATABASE_URL` 없이 실패한 현상은 mock으로 막을 수 있지만, 이는 테스트 증상만 가릴 뿐 운영 schema 소유권 충돌을 해결하지 못했다.

### 해결

- Backend Flyway V4가 `pipeline_runs`, `wiki_page_embeddings`, `wiki_embedding_vectors`, `wiki_embedding_units`, `wiki_schemas`를 생성하고 버전을 관리한다.
- Flyway V1~V3 적용 후 Python 초기화로 pipeline 테이블이 존재하는 DB도 수용하도록 `CREATE TABLE/INDEX IF NOT EXISTS`와 legacy `project_id` 변환을 migration에 포함한다.
- llmPipeline의 공용·파이프라인·Wiki schema DDL과 `POST /admin/init-db`를 제거한다.
- FastAPI lifespan은 필수 테이블 10개의 존재 여부만 확인하고, 누락 시 테이블 이름을 포함해 fail-fast한다.
- API 계약 테스트는 `verify_schema()` 경계만 mock하고, 별도 단위 테스트에서 전체 schema와 누락 schema 동작을 검증한다.
- Backend 통합 테스트는 Flyway 적용 후 파이프라인 테이블 5개의 존재를 확인한다.

Backend 변경은 비즈니스 로직이나 API 수정이 아니다. Python이 임의로 실행하던 DDL을 제거하면서 신규 DB도 정상 구성되도록 Spring Flyway에 migration을 추가하고 그 결과만 검증한다.

Flyway 이력 없이 Python이 공용 테이블 일부만 만든 DB는 자동 migration 대상이 아니다. 이 상태에서는 `baseline-on-migrate`가 V1을 마킹한 뒤 V3가 누락된 `users`, `workspaces`를 참조하며 V4 전에 실패한다. 로컬 개발 DB는 `backend/README.md`의 `처음 받았을 때 / 브랜치를 pull 한 뒤` 절차로 volume을 리셋하고, 보존이 필요한 환경은 V1 전체 schema와 데이터를 먼저 복구해야 한다.

### 검증

- `llmPipeline`: 문서 복원 전용 선택 의존성 테스트를 제외하고 `349 passed`, `28 subtests passed`
- PostgreSQL 임시 DB: V1 → V4 순차 적용, 대상 테이블 5개 확인, V4 재실행 성공
- `BackendApplicationTests`: 당시 로컬 Java runtime 부재로 실행하지 못해 Java 환경이 있는 CI 확인이 필요했다.

### 확인 위치

- startup wiring: `llmPipeline/api.py`의 `lifespan`, `app`
- Flyway migration: `backend/src/main/resources/db/migration/V4__add_pipeline_schema.sql`
- Backend 통합 테스트: `backend/src/test/java/fruition/BackendApplicationTests.java`의 `flywayCreatesPipelineTables`
- schema readiness: `llmPipeline/app/modules/wiki_ingestion/infrastructure/postgres_wiki_ingestion_repository.py`의 `verify_schema`, `REQUIRED_TABLES`

- readiness 단위 테스트: `llmPipeline/tests/modules/wiki_ingestion/test_postgres_schema_readiness.py`

## AI — Markdown 편집 router와 생성 계약 보강

### 기존 문제

- 일반 `whole_document` 편집과 구조 보존형 cleanup이 template 재구성으로 잘못 분류될 수 있었다.
- `insert_after` operation과 현재 section target 검증이 없었다.
- `markdown_create` 필수 필드와 생성형 Markdown 구조 오류를 검증하지 않아 잘못된 결과가 적용될 수 있었다.

### 해결

- router guard와 prompt에서 일반 문서 편집, 구조 보존형 cleanup과 template 변환을 구분한다.
- `insert_after`를 `current_section` 전용 operation으로 추가하고 target이 불명확하면 `clarify`로 처리한다.
- `operation_for_edit_goal`로 edit operation 결정 규칙을 공통화한다.
- `markdown_create`의 `title`, `summary`, `markdown` 필수 필드를 검증하고 최초 호출과 재시도가 같은 정규화·검증 경로를 사용한다.
- 생성형 edit와 create Markdown을 CommonMark+table parser로 검사하고, 닫히지 않은 code fence·frontmatter·display math를 계약 실패로 처리한다.
- 첫 출력이 계약을 위반하면 실패 이유와 함께 한 번 재시도하고, 재실패 결과는 전용 output contract error로 미적용한다.

### 검증

- Markdown 편집 모듈: `60 passed`, `26 subtests passed`
- 문서 복원 전용 선택 의존성 테스트 제외 전체: `357 passed`, `30 subtests passed`

### 확인 위치

- router guard: `llmPipeline/app/modules/agent/infrastructure/chat_completions_turn_router.py`
- operation 계약: `llmPipeline/app/modules/markdown_edit/domain/entities.py`의 `operation_for_edit_goal`
- 생성·재시도: `llmPipeline/app/modules/markdown_edit/infrastructure/chat_completions_markdown_editor.py`
- Markdown 구조 검증: `llmPipeline/app/modules/markdown_edit/infrastructure/markdown_syntax_validation.py`
- API 계약: `docs/spec/agent-markdown-contract.md`의 `4.3 edit`, `4.4 generated_markdown`, `7. 오류 처리`
