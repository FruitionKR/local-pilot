# 2026-07-21 이슈

## Query pipeline 요청의 workspace 식별자 누락

### 문제

Backend의 query API는 URL에서 `workspaceId`를 받고 채팅 세션 소유권도 검증했지만, LLM Pipeline으로 보내는 `POST /query` 본문에는 질문과 run 정보만 담았다. 이 상태에서는 Pipeline이 질의를 어느 workspace 데이터 범위로 처리해야 하는지 구분할 수 없다.

### 반영

- 동기 query와 비동기 query run 모두 URL의 `workspaceId`를 `QueryController` → `QueryRunService` → `QueryService` → `PipelineQueryRequester`로 전달한다.
- LLM Pipeline `POST /query` 요청 본문에 `workspace_id`를 포함한다.
- Pipeline 요청 로그에 `workspaceId`를 남겨 request 단위 추적이 가능하게 한다.
- `llmPipeline` 내부 스키마·조회 로직은 이번 작업에서 변경하지 않는다.

### 검증

- `QueryControllerTest`, `QueryRunServiceTest`, `QueryServiceTest`, `PipelineQueryRequesterTest` 통과
- `PipelineQueryRequesterTest`에서 동기·비동기 요청 본문의 `workspace_id` 포함 확인
- Backend 전체 154개 테스트 중 이번 변경과 무관한 `DocumentServiceBlocksTest.createInitialNote_savesUniqueMarkdownPerWorkspace` 1개 실패: workspace별 초기 노트 hash가 다르다는 기존 기대값이 현재 동일 Markdown 정책과 충돌함

### 확인 위치

- workspace API 경계: `backend/src/main/java/fruition/query/controller/QueryController.java`의 `query`, `createRun`
- 비동기 run 전달: `backend/src/main/java/fruition/query/service/QueryRunService.java`의 `start`, `runPipeline`
- Pipeline 호출 전달: `backend/src/main/java/fruition/query/service/QueryService.java`의 `query`
- Pipeline 요청 계약: `backend/src/main/java/fruition/query/repository/PipelineQueryRequester.java`의 `QueryPayload`, `query`

## pipeline API lifespan의 DB 스키마 소유권 충돌

### 문제

`llmPipeline/api.py`의 FastAPI `lifespan`이 `pipeline_runs`와 임베딩 테이블뿐 아니라 `documents`, `wiki_pages`, 링크 테이블까지 직접 생성했다. Spring Flyway보다 pipeline API가 먼저 기동하면 일부 테이블만 존재하는 schema가 만들어지고, Flyway가 기존 DB로 오판해 V1 baseline을 건너뛸 수 있다.

API 계약 테스트가 `TestClient` startup에서 실제 `init_db()`를 호출해 `DATABASE_URL` 없이 실패한 현상은 mock으로 막을 수 있지만, 이는 테스트 증상만 가릴 뿐 운영 schema 소유권 충돌을 해결하지 못한다.

### 반영

- Backend Flyway V4가 `pipeline_runs`, `wiki_page_embeddings`, `wiki_embedding_vectors`, `wiki_embedding_units`, `wiki_schemas`를 생성하고 버전을 관리한다.
- Flyway V1~V3 적용 후 Python 초기화로 pipeline 테이블이 존재하는 DB도 수용하도록 `CREATE TABLE/INDEX IF NOT EXISTS`와 legacy `project_id` 변환을 migration에 포함한다.
- llmPipeline의 공용·파이프라인·Wiki schema DDL과 `POST /admin/init-db`를 제거한다.
- FastAPI lifespan은 필수 테이블 10개의 존재 여부만 확인하고, 누락 시 테이블 이름을 포함해 fail-fast한다.
- API 계약 테스트는 `verify_schema()` 경계만 mock하고, 별도 단위 테스트에서 전체 schema와 누락 schema 동작을 검증한다.
- Backend 통합 테스트는 Flyway 적용 후 파이프라인 테이블 5개의 존재를 확인한다.

Backend 변경은 비즈니스 로직이나 API 수정이 아니다. Python이 임의로 실행하던 DDL을 제거하면서 신규 DB도 정상 구성되도록, Spring Flyway에 migration을 추가하고 그 결과만 검증한다.

Flyway 이력 없이 Python이 공용 테이블 일부만 만든 DB는 자동 migration 대상이 아니다. 이 상태에서는 `baseline-on-migrate`가 V1을 마킹한 뒤 V3가 누락된 `users`, `workspaces`를 참조하며 V4 전에 실패한다. 로컬 개발 DB는 `backend/README.md`의 `처음 받았을 때 / 브랜치를 pull 한 뒤` 절차로 volume을 리셋하고, 보존이 필요한 환경은 V1 전체 schema와 데이터를 먼저 복구해야 한다.

### 검증

- `llmPipeline`: 문서 복원 전용 선택 의존성 테스트를 제외하고 `349 passed`, `28 subtests passed`
- PostgreSQL 임시 DB: V1 → V4 순차 적용, 대상 테이블 5개 확인, V4 재실행 성공
- `BackendApplicationTests`: 로컬 Java runtime 부재로 실행하지 못했으며 Java 환경이 있는 CI에서 확인 필요

### 확인 위치

- startup wiring: `llmPipeline/api.py`의 `lifespan`, `app`
- Flyway migration: `backend/src/main/resources/db/migration/V4__add_pipeline_schema.sql`
- Backend 통합 테스트: `backend/src/test/java/fruition/BackendApplicationTests.java`의 `flywayCreatesPipelineTables`
- schema readiness: `llmPipeline/app/modules/wiki_ingestion/infrastructure/postgres_wiki_ingestion_repository.py`의 `verify_schema`, `REQUIRED_TABLES`
- API 계약 테스트: `llmPipeline/tests/test_pipeline_run_api_contract.py`의 `_pipeline_client`, `test_pipeline_lifespan_verifies_flyway_schema`
- readiness 단위 테스트: `llmPipeline/tests/modules/wiki_ingestion/test_postgres_schema_readiness.py`

## Query 비동기 실패 기록 rollback과 RUNNING 고착

### 문제

- `QueryService.query()`의 `@Transactional` 안에서 pipeline 실패 메시지를 저장한 뒤 `PipelineQueryException`을 다시 던져, 저장 완료 로그와 달리 `chat_messages` insert가 rollback됐다.
- `QueryRunService.runPipeline()`이 `PipelineQueryException`만 처리해 DB·직렬화 등 예상 밖 `Exception`에서는 run이 `RUNNING`에 남고 terminal SSE event가 발행되지 않을 수 있었다.

### 반영

- `QueryMessageRecorder.createPendingPair()`를 별도 Spring service와 `REQUIRES_NEW` transaction으로 분리했다. Query 접수 시 user는 `completed`, assistant는 빈 내용의 `pending`으로 저장하고 `last_message_at`을 갱신한다.
- `QueryRunService.start()`는 초기 메시지 commit을 완료한 뒤 executor를 제출하고 `202`를 반환한다. 따라서 client가 SSE를 연결하기 전에 채팅 메시지를 조회할 수 있다.
- pipeline 실패 시 `QueryMessageRecorder.markFailed()`가 기존 pending assistant를 별도 transaction에서 `failed`로 갱신하고, `QueryService`는 원래 `PipelineQueryException`을 재전파한다.
- `QueryRunService`는 예상 밖 `Exception`의 stack trace를 서버 로그에 기록하고, 사용자에게는 일반화된 오류를 전달하면서 run을 `FAILED`로 바꾸고 `query.failed` SSE를 발행한다.

Redis 또는 QueryRun 영속화와 독립적인 현재 실패 처리 보강이다. JVM 자체 복구를 기대하기 어려운 `Error`는 잡지 않는다. 장시간 `RUNNING` timeout 정리와 SSE heartbeat scheduling은 별도 후속 범위다.

### 검증

- `QueryServiceTest`: 초기 메시지 선저장, 성공 시 assistant 완료, pipeline/예상 밖 실패 시 assistant 실패 갱신 확인
- `QueryMessageRecorderTest`: completed user·pending assistant 생성, assistant 실패 갱신 및 `REQUIRES_NEW` propagation 확인
- `QueryRunServiceTest`: pipeline 오류와 예상 밖 `RuntimeException` 모두 `FAILED` 및 `query.failed`로 종결 확인
- 실행 명령: `./gradlew test --tests 'fruition.query.service.QueryServiceTest' --tests 'fruition.query.service.QueryRunServiceTest' --tests 'fruition.query.service.QueryMessageRecorderTest'`
- Backend 전체 테스트: `./gradlew test` → `BUILD SUCCESSFUL`
- 실제 run `query_c53cba54-36ca-4fa5-b047-f215ebbb7424`: `202` 직후 SSE 연결 전에 채팅 API에서 `user=completed`, `assistant=pending` 확인. pipeline 종료 후 같은 `pair_id`의 assistant가 `failed`로 갱신된 것을 확인

### 확인 위치

- 메시지 선저장·실패 갱신 transaction: `backend/src/main/java/fruition/query/service/QueryMessageRecorder.java`의 `createPendingPair`, `markFailed`
- pipeline 실패 연결: `backend/src/main/java/fruition/query/service/QueryService.java`의 `catch (PipelineQueryException e)`
- 예상 밖 예외 종결: `backend/src/main/java/fruition/query/service/QueryRunService.java`의 `runPipeline`, `failRun`
- 설계 설명: `docs/design/query-sse-redis.md`의 `3. 현재 in-memory 실패 처리`
