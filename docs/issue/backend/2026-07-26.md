## 1. 문서 콘텐츠 버전 이력·롤백 서버화

본문 수동 저장(`PUT .../content`)과 낙관적 버전 충돌은 구현됐지만, 저장은 `document_edit_states`의 단일 행(`document_id` PK)만 갱신하고 이전 버전 스냅샷을 남기지 않는다. 클라이언트측(localStorage) 스냅샷을 서버 이력으로 승격하려면 버전 이력 저장이 선결이다.

### 남은 작업

- `document_content_versions` 성격의 버전 테이블과 이력 조회·롤백 API를 추가한다.
- 롤백 시 `documents.current_version` 증가와 낙관적 충돌 계약을 유지한다.

### 확인 위치

- 현재 단일 행 저장: `backend/src/main/resources/db/migration/V9__add_document_editing_core.sql`의 `document_edit_states`(PK `document_id`)
- 본문 저장·버전 갱신: `backend/src/main/java/fruition/document/service/DocumentService.java`의 `saveContent`, `DocumentRepository.updateContentIfVersionMatches`
- 클라이언트 스냅샷(승격 대상): `frontend/app/_components/history/snapshotStore.ts`, `useSnapshots.ts`, `HistoryPanel.tsx`

## 2. Agent turn ↔ chat session 연결

`POST /api/workspaces/{workspace_id}/agent/turn`은 구현됐고, 오래된 `baseVersion`을 pipeline 호출 전에 `409`로 거절하는 처리도 완료됐다(→ backlog 참조). 남은 것은 대화 context를 backend가 구성하는 부분이다.

### 남은 작업

- 현재 `conversationContext`는 클라이언트가 채워 보내고 backend는 그대로 pipeline에 전달만 한다. Agent 요청을 chat session에 연결해 최근 대화 요약·reference context를 backend에서 구성한다.
- `sessionId`를 request에 추가하거나 endpoint를 `/api/workspaces/{workspace_id}/chat/sessions/{session_id}/agent/turn`으로 두는 방식을 결정한다.
- 영속 content 저장 API까지 포함한 권한·version·timeout 통합 테스트를 추가한다.

### 확인 위치

- 전체 계약: `docs/spec/agent-markdown-contract.md`
- Spring endpoint: `backend/src/main/java/fruition/agent/controller/AgentTurnController.java`
- context 전달만 하는 현재 구현: `backend/src/main/java/fruition/agent/repository/PipelineAgentRequester.java`의 `toPayload`
- pipeline endpoint: `llmPipeline/app/modules/agent/interfaces/http/routes.py`의 `POST /agent/turn`

## 3. workspace 폴더 트리 영속화 API

폴더 데이터 모델(`source_folders` 테이블·엔티티·리포지토리)은 준비돼 있으나 이를 쓰는 REST API와 서비스 로직이 없다. `SourceFolderRepository`는 빈 인터페이스이며 코드베이스에서 사용처가 없다. 프론트는 여전히 workspace별 `localStorage`로만 트리를 관리한다.

### 필요한 API 계약

- `GET /api/workspaces/{workspace_id}/document-tree` — 폴더 계층·문서 배치·형제 정렬 순서 반환
- `POST /api/workspaces/{workspace_id}/folders` — 폴더 생성(이름·상위 폴더·정렬 위치)
- `PATCH /api/workspaces/{workspace_id}/folders/{folder_id}` — 이름·상위 폴더·정렬 위치 변경
- `DELETE /api/workspaces/{workspace_id}/folders/{folder_id}` — 비어 있지 않은 폴더 삭제 정책 명시
- `PATCH /api/workspaces/{workspace_id}/documents/{document_id}/placement` — 문서 폴더 ID·정렬 위치 변경(최상위는 `folder_id: null`)
- 전체 트리를 덮어쓰지 않도록 version 또는 `updated_at` 기반 조건부 변경 계약이 필요하다.

### Backend 구현 작업

1. 같은 부모 안의 폴더·문서 정렬 순서를 저장할 모델을 확정한다.
2. 폴더 생성·이름 변경·이동·삭제와 문서 배치 변경을 transaction으로 처리한다.
3. 폴더를 자기 자신이나 하위 폴더로 이동하는 순환 구조를 차단한다.
4. 모든 조회·변경에서 workspace 구성원 권한과 대상 folder/document 소속을 검증한다.
5. 문서 업로드 시 기본 배치 위치와 폴더 삭제 시 포함 문서 처리 정책을 확정한다.
6. 동시 이동·이름 변경 충돌 응답을 정의한다.

### 확인 위치

- 준비된 모델: `backend/src/main/java/fruition/document/domain/SourceFolder.java`(`parentFolderId`, `sortOrder`), `V9__add_document_editing_core.sql`의 `source_folders`, `Document.java`의 `sourceFolderId`/`sortOrder`
- 미사용 리포지토리: `backend/src/main/java/fruition/document/repository/SourceFolderRepository.java`
- 프론트 임시 저장: `frontend/app/_hooks/useProjectTree.ts`, 이동 로직 `frontend/app/_lib/tree.ts`의 `moveProjectTreeItem`

## 4. 문서 업로드 ↔ Ingest 분리

`POST /api/workspaces/{workspace_id}/documents`는 Markdown 업로드 시 즉시 `processing` 상태로 두고 pipeline 요청까지 자동 등록한다. 여러 문서를 먼저 정리·편집한 뒤 사용자가 명시적으로 Ingest를 시작하는 흐름을 구현할 수 없다.

### 필요한 API 계약

- 업로드는 Object Storage와 `documents` 레코드 저장까지만 하고 `uploaded` 상태를 반환한다.
- `POST /api/workspaces/{workspace_id}/documents/{document_id}/ingest` — `uploaded` 문서를 `processing`으로 전환하고 pipeline 요청을 등록한다. 편집 Markdown을 선택적으로 받으면 같은 transaction에서 원본·`content_hash`·`byte_size`를 갱신한 뒤 재처리한다. 중복 요청은 idempotent 처리하거나 명확한 충돌 응답을 반환한다.

### 확인 위치

- 현재 업로드·자동 처리: `backend/src/main/java/fruition/document/service/DocumentService.java`의 `upload`(Markdown이면 `requestProcessingAfterCommit` 호출), 초기 상태 `Document.java`의 생성자 기본값 `processing`
- 업로드 endpoint: `backend/src/main/java/fruition/document/controller/DocumentController.java`
- 프론트 업로드 호출: `frontend/app/_lib/api.ts`의 `uploadDocumentFile`

## 5. 계층 트리 cascade 삭제·트리 복구

단일 문서 소프트 삭제·복구와 `delete_operation_id` 컬럼은 구현됐으나, 부모 삭제 시 하위 트리를 함께 삭제하는 로직과 원위치(부모·순서) 트리 복구가 없다. 현재 복구는 역할별 최상위 마지막 위치로만 배치한다.

### 남은 작업

- 부모 페이지 삭제 시 전체 하위 페이지를 같은 `delete_operation_id`로 함께 삭제한다.
- 전체 트리 복구는 기존 부모와 순서를 복원한다(현재는 최상위 마지막 위치로만 복구).
- 원본 폴더 트리 삭제·복구를 구현한다.
- 영구 삭제 보존 기간과 실행 주체를 결정한다.

### 확인 위치

- 단일 삭제·복구(하위 미포함): `DocumentService.java`의 `delete`(`softDeleteIfVersionMatches` 단건 호출), `restore`(최상위 마지막 위치로 복구), `DocumentRepository.java`의 `softDeleteIfVersionMatches`/`restoreIfVersionMatches`
- 컬럼: `V9__add_document_editing_core.sql`의 `delete_operation_id`(documents/source_folders), `Document.java`/`SourceFolder.java`
- SDD: `docs/spec/sdd/markdown-document-hierarchy.md`의 `REQ-H013`, `REQ-H014`; `docs/spec/sdd/tasks/markdown-document-hierarchy-tasks.md`의 `TASK-H006`

## 6. Markdown 외 문서 형식(PDF/DOCX) 확장

비-Markdown 업로드는 `uploaded` 읽기 전용 원본 저장까지만 하고 변환 pipeline을 실행하지 않는다. DOCX는 허용 MIME도 아니다(`ALLOWED_MIME_TYPES = {application/pdf, text/markdown, text/x-markdown}`).

### 남은 작업

- 지원 형식·MIME 정책을 정의한다.
- `llmPipeline`의 PDF 문서 복원 CLI를 worker 또는 API로 연결하고 저장 경로를 정의한다.
- 변환 작업 run ID를 Wiki 생성 pipeline run ID와 분리한다.
- 변환 결과 callback의 인증·멱등성·checksum·크기 제한 계약을 정의하고, 변환 완료 후 Wiki pipeline 시작 순서를 정의한다.
- PDF를 `.md` 복제본으로 만드는 기능은 변환 편집본 등록 완료 후 `POST /duplicate`와 연결한다.
- PDF 등 Markdown 외 내보내기 형식과 이미지·첨부 자원 포함 정책을 정의한다.

### 확인 위치

- 비-Markdown 원본 저장만: `DocumentService.java`의 `upload`(`!markdownUpload`이면 `DocumentStatus.uploaded`, 큐 미등록)
- 허용 MIME: `DocumentController.java`의 `ALLOWED_MIME_TYPES`
- 파이프라인 콜백(상태만): `backend/src/main/java/fruition/document/controller/DocumentPipelineController.java`
- SDD: `docs/spec/sdd/markdown-document-core.md`의 `변환 계약`, `DEC-003/004`; `docs/spec/sdd/tasks/markdown-document-core-tasks.md`의 `TASK-005`
- pipeline CLI: `llmPipeline/app/modules/document_restoration/interfaces/cli.py`

## 7. 운영 이메일 인증 메일 서버 연동

발송 구현이 인증번호를 로그에 남기는 개발용 stub(`LoggingEmailVerificationSender`)뿐이다. 프로필 제한 없이 무조건 `@Component`로 등록된다. 로컬은 고정 코드 `9700`을 쓴다.

### 남은 작업

1. `backend/build.gradle`에 `spring-boot-starter-mail`(또는 SendGrid/SES SDK)를 추가한다(현재 mail 의존성 없음).
2. `SmtpEmailVerificationSender` 운영 구현을 추가하고, `LoggingEmailVerificationSender`를 `@Profile("local")`(또는 `@ConditionalOnProperty`)로 배타 등록한다.
3. `MAIL_*`/`SMTP_*` 또는 provider API key를 `.env.example`과 `application*.properties`(`spring.mail.*`)에 추가한다.
4. 발송 실패·timeout·재시도 정책과 목적별 메일 template을 적용한다.
5. production 가드: `AUTH_EMAIL_DEV_FIXED_CODE`가 비어 있고 dev stub이 미등록임을 기동 시 검증한다.
6. provider sandbox 또는 test double 통합 테스트를 추가한다.

### 확인 위치

- 발급·검증: `backend/src/main/java/fruition/user/service/EmailVerificationService.java`
- 발송 interface·개발 stub: `backend/src/main/java/fruition/user/mail/EmailVerificationSender.java`, `LoggingEmailVerificationSender.java`
- 환경별 고정 코드: `application.properties:62`(운영 빈값), `application-local.properties:3`(9700)
- 프론트 자동 감지: `frontend/app/(auth)/_hooks/useDevelopmentVerificationCode.ts`

## 9. 직접 생성 Markdown의 레거시 `/original` 계약

`GET /api/workspaces/{workspace_id}/documents/{document_id}/original`은 `source_uri`가 있는 업로드 원본만 스트리밍한다. 직접 생성 Markdown은 `source_uri=null`이라 여전히 `404 DOCUMENT_ORIGINAL_NOT_FOUND`를 반환한다. 최신 편집본은 별도 `/export`가 담당한다.

### 결정 필요

- 레거시 `/original`에서도 직접 생성 문서의 최신 편집 상태를 `text/markdown`으로 반환할지 결정한다.
- 지원한다면 업로드 원본 조회와 최신 편집본 내보내기의 역할 중복을 정리하고 회귀 테스트를 추가한다.

### 확인 위치

- `DocumentService.java`의 `getOriginal`(`source_uri` null이면 404), `DocumentExportService.exportMarkdown`
- `DocumentController.java`의 `GET .../original`, `GET .../export`
- SDD: `docs/spec/sdd/markdown-document-core.md`의 `REQ-006a`
