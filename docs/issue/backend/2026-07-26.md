## 2. Agent turn 대화 맥락 — `chat_answer`·`markdown_create`에만 적용 (범위 축소)

원래 "agent turn을 chat session에 연결해 backend가 대화 요약·reference context를 구성"하려던 이슈다. 코드 확인 결과 **대부분 불필요**해 범위를 좁힌다.

### 코드 확인으로 드러난 현황

- **편집/대화는 프론트에서 이미 분리**된다. 같은 입력창이지만 문서 편집기가 열려 있으면(`markdownEditContext` 있음) `POST /agent/turn`(편집), 아니면 `POST /chat/sessions/{id}/query`(대화)로 자동 분기한다(`frontend/.../AgentPanel.tsx`의 `handleSubmit`). 사용자가 모드를 고르는 게 아니라 "문서 열림 여부"로 결정된다.
- **agent turn 결과는 채팅 메시지로 저장되지 않는다**(로컬 임시 상태). 즉 편집 중 편집기 draft·응답이 query의 대화·지식에 섞이지 않는다. Q&A 지식 오염 우려는 구조적으로 이미 방지됨.
- 프론트가 소비하는 action은 **`markdown_edit`(편집)·`markdown_create`(생성)이 주력**, `chat_answer`/`clarify`/`reject`는 한 줄 알림 수준.
- **`conversationContext`는 이미 선택적·클라이언트 주도**다. 편집 중 사용자가 **선택한 채팅 문답만**(`buildSelectedConversationSummary(selectedPairIds)`) 요약해 보내고, 없으면 필드를 생략한다.

### 결론(축소된 범위)

- **`markdown_edit`(순수 편집)는 대화 맥락 불필요.** backend의 chat session 연결·요약 구성은 **하지 않는다.**
- **대화 맥락이 의미 있는 유일한 경우는 편집 중 `chat_answer`·`markdown_create`** 뿐이며, 그 맥락은 **프론트가 사용자 선택 기반으로 optional하게 첨부**하는 현행 방식을 유지한다.
- 따라서 backend는 `conversationContext`를 **받아서 pipeline `conversation_context`로 전달만** 한다(현행 `PipelineAgentRequester.toPayload` 그대로). `sessionId` 연결·요약 자동 구성·`contextSummary` 유지 로직은 **불필요**로 판단해 진행하지 않는다.

### 남은(선택) 후속

- 편집 중 `chat_answer`/`markdown_create`의 대화 맥락 품질을 높이려면(사용자 선택 대신 자동 요약 등) 별도 소규모 이슈로 다룬다. 자동 LLM 요약이 필요하면 AI 팀 요약 endpoint가 선행이다.
- `ChatSession.contextSummary` 필드는 현재 어디서도 갱신되지 않는 미사용 placeholder다. 위 자동 요약을 도입할 때만 채운다.

### 확인 위치

- 프론트 분기: `frontend/src/widgets/agent-panel/ui/AgentPanel.tsx`의 `handleSubmit`, 편집 컨텍스트 발행 `frontend/src/features/note-editing/ui/NoteEditor.tsx`의 `onMarkdownEditContextChange`
- 계약: `docs/spec/agent-markdown-contract.md`(`conversationContext`는 optional)
- 전달만 하는 현재 구현: `backend/src/main/java/fruition/agent/repository/PipelineAgentRequester.java`의 `toPayload`
- pipeline endpoint: `llmPipeline/app/modules/agent/interfaces/http/routes.py`의 `POST /agent/turn`

## 5. 계층 트리 cascade 삭제·복구 — 해결

계층은 폴더 트리(`source_folders`) 하나다(페이지 중첩 `parent_document_id`는 제거됨). 폴더 삭제는 하위 폴더·문서를 같은 `delete_operation_id`로 cascade 소프트 삭제(항목 3)하고, 폴더 복구는 그 그룹을 삭제 시점 트리·배치를 보존하며 되살린다. 문서 복구도 원래 폴더가 살아 있으면 그 폴더로 복원한다.

- 폴더 복구: `POST /folders/{folder_id}/restore` — 그룹 트리 보존 복구 + 고아 항목 최상위 fixup
- 문서 복구: `POST /documents/{document_id}/restore` — 원래 폴더 활성 시 그 폴더·순서, 사라졌으면 최상위 마지막
- 해결 기록: [`docs/backlog/issue-2026-07-26.md`](../../backlog/issue-2026-07-26.md)의 `폴더 트리 cascade 삭제·복구`

## 6. Markdown 외 문서 형식(PDF/DOCX) 확장

비-Markdown 업로드는 `uploaded` 읽기 전용 원본 저장까지만 하고 변환 pipeline을 실행하지 않는다. DOCX는 허용 MIME도 아니다(`ALLOWED_MIME_TYPES = {application/pdf, text/markdown, text/x-markdown}`).

### 남은 작업

- 지원 형식·MIME 정책을 정의한다.
- `llmPipeline`의 PDF 문서 복원 CLI를 worker 또는 API로 연결하고 저장 경로를 정의한다.

- PDF 등 Markdown 외 내보내기 형식과 이미지·첨부 자원 포함 정책을 정의한다.

## 9. 직접 생성 Markdown의 레거시 `/original` 계약 — 결정 완료 (변경 없음)

**결정: A안 — `/original`은 "업로드 원본 전용"으로 유지한다.** 직접 생성 문서(`source_uri=null`)는 계속 `404 DOCUMENT_ORIGINAL_NOT_FOUND`를 반환하고, 최신 편집본은 `/export`(다운로드)·`/content`(편집기)가 담당한다.

근거:
- 프론트의 모든 노트 생성(신규 노트·AI 초안)은 멀티파트 업로드(`uploadDocumentFile`)를 타므로 `source_uri`가 항상 존재한다. 즉 `source_uri=null` 케이스는 현재 프론트에서 발생하지 않아 404가 실제로 노출되지 않는다.
- `/export`·`/content`가 최신 편집본을 이미 제공하므로, `/original`에 fallback을 넣는 건 소비자 없는 speculative 코드가 된다.
- 재ingest(항목 4)로 편집본이 원본을 갱신하므로 `/original`은 "확정 원문"의 역할을 그대로 유지한다.
- `POST /markdown`·`POST /duplicate`(source_uri=null 생성)는 현재 프론트 소비자가 없다. 향후 이들을 프론트에서 쓰게 되면 그때 다시 검토한다.

해결 기록: [`docs/backlog/issue-2026-07-26.md`](../../backlog/issue-2026-07-26.md)

## 10. Kakao OAuth — 앱 구현·자격증명 완료 (콘솔 설정 확인만 남음)

비즈 앱 전환·이메일 동의 승인이 완료돼 보류가 해제됐다. **backend·frontend 코드와 설정은 이미 완비**돼 있어 앱 쪽에서 새로 짤 것은 없다.

- **Backend 코드**: `OAuth2UserInfoFactory`의 `case "kakao"`, `KakaoOAuth2UserInfo`(`kakao_account.email`·`profile.nickname` 추출).
- **Backend 설정**: `application.properties`에 kakao registration/provider 완비(`scope=profile_nickname,account_email`, `client_secret_post`, provider URI, `user-name-attribute=id`).
- **Frontend**: `AuthControls.tsx`의 "카카오" 버튼 → `/oauth2/authorization/kakao`.
- **자격증명**: `infra/.env`의 `KAKAO_CLIENT_ID`·`KAKAO_CLIENT_SECRET` 주입됨. `bootRun`이 `infra/.env`를 환경변수로 로드한다(`backend/build.gradle`의 bootRun `doFirst`).

### 남은 확인 (카카오 개발자 콘솔, 코드 밖)

- Redirect URI 등록: `{baseUrl}/login/oauth2/code/kakao` (로컬 `http://localhost:8080/...`, 운영 도메인).
- Client Secret: 설정이 `client_secret_post`이므로 콘솔에서 Client Secret 사용(활성화)하고 `KAKAO_CLIENT_SECRET`과 일치시킨다.
- 로컬에서 "카카오" 버튼으로 실제 로그인 검증. 실패 시 에러 코드(예: `OAUTH_EMAIL_NOT_PROVIDED`, redirect_uri mismatch, KOE010)로 원인 확인.

- 배경: `docs/backlog/issue-2026-07-03.md`의 Kakao OAuth 섹션.
