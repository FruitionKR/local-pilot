## 1. 문서 콘텐츠 버전 이력·롤백 서버화 — 해결

`document_content_versions` 테이블(V11)과 조회·복원 API를 추가해 콘텐츠 버전 이력을 서버에 보관한다. 스냅샷은 **AI 편집 적용(`PUT /content`의 `source=agent`) 시에만** 남긴다(수동 저장·baseline은 남기지 않음). `POST .../versions/{version}/restore`로 과거 AI 편집 시점 내용으로 비파괴 복원한다(복원 자체는 새 스냅샷 미기록).

- 해결 기록: [`docs/backlog/issue-2026-07-26.md`](../../backlog/issue-2026-07-26.md)의 `문서 콘텐츠 버전 이력·롤백`

### 남은 후속

- **프론트 배선**: AI Apply 저장 시 `PUT /content`에 `source=agent`를 보내야 스냅샷이 쌓인다. 아울러 `PUT /content` 계약 불일치(프론트가 옛 JSON `expected_content_version` 사용)를 해소해야 저장 자체가 동작한다 → `docs/issue/frontend/2026-07-24.md`.

- diff(-/+)는 백엔드가 전체 본문을 제공하고 프론트가 계산한다(백엔드 diff 미제공).

## 2. Agent turn ↔ chat session 연결

`POST /api/workspaces/{workspace_id}/agent/turn`은 구현됐고, 오래된 `baseVersion`을 pipeline 호출 전에 `409`로 거절하는 처리도 완료됐다(→ backlog 참조). 남은 것은 대화 context를 backend가 구성하는 부분이다.

### 남은 작업

- 현재 `conversationContext`는 클라이언트가 채워 보내고 backend는 그대로 pipeline에 전달만 한다. Agent 요청을 chat session에 연결해 최근 대화 요약·reference context를 backend에서 구성한다.
- `sessionId`를 request에 추가하거나 endpoint를 `/api/workspaces/{workspace_id}/chat/sessions/{session_id}/agent/turn`으로 두는 방식을 결정한다.
- 영속 content 저장 API까지 포함한 권한·version·timeout 통합 테스트를 추가한다.

### 확인 위치

- 전체 계약: `docs/spec/agent-markdown-contract.md`
- Spring endpoint: `backend/src/main/java/fruition/agent/controller/AgentTurnController.java`
- context 전달만 하는 현재 구현: `backend/src/main/java/fruition/agent/repository/PipelineAgentRequester.java`의 `toPayload`
- pipeline endpoint: `llmPipeline/app/modules/agent/interfaces/http/routes.py`의 `POST /agent/turn`

## 3. workspace 폴더 트리 영속화 API — 해결

`source_folders` 모델을 REST API로 연결했다. 엔드포인트 5종(`GET /document-tree`, `POST /folders`, `PATCH /folders/{id}`, `DELETE /folders/{id}`, `PATCH /documents/{id}/placement`)을 추가하고, 폴더 삭제는 cascade 소프트 삭제, 이동은 순환 차단, 변경은 `base_version` 낙관적 잠금으로 처리한다.

- 해결 기록: [`docs/backlog/issue-2026-07-26.md`](../../backlog/issue-2026-07-26.md)의 `폴더 트리 영속화 API`
- 요약: `docs/changelog/backend.md` 2026-07-26 항목

### 남은 후속

- **폴더 복구(트리 복원)**: cascade 소프트 삭제된 폴더를 되살리는 기능은 미구현 → `5. 계층 트리 cascade 삭제·트리 복구`와 함께 다룬다. 함께 삭제된 문서는 `POST /documents/{id}/restore`로 개별 복구 가능.
- 프론트 `useProjectTree`의 `localStorage` 저장을 이 API로 교체(프론트 작업).

## 4. 문서 업로드 ↔ Ingest 분리

### 진행 상황

- **1단계(완료, additive)**: `POST /api/workspaces/{workspace_id}/documents/{document_id}/ingest`를 추가했다. 편집 가능 Markdown 문서의 DB 편집본을 MinIO 원본으로 승격한 뒤 재처리해, 편집한 내용으로 위키를 다시 만들 수 있다. 이미 `processing`이면 `409 DOCUMENT_ALREADY_PROCESSING`으로 거절한다. **업로드 자동 처리는 그대로 유지**해 기존 흐름을 깨지 않는다. → 해결 기록: [`docs/backlog/issue-2026-07-26.md`](../../backlog/issue-2026-07-26.md)

### 남은 작업 (2단계, 프론트 대응 필요)

- 업로드를 저장까지만 하고 `uploaded` 상태를 반환하도록 전환한다(자동 처리 off). 지금 끄면 프론트가 깨지므로 프론트 ingest 버튼과 함께 진행해야 한다.
- 프론트에 ingest 버튼 UI를 추가하고, 업로드 즉시 처리 의존을 제거한다(프론트 이슈로 별도 관리).
- 비-Markdown(PDF 등) ingest는 `6. Markdown 외 문서 형식 확장`과 함께 다룬다.

### 확인 위치

- 재ingest: `backend/src/main/java/fruition/document/service/DocumentService.java`의 `ingest`, `Document.java`의 `reopenForReingest`
- 현재 업로드·자동 처리: `DocumentService.java`의 `upload`(Markdown이면 `requestProcessingAfterCommit` 호출), 초기 상태 `Document.java` 생성자 기본값 `processing`
- 업로드 endpoint: `backend/src/main/java/fruition/document/controller/DocumentController.java`
- 프론트 업로드 호출: `frontend/src/entities/document/api/document.ts`의 `uploadDocumentFile`(신규 노트·AI 초안 모두 이 업로드 경로 사용)

## 5. 계층 트리 cascade 삭제·복구 — 해결

계층은 폴더 트리(`source_folders`) 하나다(페이지 중첩 `parent_document_id`는 제거됨). 폴더 삭제는 하위 폴더·문서를 같은 `delete_operation_id`로 cascade 소프트 삭제(항목 3)하고, 폴더 복구는 그 그룹을 삭제 시점 트리·배치를 보존하며 되살린다. 문서 복구도 원래 폴더가 살아 있으면 그 폴더로 복원한다.

- 폴더 복구: `POST /folders/{folder_id}/restore` — 그룹 트리 보존 복구 + 고아 항목 최상위 fixup
- 문서 복구: `POST /documents/{document_id}/restore` — 원래 폴더 활성 시 그 폴더·순서, 사라졌으면 최상위 마지막
- 해결 기록: [`docs/backlog/issue-2026-07-26.md`](../../backlog/issue-2026-07-26.md)의 `폴더 트리 cascade 삭제·복구`
- 요약: `docs/changelog/backend.md` 2026-07-26 항목

### 남은 후속

- **영구 삭제 보존 기간·실행 주체** 결정(운영 정책). 관련 AI 정책: `docs/issue/ai/2026-07-25.md`의 workspace 복구 시 산출물 유지/폐기.

## 6. Markdown 외 문서 형식(PDF/DOCX) 확장

비-Markdown 업로드는 `uploaded` 읽기 전용 원본 저장까지만 하고 변환 pipeline을 실행하지 않는다. DOCX는 허용 MIME도 아니다(`ALLOWED_MIME_TYPES = {application/pdf, text/markdown, text/x-markdown}`).

### 남은 작업

- 지원 형식·MIME 정책을 정의한다.
- `llmPipeline`의 PDF 문서 복원 CLI를 worker 또는 API로 연결하고 저장 경로를 정의한다.
- 변환 작업 run ID를 Wiki 생성 pipeline run ID와 분리한다.
- 변환 결과 callback의 인증·멱등성·checksum·크기 제한 계약을 정의하고, 변환 완료 후 Wiki pipeline 시작 순서를 정의한다.
- PDF를 `.md` 복제본으로 만드는 기능은 변환 편집본 등록 완료 후 `POST /duplicate`와 연결한다.
- PDF 등 Markdown 외 내보내기 형식과 이미지·첨부 자원 포함 정책을 정의한다.

### 확인 위치

- 비-Markdown 원본 저장만: `DocumentService.java`의 `upload`(`!markdownUpload`이면 `DocumentStatus.uploaded`, 큐 미등록)
- 허용 MIME: `DocumentController.java`의 `ALLOWED_MIME_TYPES`
- 파이프라인 콜백(상태만): `backend/src/main/java/fruition/document/controller/DocumentPipelineController.java`
- SDD: `docs/spec/sdd/markdown-document-core.md`의 `변환 계약`, `DEC-003/004`; `docs/spec/sdd/tasks/markdown-document-core-tasks.md`의 `TASK-005`
- pipeline CLI: `llmPipeline/app/modules/document_restoration/interfaces/cli.py`

## 7. 운영 이메일 인증 메일 서버 연동

발송 구현이 인증번호를 로그에 남기는 개발용 stub(`LoggingEmailVerificationSender`)뿐이다. 프로필 제한 없이 무조건 `@Component`로 등록된다. 로컬은 고정 코드 `9700`을 쓴다.

### 남은 작업

1. `backend/build.gradle`에 `spring-boot-starter-mail`(또는 SendGrid/SES SDK)를 추가한다(현재 mail 의존성 없음).
2. `SmtpEmailVerificationSender` 운영 구현을 추가하고, `LoggingEmailVerificationSender`를 `@Profile("local")`(또는 `@ConditionalOnProperty`)로 배타 등록한다.
3. `MAIL_*`/`SMTP_*` 또는 provider API key를 `.env.example`과 `application*.properties`(`spring.mail.*`)에 추가한다.
4. 발송 실패·timeout·재시도 정책과 목적별 메일 template을 적용한다.
5. production 가드: `AUTH_EMAIL_DEV_FIXED_CODE`가 비어 있고 dev stub이 미등록임을 기동 시 검증한다.
6. provider sandbox 또는 test double 통합 테스트를 추가한다.

### 확인 위치

- 발급·검증: `backend/src/main/java/fruition/user/service/EmailVerificationService.java`
- 발송 interface·개발 stub: `backend/src/main/java/fruition/user/mail/EmailVerificationSender.java`, `LoggingEmailVerificationSender.java`
- 환경별 고정 코드: `application.properties:62`(운영 빈값), `application-local.properties:3`(9700)
- 프론트 자동 감지: `frontend/app/(auth)/_hooks/useDevelopmentVerificationCode.ts`

## 9. 직접 생성 Markdown의 레거시 `/original` 계약 — 결정 완료 (변경 없음)

**결정: A안 — `/original`은 "업로드 원본 전용"으로 유지한다.** 직접 생성 문서(`source_uri=null`)는 계속 `404 DOCUMENT_ORIGINAL_NOT_FOUND`를 반환하고, 최신 편집본은 `/export`(다운로드)·`/content`(편집기)가 담당한다.

근거:
- 프론트의 모든 노트 생성(신규 노트·AI 초안)은 멀티파트 업로드(`uploadDocumentFile`)를 타므로 `source_uri`가 항상 존재한다. 즉 `source_uri=null` 케이스는 현재 프론트에서 발생하지 않아 404가 실제로 노출되지 않는다.
- `/export`·`/content`가 최신 편집본을 이미 제공하므로, `/original`에 fallback을 넣는 건 소비자 없는 speculative 코드가 된다.
- 재ingest(항목 4)로 편집본이 원본을 갱신하므로 `/original`은 "확정 원문"의 역할을 그대로 유지한다.
- `POST /markdown`·`POST /duplicate`(source_uri=null 생성)는 현재 프론트 소비자가 없다. 향후 이들을 프론트에서 쓰게 되면 그때 다시 검토한다.

해결 기록: [`docs/backlog/issue-2026-07-26.md`](../../backlog/issue-2026-07-26.md)
