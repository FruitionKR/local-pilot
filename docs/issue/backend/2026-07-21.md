# 2026-07-21 Backend 이슈

## 1. 이메일 인증 기반 회원가입 계약

Figma 회원가입·비밀번호 재설정 화면에 필요한 이메일 인증 API가 없다. 기존 이슈는 [`docs/issue/backend/2026-07-16.md`](2026-07-16.md)의 `3. 인증 화면 도입을 위한 API 계약 보완`에서 이관했다.

### 현재 상태

- `AuthController`는 `POST /api/auth/signup`, `POST /api/auth/login`, `POST /api/auth/refresh`, `POST /api/auth/logout`, `POST /api/auth/oauth/exchange`, `GET /api/auth/me`만 제공한다.
- `POST /api/auth/signup`은 중복 이메일에 `409 DUPLICATE_EMAIL`을 반환하고 선택 필드 `display_name`을 받는다. 닉네임 저장 자체는 구현 완료됐다.
- 인증번호 발급·저장·검증, 만료, 재요청 제한, verification token endpoint는 없다.
- 프론트엔드는 개발 환경에서 임시 인증번호 `9700`을 사용하며 production에서는 이 우회를 비활성화한다.
- 현재 프론트 작업 트리는 중복 이메일의 다음 화면 진입을 막기 위해 `인증 요청` 단계에서 `POST /api/auth/signup`을 먼저 호출한다. 사용자가 인증을 중단해도 계정이 생성되는 임시 우회이므로 실제 인증 API 연결 시 제거해야 한다.

### 필요한 API 계약

#### 1. 인증 요청

- `POST /api/auth/email-verifications`
- 입력: `email`, `purpose`(`signup` 또는 `password_reset`)
- 응답: `verification_id`, `expires_in`, `retry_after`
- `signup` 용도에서 기존 회원의 다음 화면 진입을 막으려면 `409 DUPLICATE_EMAIL`을 반환한다. 이메일 존재 여부 노출을 허용하는 정책이므로 rate limit과 감사 로그를 함께 적용한다.
- `password_reset` 용도는 계정 존재 여부와 관계없이 동일한 응답을 반환한다.
- 재요청 cooldown, 일일 횟수 제한, 새 인증번호 발급 시 기존 번호 폐기 규칙을 적용한다.

#### 2. 인증번호 검증

- `POST /api/auth/email-verifications/{verification_id}/confirm`
- 입력: `code`
- 응답: 1회 사용 가능한 `verification_token`, `expires_in`
- `INVALID_VERIFICATION_CODE`, `VERIFICATION_CODE_EXPIRED` 오류 code를 구분한다.

#### 3. 최종 회원가입

- `POST /api/auth/signup`에 `verification_token`을 필수로 추가한다.
- 입력: `email`, `password`, `display_name`, `verification_token`
- token의 email·purpose가 요청과 일치하는지 검증하고, 만료·1회 사용·가입 성공 시 폐기 규칙을 적용한다.
- 이메일 중복은 인증 요청과 최종 가입 모두에서 검증해 경쟁 조건을 막는다.

### 비밀번호 재설정 계약

- 인증 완료 후 회원가입 token과 구분되는 단기 `reset_token`을 발급한다.
- `reset_token`으로 비밀번호를 변경하는 endpoint와 성공 시 기존 refresh token 전체 폐기 여부를 확정한다.
- 가입되지 않은 이메일에도 동일한 응답을 반환해 계정 존재 여부를 보호한다.

### 추가 결정 사항

- 현재 별도 사용자 아이디·전화번호·복구 이메일이 없으므로 `아이디 찾기`를 제거하거나 검증 수단을 먼저 추가해야 한다.
- 현재 비밀번호 계약은 `8~72자`만 검증한다. `PASSWORD_TOO_SHORT`, `PASSWORD_POLICY_VIOLATION`, `INVALID_CREDENTIALS` 등 오류 code와 조합 규칙을 확정해야 한다.
- 로그인 실패 응답은 이메일 존재 여부와 비밀번호 오류를 구분하지 않는 현재 원칙을 유지한다.

### 완료 조건

- 회원가입 인증 요청에서 중복 이메일이 다음 단계로 진입하지 않는다.
- 인증번호 만료·재요청·오류 code·rate limit 정책이 백엔드 테스트로 검증된다.
- 유효한 `verification_token`이 없으면 회원가입이 실패하고, token은 성공 후 재사용할 수 없다.
- 프론트엔드의 임시 인증번호와 인증 전 회원가입 호출이 제거된다.
- 비밀번호 재설정은 계정 존재 여부를 노출하지 않고, 성공 후 token 폐기 정책을 따른다.

### 확인 위치

- 현재 Auth endpoint: `backend/src/main/java/fruition/user/controller/AuthController.java`의 `signup`, `login`, `refresh`, `logout`, `exchangeOAuthCode`, `me`
- 회원가입 요청: `backend/src/main/java/fruition/user/dto/SignupRequest.java`의 `email`, `password`, `display_name`
- 현재 API 계약: `docs/Fruition_MVP_API_Contract.md`의 `5. Auth API`, `POST /api/auth/signup`, `POST /api/auth/login`
- 프론트 임시 처리: `frontend/app/login/page.tsx`의 `handleSignupRequest`, 회원가입 인증 완료 effect

## 2. 노트 본문 저장 API 부재

사이드바의 `새 노트`는 초기 Markdown 파일을 기존 multipart 업로드 API로 저장해 생성할 수 있다. 그러나 WYSIWYG 편집 결과를 기존 문서에 다시 저장할 endpoint가 없다.

### 현재 상태

- 생성: `POST /api/workspaces/{workspace_id}/documents`에 `새 문서.md`를 업로드한다.
- 조회: `GET /api/workspaces/{workspace_id}/documents/{document_id}/original`로 원본 Markdown을 읽는다.
- 변경: 파일명 변경 endpoint만 있고 본문 갱신 endpoint는 없다.

### 필요한 API 계약

- `PUT /api/workspaces/{workspace_id}/documents/{document_id}/content`
- 입력: Markdown 본문과 충돌 감지를 위한 문서 version 또는 `updated_at`.
- 처리: MinIO 원본 교체, `content_hash`·`byte_size` 갱신, 수정 시각 기록.
- 편집 저장 후 파이프라인을 다시 실행할지와 기존 Wiki page를 어떻게 조정할지 정책을 확정한다.
- 자동 저장 요청이 겹칠 때 이전 요청이 최신 본문을 덮어쓰지 않도록 충돌 응답을 정의한다.

### 완료 조건

- 인증된 workspace 구성원만 노트 본문을 수정할 수 있다.
- 저장 후 원본 조회에서 최신 Markdown이 반환된다.
- 동시 저장 충돌, 빈 본문, 중복 콘텐츠, 저장소 실패가 backend 테스트로 검증된다.

### 확인 위치

- 문서 업로드·원본 조회: `backend/src/main/java/fruition/document/controller/DocumentController.java`의 `upload`, `getOriginal`
- 원본 저장·해시 처리: `backend/src/main/java/fruition/document/service/DocumentService.java`의 `upload`
- 프론트 원본 조회: `frontend/app/_lib/api.ts`의 `fetchDocumentOriginal`

### 프론트엔드 프로토타입 결정

- 이번 단계에서는 production 본문 저장을 구현하지 않는다.
- Spring `local` profile에서만 메모리 기반 example mock을 제공한다.
- mock은 version 충돌 계약만 검증하고 DB, MinIO, Wiki와 pipeline을 변경하지 않는다.
- mock 계약과 frontend 구현 순서는 `docs/spec/note-editor-prototype.md`의 `4. local backend mock 계약`, `6. 구현 순서`를 따른다.
- 이 이슈의 production 완료 조건은 그대로 미해결 상태로 유지한다.

## 3. documents.content_hash 중복 범위와 편집 노트 정책

기존 전역 `content_hash` UNIQUE 제약은 서로 다른 workspace의 동일 문서를 막는다. `(workspace_id, content_hash)` 복합 UNIQUE로 바꾸는 기존 제안도 같은 workspace 안에서 내용이 같은 노트 두 개를 저장하지 못하게 하므로 편집 노트에는 충분하지 않다.

### production 전환 시 필요한 결정

- DB의 전역 `content_hash` UNIQUE 제약을 제거한다.
- 일반 파일 업로드와 chat export 중복 판정은 workspace 범위의 애플리케이션 검사로 유지한다.
- 본문 편집 저장에서는 동일한 Markdown을 가진 여러 노트를 허용한다.
- 초기 노트의 `fruition-workspace` 및 새 노트의 `fruition-note` 내부 주석을 production 식별 수단으로 사용하지 않는다.
- editable note를 구분할 명시적 document kind/origin 계약을 추가한다.

### 완료 조건

- 서로 다른 workspace에 동일한 파일을 업로드할 수 있다.
- 같은 workspace의 일반 파일 재업로드는 정책에 따라 거부된다.
- 같은 workspace의 서로 다른 노트는 본문이 같아도 저장할 수 있다.
- 내부 식별 주석이 원본 Markdown과 pipeline 입력에 필요하지 않다.

### 확인 위치

- DB 제약: `backend/src/main/resources/db/migration/V1__baseline_schema.sql`의 `ukeafca5s6k4behm6am8avmcik3`
- JPA mapping: `backend/src/main/java/fruition/document/domain/Document.java`의 `contentHash`
- 중복 조회: `backend/src/main/java/fruition/document/repository/DocumentRepository.java`의 `findByContentHash`
- 업로드·초기 노트·chat export: `backend/src/main/java/fruition/document/service/DocumentService.java`

## 4. Markdown Agent turn public endpoint 부재

Frontend는 편집 중인 문서 snapshot을 보내는 Agent client를 구현했지만, 인증·권한과 문서 version을 검증한 뒤 `llmPipeline`의 `POST /agent/turn`으로 전달할 Spring endpoint가 없다.

Frontend의 diff preview, Apply/취소/재생성, stale buffer 차단과 새 Markdown draft 저장은 구현됐다. 이 이슈의 endpoint가 연결되면 mock 없이 실제 pipeline 응답으로 해당 흐름을 사용할 수 있다.

### 필요한 API 계약

- `POST /api/workspaces/{workspace_id}/agent/turn`
- 입력: `documentId`, `baseVersion`, `message`, 선택적 `conversationContext`, `editorSnapshot`
- 처리: workspace·document 접근 권한과 `baseVersion`을 검증하고 pipeline DTO의 snake_case 필드로 변환한다.
- 응답: pipeline 결과에 `documentId`, `baseVersion`, `requestId`를 붙여 frontend에 반환한다.
- pipeline의 400/422 detail code와 message를 보존하고, `markdown_edit` 응답만으로 문서를 저장하지 않는다.

### 완료 조건

- 권한 없는 workspace 또는 document 요청이 pipeline 호출 전에 거절된다.
- 오래된 `baseVersion` 요청이 충돌 응답으로 거절된다.
- `markdown_edit`, `clarify`, `reject` 응답과 422 구조 검증 오류가 frontend까지 보존된다.
- endpoint 통합 테스트에서 pipeline client 변환과 오류 mapping을 검증한다.

### 확인 위치

- 전체 계약: `docs/spec/agent-markdown-contract.md`의 `Frontend → Spring backend`, `Spring backend → llmPipeline`, `오류 처리`
- frontend 호출: `frontend/app/_lib/api.ts`의 `requestAgentTurn`
- frontend DTO: `frontend/app/_lib/markdownAgent.ts`의 `AgentTurnRequest`, `AgentTurnResponse`
- pipeline endpoint: `llmPipeline/app/modules/agent/http/routes.py`의 `POST /agent/turn`
