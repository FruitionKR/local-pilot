## 2. 노트 본문 저장 API 부재

사이드바의 `새 노트`는 초기 Markdown 파일을 기존 multipart 업로드 API로 저장해 생성할 수 있다. 그러나 WYSIWYG 편집 결과를 기존 문서에 다시 저장할 endpoint가 없다.

### 현재 상태

- 생성: `POST /api/workspaces/{workspace_id}/documents`에 `새 문서.md`를 업로드한다.
- 조회: `GET /api/workspaces/{workspace_id}/documents/{document_id}/original`로 원본 Markdown을 읽는다.
- 변경: 파일명 변경 endpoint만 있고 본문 갱신 endpoint는 없다.

### 필요한 API 계약

- `PUT /api/workspaces/{workspace_id}/documents/{document_id}/content`
- 입력: Markdown 본문과 충돌 감지를 위한 문서 version 또는 `updated_at`.
- 처리: MinIO 원본 교체, `content_hash`·`byte_size` 갱신, 수정 시각 기록.
- 편집 저장 후 파이프라인을 다시 실행할지와 기존 Wiki page를 어떻게 조정할지 정책을 확정한다.
- 자동 저장 요청이 겹칠 때 이전 요청이 최신 본문을 덮어쓰지 않도록 충돌 응답을 정의한다.

### 완료 조건

- 인증된 workspace 구성원만 노트 본문을 수정할 수 있다.
- 저장 후 원본 조회에서 최신 Markdown이 반환된다.
- 동시 저장 충돌, 빈 본문, 중복 콘텐츠, 저장소 실패가 backend 테스트로 검증된다.

### 확인 위치

- 문서 업로드·원본 조회: `backend/src/main/java/fruition/document/controller/DocumentController.java`의 `upload`, `getOriginal`
- 원본 저장·해시 처리: `backend/src/main/java/fruition/document/service/DocumentService.java`의 `upload`
- 프론트 원본 조회: `frontend/app/_lib/api.ts`의 `fetchDocumentOriginal`

### 프론트엔드 프로토타입 결정

- 이번 단계에서는 production 본문 저장을 구현하지 않는다.
- Spring `local` profile에서만 메모리 기반 example mock을 제공한다.
- mock은 version 충돌 계약만 검증하고 DB, MinIO, Wiki와 pipeline을 변경하지 않는다.
- mock 계약과 frontend 구현 순서는 `docs/spec/note-editor-prototype.md`의 `4. local backend mock 계약`, `6. 구현 순서`를 따른다.
- 이 이슈의 production 완료 조건은 그대로 미해결 상태로 유지한다.

## 3. documents.content_hash 중복 범위와 편집 노트 정책

기존 전역 `content_hash` UNIQUE 제약은 서로 다른 workspace의 동일 문서를 막는다. `(workspace_id, content_hash)` 복합 UNIQUE로 바꾸는 기존 제안도 같은 workspace 안에서 내용이 같은 노트 두 개를 저장하지 못하게 하므로 편집 노트에는 충분하지 않다.

### production 전환 시 필요한 결정

- DB의 전역 `content_hash` UNIQUE 제약을 제거한다.
- 일반 파일 업로드와 chat export 중복 판정은 workspace 범위의 애플리케이션 검사로 유지한다.
- 본문 편집 저장에서는 동일한 Markdown을 가진 여러 노트를 허용한다.
- 초기 노트의 `fruition-workspace` 및 새 노트의 `fruition-note` 내부 주석을 production 식별 수단으로 사용하지 않는다.
- editable note를 구분할 명시적 document kind/origin 계약을 추가한다.

### 완료 조건

- 서로 다른 workspace에 동일한 파일을 업로드할 수 있다.
- 같은 workspace의 일반 파일 재업로드는 정책에 따라 거부된다.
- 같은 workspace의 서로 다른 노트는 본문이 같아도 저장할 수 있다.
- 내부 식별 주석이 원본 Markdown과 pipeline 입력에 필요하지 않다.

### 확인 위치

- DB 제약: `backend/src/main/resources/db/migration/V1__baseline_schema.sql`의 `ukeafca5s6k4behm6am8avmcik3`
- JPA mapping: `backend/src/main/java/fruition/document/domain/Document.java`의 `contentHash`
- 중복 조회: `backend/src/main/java/fruition/document/repository/DocumentRepository.java`의 `findByContentHash`
- 업로드·초기 노트·chat export: `backend/src/main/java/fruition/document/service/DocumentService.java`

## 7. llmPipeline 실행 요청의 user_id, workspace_id 제거 검토

- 현재 `DocumentProcessingRequester`는 `documents`에서 읽은 `user_id`, `workspace_id`를 `/pipeline/runs`와 `/chat-wiki/runs` 요청 body에 포함한다.
- llmPipeline은 Wiki 저장 범위를 `document_id`로 조회하고 두 필드를 호환 목적으로만 수신한다.
- Backend 요청 DTO와 requester 인자에서 두 필드를 제거할지 협의하고, 제거 시 일반·채팅 요청 contract 테스트를 함께 갱신한다.
- 관련 위치: `docs/spec/chat-to-wiki-contract.md`의 `3. 채팅 입력 계약`, `backend/src/main/java/fruition/document/repository/DocumentProcessingRequester.java`.
