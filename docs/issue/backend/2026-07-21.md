# 2026-07-21 Backend 이슈

## 1. 이메일 인증 기반 회원가입 계약

Figma 회원가입·비밀번호 재설정 화면에 필요한 이메일 인증 API가 없다. 기존 이슈는 [`docs/issue/backend/2026-07-16.md`](2026-07-16.md)의 `3. 인증 화면 도입을 위한 API 계약 보완`에서 이관했다.

### 현재 상태

- `AuthController`는 `POST /api/auth/signup`, `POST /api/auth/login`, `POST /api/auth/refresh`, `POST /api/auth/logout`, `POST /api/auth/oauth/exchange`, `GET /api/auth/me`만 제공한다.
- `POST /api/auth/signup`은 중복 이메일에 `409 DUPLICATE_EMAIL`을 반환하고 선택 필드 `display_name`을 받는다. 닉네임 저장 자체는 구현 완료됐다.
- 인증번호 발급·저장·검증, 만료, 재요청 제한, verification token endpoint는 없다.
- 프론트엔드는 개발 환경에서 임시 인증번호 `9700`을 사용하며 production에서는 이 우회를 비활성화한다.
- 현재 프론트 작업 트리는 중복 이메일의 다음 화면 진입을 막기 위해 `인증 요청` 단계에서 `POST /api/auth/signup`을 먼저 호출한다. 사용자가 인증을 중단해도 계정이 생성되는 임시 우회이므로 실제 인증 API 연결 시 제거해야 한다.

### 필요한 API 계약

#### 1. 인증 요청

- `POST /api/auth/email-verifications`
- 입력: `email`, `purpose`(`signup` 또는 `password_reset`)
- 응답: `verification_id`, `expires_in`, `retry_after`
- `signup` 용도에서 기존 회원의 다음 화면 진입을 막으려면 `409 DUPLICATE_EMAIL`을 반환한다. 이메일 존재 여부 노출을 허용하는 정책이므로 rate limit과 감사 로그를 함께 적용한다.
- `password_reset` 용도는 계정 존재 여부와 관계없이 동일한 응답을 반환한다.
- 재요청 cooldown, 일일 횟수 제한, 새 인증번호 발급 시 기존 번호 폐기 규칙을 적용한다.

#### 2. 인증번호 검증

- `POST /api/auth/email-verifications/{verification_id}/confirm`
- 입력: `code`
- 응답: 1회 사용 가능한 `verification_token`, `expires_in`
- `INVALID_VERIFICATION_CODE`, `VERIFICATION_CODE_EXPIRED` 오류 code를 구분한다.

#### 3. 최종 회원가입

- `POST /api/auth/signup`에 `verification_token`을 필수로 추가한다.
- 입력: `email`, `password`, `display_name`, `verification_token`
- token의 email·purpose가 요청과 일치하는지 검증하고, 만료·1회 사용·가입 성공 시 폐기 규칙을 적용한다.
- 이메일 중복은 인증 요청과 최종 가입 모두에서 검증해 경쟁 조건을 막는다.

### 비밀번호 재설정 계약

- 인증 완료 후 회원가입 token과 구분되는 단기 `reset_token`을 발급한다.
- `reset_token`으로 비밀번호를 변경하는 endpoint와 성공 시 기존 refresh token 전체 폐기 여부를 확정한다.
- 가입되지 않은 이메일에도 동일한 응답을 반환해 계정 존재 여부를 보호한다.

### 추가 결정 사항

- 현재 별도 사용자 아이디·전화번호·복구 이메일이 없으므로 `아이디 찾기`를 제거하거나 검증 수단을 먼저 추가해야 한다.
- 현재 비밀번호 계약은 `8~72자`만 검증한다. `PASSWORD_TOO_SHORT`, `PASSWORD_POLICY_VIOLATION`, `INVALID_CREDENTIALS` 등 오류 code와 조합 규칙을 확정해야 한다.
- 로그인 실패 응답은 이메일 존재 여부와 비밀번호 오류를 구분하지 않는 현재 원칙을 유지한다.

### 완료 조건

- 회원가입 인증 요청에서 중복 이메일이 다음 단계로 진입하지 않는다.
- 인증번호 만료·재요청·오류 code·rate limit 정책이 백엔드 테스트로 검증된다.
- 유효한 `verification_token`이 없으면 회원가입이 실패하고, token은 성공 후 재사용할 수 없다.
- 프론트엔드의 임시 인증번호와 인증 전 회원가입 호출이 제거된다.
- 비밀번호 재설정은 계정 존재 여부를 노출하지 않고, 성공 후 token 폐기 정책을 따른다.

### 확인 위치

- 현재 Auth endpoint: `backend/src/main/java/fruition/user/controller/AuthController.java`의 `signup`, `login`, `refresh`, `logout`, `exchangeOAuthCode`, `me`
- 회원가입 요청: `backend/src/main/java/fruition/user/dto/SignupRequest.java`의 `email`, `password`, `display_name`
- 현재 API 계약: `docs/Fruition_MVP_API_Contract.md`의 `5. Auth API`, `POST /api/auth/signup`, `POST /api/auth/login`
- 프론트 임시 처리: `frontend/app/login/page.tsx`의 `handleSignupRequest`, 회원가입 인증 완료 effect
