# 2026-08-09 Backend 이슈

## 채팅 멀티턴 context 저장·전달 연결

### 배경

- LLM Pipeline의 Query와 Agent turn은 `recent_conversation_summary`, 최대 6개의
  `recent_messages`, `reference_context`를 대화 문맥으로 받을 수 있다.
- `recent_messages`가 6개에 도달하면 LLM Pipeline이 누적 요약을 갱신하고 응답의
  `updated_conversation_summary`로 반환한다.
- 해당 요청은 원문 6개를 그대로 사용하며, 반환된 요약은 다음 요청부터 사용한다.
- Spring Backend는 채팅 메시지와 `ChatSession.contextSummary`를 저장하지만, 현재 일반 Query에
  대화 문맥을 전달하거나 갱신된 요약을 저장하지 않는다.

### 필요한 작업

- `ChatMessageRepository`에서 세션의 아직 요약하지 않은 완료 메시지를 시간순으로 최대 6개 조회한다.
- `PipelineQueryRequester.QueryPayload`에 다음 필드를 추가한다.
  - `recent_conversation_summary`
  - `recent_messages`
  - `reference_context`
- Query 응답의 `updated_conversation_summary`가 있으면 `ChatSession.contextSummary`와
  `contextSummaryUpdatedAt`을 갱신한다.
- 동기 Query와 비동기 Query run이 동일한 context 조립·저장 경로를 사용하도록 한다.
- Agent turn에도 자동 문맥을 적용하려면 요청에 채팅 `sessionId`를 추가하고 소유권을 검증한 뒤 같은
  context를 `conversation_context`로 전달한다.
- 요약 갱신에 포함한 메시지의 경계를 보존해 같은 문답을 반복 요약하지 않는다.

### LLM Pipeline 계약 확인 위치

- `llmPipeline/app/modules/query/interfaces/http/schemas.py`
  - `QueryRequest.recent_messages`
  - `QueryResponse.updated_conversation_summary`
- `llmPipeline/app/modules/agent/interfaces/http/schemas.py`
  - `AgentConversationContextRequest.recent_messages`
  - `AgentTurnResponse.updated_conversation_summary`
- `llmPipeline/app/modules/query/application/conversation_context_resolver.py`
  - `RECENT_MESSAGE_LIMIT`
  - `update_conversation_summary()`
- 주요 API: `POST /query`, `POST /agent/turn`

### 테스트와 완료 조건

- [ ] 첫 질문은 기존 single-turn Query와 동일하게 동작한다.
- [ ] 후속 질문은 기존 누적 요약과 최근 원문 메시지를 함께 LLM Pipeline에 전달한다.
- [ ] 최근 메시지가 6개에 도달하면 응답의 갱신 요약을 세션에 저장한다.
- [ ] 저장 완료 후 같은 메시지를 다음 요약 입력에 다시 포함하지 않는다.
- [ ] 동기·비동기 Query가 동일한 멀티턴 결과를 반환한다.
- [ ] 다른 사용자나 Workspace의 세션 메시지는 context에 포함되지 않는다.

## Skill 작성·실행 계약을 기존 llmPipeline 흐름과 재정렬

### 배경과 원인

- Backend Skill 구현 전에 llmPipeline은 `POST /skills/author`에서 `preserve`, `enhance`,
  `regenerate` 작성과 LLM 의미·안전 검사를 제공하고 있었다.
- `docs/llm-wiki/flows/skill-authoring.md`의 `Skill의 name은 별도 표시 제목이 아니다` 섹션은
  Skill 이름을 slash command 식별자로 정의하고 `name`과 `slug`에 같은 값을 저장하도록 명시한다.
- Backend는 이후 `POST /skills/refine`과 별도 `command`, `name`을 도입했다. 이 계약은 기존
  `author` 기능과 중복되고 하나로 통합된 Skill 이름 의미를 다시 분리한다.
- `a596a2a`는 Spring이 접근 가능한 Skill 후보와 실행 version snapshot을 `/agent/turn`에 전달하도록
  구현했지만, `e7bd395`가 `Skill 라우팅을 LLM Pipeline으로 일원화`한다는 이유로 해당 전달 경로를
  제거했다. 현재 `PipelineAgentRequester`는 항상 `skill_mode="auto"`만 보내므로 Spring에 저장된
  Skill definition을 llmPipeline 실행 경로에 연결하지 않는다.
- 제거된 Spring snapshot 계약을 전제로 작성된 기존 AI 이슈가 남아 llmPipeline에 호출자 없는
  `refine`, `selected_skill`, `skill_candidates` 수신 구현을 다시 요구했다.

### 해결 방법

- Skill 구체화는 새 `/skills/refine`을 만들지 말고 기존 llmPipeline `POST /skills/author`를 재사용한다.
- API에서는 command 식별자 하나만 받고, 물리적으로 `skills.command`와 `skill_versions.name`을
  유지해야 한다면 같은 값을 저장한다. 별도 표시 이름 요구사항이 확정되기 전에는 두 의미를 나누지 않는다.
- 게시 전 검토는 기존 `author`의 `preserve` 경로에 있는 LLM 의미·안전 검사를 재사용한다. 같은 의미
  검사기를 별도로 구현하지 않는다.
- Agent 실행은 `e7bd395`에서 제거한 연결을 먼저 재검토한다. 자연어 의미 선택은 llmPipeline이
  담당하더라도, Backend는 접근 권한과 `auto_routing_enabled`를 적용한 후보 definition을 전달해야 한다.
  명시적 `/command`는 Backend가 권한과 command를 확인한 뒤 해당 version definition을 전달한다.
- Backend 송신 계약이 확정되기 전에는 llmPipeline에 새로운 snapshot 수신 API를 추가하지 않는다.
  계약 확정 후 필요한 AI 작업이 남으면 역할별 이슈로 분리해 상호 참조한다.

### 해결 효과

- Skill 작성 endpoint와 LLM 의미 검사 경로가 하나로 유지된다.
- command와 이름의 의미가 다시 갈라져 생성·수정·version 이력에서 값이 어긋나는 문제를 막는다.
- 실제 송신자 없는 llmPipeline API와 schema를 추가하지 않는다.
- Spring 권한 필터링과 llmPipeline 자연어 라우팅의 책임이 겹치지 않으면서 Spring 저장 Skill을 실제
  Agent 실행에 연결할 수 있다.
