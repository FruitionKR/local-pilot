# 2026-07-16 Backend 이슈

## 1. [완료] wiki_pages 잔재 unique constraint `uq_wiki_pages_type_slug`

- 과거 엔티티 잔재 constraint가 llmPipeline의 wiki page upsert를 막던 문제. **Flyway `V2__drop_leftover_wiki_pages_unique.sql`로 해결됨.**
- 원문/상세: `docs/backlog/issue-2026-07-16.md`. 변경 기록: `docs/changelog/backend.md` 2026-07-16 항목.

## 2. [팀원 조치 필요] Flyway + FK CASCADE 도입에 따른 로컬 DB 최초 1회 리셋

- 현재 DB `wiki_pages`에 unique constraint 2개 공존:
  - `uq_wiki_pages_workspace_type_slug (user_id, workspace_id, page_type, slug)` — 현행. `fruition/wiki/domain/WikiPage.java:9`에 정의됨.
  - `uq_wiki_pages_type_slug (page_type, slug)` — 과거 entity 정의의 잔재. 현재 코드 어디에도 정의 없음. JPA `ddl-auto=update`는 기존 constraint를 삭제하지 않아 DB에만 남아 있음.
- 영향: llmPipeline이 wiki page를 workspace 단위 constraint 대상으로 upsert(`ON CONFLICT (user_id, workspace_id, page_type, slug)`)하는데, 잔재 constraint가 전역 `(page_type, slug)` 중복을 먼저 막아 문서 재실행 run이 `duplicate key value violates unique constraint "uq_wiki_pages_type_slug"`로 실패. 상세 재현: `docs/issue/ai/2026-07-16.md` 이슈 2.
- 조치: dev DB에서 `ALTER TABLE wiki_pages DROP CONSTRAINT uq_wiki_pages_type_slug;` 실행 및 팀원 로컬 DB 반영 방법 공지 (초기화 또는 동일 DDL 실행). 마이그레이션 도구 도입 전까지는 수동 DDL로 처리.

## 2. llmPipeline 실행 요청의 `user_id`, `workspace_id` 제거 검토

- 현재 `DocumentProcessingRequester`는 `documents`에서 읽은 `user_id`, `workspace_id`를 `/pipeline/runs`와 `/chat-wiki/runs` 요청 body에 포함한다.
- 채팅 Wiki 계약의 실행 식별자는 `document_id`이며, llmPipeline도 Wiki 저장 범위를 해당 문서 row에서 직접 조회하도록 변경했다.
- AI 쪽은 기존 Backend와의 호환성을 위해 두 필드를 당분간 수신하지만 Wiki 저장 범위에는 사용하지 않는다.
- 조치: Backend 요청 DTO와 `DocumentProcessingRequester.request` 인자에서 `user_id`, `workspace_id`를 제거할지 협의한다. 제거 시 일반·채팅 요청 contract 테스트를 함께 갱신한다.
- 관련 위치: `docs/spec/chat-to-wiki-contract.md`의 `3. 채팅 입력 계약`, `llmPipeline/api.py`의 `PipelineRunIn`, `ChatWikiRunIn`, `_run_pipeline_request`.

## 3. 인증 화면 도입을 위한 API 계약 보완

Figma 인증 화면 15개 노드(`39:943` 외 로그인·회원가입·비밀번호 재설정 화면 및 컴포넌트 Variant)를 프론트엔드에 반영하면서 확인한 백엔드 미지원 범위다.

현재 인증 계약은 [`docs/Fruition_MVP_API_Contract.md`](../../Fruition_MVP_API_Contract.md)의 `5. Auth API`와 `POST /api/auth/signup`, `POST /api/auth/login`, `POST /api/auth/oauth/exchange`를 기준으로 한다.

### 3.1 이메일 인증번호 요청·검증·재요청

- Figma 화면에는 이메일 인증번호 요청, 5분 타이머, 인증번호 검증, 재요청 흐름이 있다.
- 현재 백엔드에는 인증번호 발급·저장·검증 endpoint와 만료·재요청 정책이 없다.
- 프론트엔드는 회원가입과 비밀번호 찾기에서 동일한 인증 요청 모듈을 사용한다. 요청 직후 버튼에 `5:00` 카운트다운을 표시하고, 만료 전에는 버튼을 비활성화하며, 만료 후 같은 버튼으로 재요청하도록 구성한다.
- 백엔드 연동 전까지 재요청 버튼은 로컬 타이머만 다시 시작한다.
- 로컬 개발 환경에서는 임시 인증번호 `9700`으로 다음 화면을 검증할 수 있다. production build에서는 이 우회를 비활성화한다.
- 필요한 계약:
  - 인증번호 요청 endpoint
  - 인증번호 검증 endpoint와 가입에 사용할 일회성 verification token
  - 응답의 `expires_in` 또는 만료 시각과 서버 기준 잔여 시간
  - 재요청 cooldown, 일일 횟수 제한, 기존 인증번호 폐기 규칙
  - 이메일 존재 여부를 노출하지 않는 공통 응답과 rate limit

### 3.2 회원가입 요청의 닉네임·이메일 인증 연계

- Figma 회원가입 입력은 `nickname`, `email`, `password`로 구성된다.
- 현재 `POST /api/auth/signup`은 `email`, `password`만 받고 `display_name`을 이메일 앞 3글자로 자동 생성한다.
- 이메일 인증 도입 시 `POST /api/auth/signup`에 닉네임과 검증 완료 증명을 전달하는 계약이 필요하다.
- 결정 필요:
  - 요청 필드명 `nickname`과 응답 필드명 `display_name`의 통일 여부
  - 닉네임 길이·허용 문자·중복 허용 정책
  - verification token의 만료·1회 사용·가입 성공 시 폐기 규칙

### 3.3 비밀번호 찾기·재설정

- Figma에는 이메일 인증, 인증번호 검증, 새 비밀번호와 비밀번호 재확인 화면이 있다.
- 현재 비밀번호 재설정 endpoint가 없다.
- 필요한 계약:
  - 비밀번호 재설정 인증 요청 endpoint
  - 인증번호 검증 후 발급되는 단기 reset token
  - reset token으로 비밀번호를 변경하는 endpoint
  - 성공 시 기존 refresh token 전체 폐기 여부
  - 가입되지 않은 이메일에도 동일한 응답을 반환하는 계정 존재 여부 보호 정책

### 3.4 아이디 찾기

- 현재 `users.email`이 계정 식별자이며 전화번호, 복구 이메일, 별도 사용자 아이디가 없다.
- `display_name`은 고유하지 않고 이메일에서 자동 생성되므로 이메일 역조회 수단으로 사용할 수 없다.
- OAuth 사용자는 동일 provider로 다시 인증하면 `provider_user_id → user_id → email` 조회가 가능하지만 일반 이메일 가입자는 역조회가 불가능하다.
- 결정 필요:
  - 로그인 화면의 `아이디 찾기`를 제거할지
  - 기능을 유지한다면 검증된 전화번호·복구 이메일·외부 본인인증 중 어떤 식별 수단을 추가할지

### 3.5 비밀번호 정책과 오류 code

- Figma 오류 Variant에는 8자 미만, 영문·숫자·특수문자 조합 실패, 비밀번호 불일치가 있다.
- 현재 API 계약은 비밀번호 `8~72자`만 명시한다.
- 프론트 문구를 안정적으로 매핑할 수 있도록 다음 오류 code와 검증 기준을 확정해야 한다.
  - `PASSWORD_TOO_SHORT`
  - `PASSWORD_POLICY_VIOLATION`
  - `DUPLICATE_EMAIL`
  - `INVALID_VERIFICATION_CODE`
  - `VERIFICATION_CODE_EXPIRED`
  - `INVALID_CREDENTIALS`
- 로그인 실패 응답은 이메일 존재 여부와 비밀번호 오류를 구분하지 않는 현재 원칙을 유지한다.

### 3.6 프론트엔드 임시 처리

- `POST /api/auth/login`은 기존대로 연결한다.
- 이메일 인증은 로컬 개발 환경의 임시 인증번호 `9700`으로만 통과시킨다.
- 회원가입은 임시 인증 통과 후 기존 `POST /api/auth/signup`과 `POST /api/auth/login`을 순서대로 호출한다.
- 비밀번호 재설정은 실제 변경 endpoint가 없어 Figma 화면 전환과 입력 상태만 제공한다.
- 백엔드 계약 확정 후 임시 화면 전환을 실제 endpoint 호출로 교체한다.
