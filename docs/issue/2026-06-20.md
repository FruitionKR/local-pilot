# 2026-06-20 이슈

## 미결 이슈

### 1. 프론트엔드를 SSE 기반 진행상황 표시로 전환

**현황**

Spring 백엔드에 Query run/SSE 중계 구조(`POST /api/query/runs`, `GET /api/query/runs/{requestId}/events`, `POST /api/query/runs/{requestId}/events/callback`, `GET /api/query/runs/{requestId}`)를 구현했다.
같은 날 `dev`에 병합된 pipeline 커밋(`16118e1 feat: 쿼리 이벤트 콜백 계약 추가`)이 `request_id`/`log_callback_url`을 받아 요청별로 동적 callback publisher를 생성하도록 이미 구현해뒀다 — 즉 pipeline 쪽 선행 작업은 끝난 상태다.

프론트엔드는 현재 `POST /api/query`(동기)만 호출하고, `StatusList`/`agentData.ts`는 실제 event가 아니라 정적인 3단계(`질문 분석` → `관련 Wiki page 검색` → `근거 기반 답변 작성`)를 보여준다.
`POST /api/query`는 이번 작업에서 변경하지 않고 그대로 유지했으므로, 프론트엔드는 지금 당장 아무것도 바꾸지 않아도 기존처럼 동작한다. 전환은 blocking이 아니다.

**필요한 작업**

- `POST /api/query/runs` 호출 → 응답의 `request_id`로 `GET /api/query/runs/{requestId}/events` SSE 구독으로 전환
- `StatusList`/`agentData.ts`의 정적 3단계 표시를 실제 `stage`/`message` 기반으로 교체
- SSE 실패 시 `GET /api/query/runs/{requestId}` polling으로 fallback
- 최종 답변은 SSE `query.completed`가 아니라 기존처럼 `/api/chat/messages` 갱신 결과로 표시 (중복 방지)
- `retrieval_scored`의 `top_sources`/`top_concepts`를 후보 근거/검색 결과 UI에 연결할 수 있는지 검토
- `web_search_started` 계열 event는 내부 Wiki 경로가 아니라 웹 검색 fallback 경로임을 UI에서 구분

**참고 문서**

- 설계 전체: `docs/spec/backend-query-events-api.md` ("후속 작업 (이슈 문서로 이동) > frontend" 절, SSE 이벤트 포맷은 "API > GET /api/query/runs/{requestId}/events" 절)
- 프론트 진행 상태 표시: `frontend/app/_components/agent-panel/StatusList.tsx`, `frontend/app/_components/agent-panel/agentData.ts`
- 프론트 채팅 panel: `frontend/app/_components/agent-panel/AgentPanel.tsx`

**검증 기준**

- Query 실행 중 Agent 패널에 실제 backend/pipeline event message가 순서대로 표시된다
- 내부 Wiki 경로와 web search fallback 경로가 UI에서 구분된다
- 최종 답변과 진행 event가 중복 메시지로 표시되지 않는다
- SSE 연결이 실패해도 기존 최종 응답 조회 흐름은 깨지지 않는다

## 참고: 백엔드 작업 중 확인된 사항

이번 백엔드 작업 도중 `dev`를 pull하면서, pipeline의 `request_id`/`log_callback_url` 지원(원래 이슈로 남기려던 항목)이 이미 다른 커밋(`16118e1`)으로 구현되어 있는 것을 확인했다. 별도 미결 이슈로 등록하지 않고 여기 기록만 남긴다.

- pipeline이 보내는 callback payload에는 `request_id`, `event_type`, `stage`, `message`, `sequence`, `timestamp`, `data`가 포함된다 (`llmPipeline/app/modules/query/infrastructure/query_event_publisher.py`).
- 다만 Spring `QueryEventBroker`는 pipeline의 `sequence`/`timestamp`를 사용하지 않고 자체적으로 다시 부여한다 — `query.completed`/`query.failed`(pipeline이 보내지 않는 합성 event)까지 하나의 순번으로 묶기 위함. `PipelineEventCallbackRequest`(`backend/src/main/java/fruition/query/dto/PipelineEventCallbackRequest.java`)에 두 필드를 바인딩은 해두되 미사용 처리했다.
- 아직 end-to-end로 실제 서버를 띄워 pipeline → callback → SSE 흐름을 수동 검증하지는 못했다 (이 환경에 Docker가 없어 `BackendApplicationTests.contextLoads()`도 실패하는 상태). `docker-compose`로 backend+pipeline을 같이 띄울 수 있는 환경에서 `docs/spec/backend-query-events-api.md`의 "검증 기준" 절 기준으로 한 번 수동 확인이 필요하다.
- `CALLBACK_BASE_URL` 기본값을 처음에 `http://backend:8080`으로 잘못 넣었다가, `scripts/dev-up.sh`/`docs/local-runbook.md`를 보고 backend가 docker-compose 서비스가 아니라 호스트에서 `./gradlew bootRun`으로 직접 뜬다는 걸 확인하고 `http://host.docker.internal:8080`으로 고쳤다 (`infra/.env.example`, `application.properties`, `infra/docker-compose.pipeline.yml`의 `extra_hosts` 추가). 실제 환경에서 한 번 더 확인이 필요하다.
