# 2026-06-27 이슈

## 채팅 Wiki observation 기능 backend/frontend 연동 계약 정리

### 배경

`llmPipeline`에 채팅 원문을 Wiki source/concept 구조로 변환하고, observation 중복/누락을 평가해 보정하는 실험 기능이 추가됐다.
또한 Query API는 멀티턴 질의를 위해 `recent_conversation_summary`, `reference_context`를 선택 입력으로 받을 수 있다.

현재 남은 문제는 pipeline 내부 기능이 backend/frontend 제품 흐름에서 어떻게 사용될지 계약이 아직 명확하지 않다는 점이다.

### 현재 확인된 상태

- `llmPipeline POST /query`는 `question` 외에 `recent_conversation_summary`, `reference_context`를 받을 수 있다.
- Spring backend의 기존 query 중계 문서는 아직 `question`만 전달하는 형태로 설명되어 있었다.
- 프론트엔드는 `llmPipeline`을 직접 호출하지 않고 Spring `POST /api/query`만 호출하는 구조를 유지한다.
- 채팅 Wiki page 생성 evaluator/repair loop는 실험 경로에서 검증됐지만, 실제 `POST /pipeline/runs` API에서 어떤 설정으로 켤지는 추가 확인이 필요하다.

### 결정 방향

1차 구현에서는 프론트엔드가 LLM용 context 구조를 직접 만들지 않는다.
Spring backend가 저장된 채팅 이력과 최근 질의 응답을 기준으로 멀티턴 context를 구성하고, `llmPipeline POST /query`에 전달한다.

프론트엔드는 기존 `POST /api/query` 호출 구조를 유지한다.
나중에 사용자가 특정 page/concept를 UI에서 명시 선택하는 기능이 생기면, 그때 Spring API에 별도 입력 필드를 추가한다.

### backend 검토 항목

- `PipelineQueryRequester` 요청 DTO에 `recent_conversation_summary`, `reference_context`를 추가한다.
- `QueryService`에서 최근 `chat_messages`를 조회해 context를 만들지, 별도 context compiler를 둘지 결정한다.
- context 생성 실패 시 기존처럼 `question`만 전달하는 fallback을 유지한다.
- 답변 저장 시 사용된 context를 함께 저장할지 결정한다.
- 멀티턴 context가 source/concept/evidence retrieval 점수에 어떤 영향을 줬는지 로그 또는 debug artifact로 확인할 수 있게 한다.

### frontend 검토 항목

- 1차 구현에서는 프론트엔드 변경 없이 유지한다.
- 프론트가 직접 보내야 할 값이 있다면 `question` 외에 UI 선택 상태만 넘기고, LLM용 `reference_context` 변환은 backend가 맡는다.
- 답변에 포함되는 source/concept/evidence 링크 표시 방식은 기존 응답 계약을 따른다.

### llmPipeline API 검토 항목

- `POST /query` 요청 스펙에 `recent_conversation_summary`, `reference_context` 예시를 유지한다.
- `POST /pipeline/runs`에서 채팅 Wiki page 생성 평가 루프를 켤 수 있는지 확인한다.
- 필요한 경우 아래 설정을 API 입력으로 추가한다.
  - `wiki_evaluation_loop`
  - `max_eval_attempts`
  - `wiki_evaluator_system_prompt`
  - `json_mode`
- evaluation/repair 결과를 manifest 또는 debug artifact에 저장해 재현 가능하게 만든다.
