# 2026-07-02 이슈

## Wiki 페이지 workspace 격리 미구현

### 배경

`feature/user-workspace-auth` 브랜치에서 User/Workspace/Auth 기반을 구현한 뒤, 기존 리소스(documents, wiki_pages)에 `workspace_id`/`user_id`를 연동하는 작업을 진행했다. Document는 Spring Boot가 CRUD를 전담하므로 문제없이 연동했지만, Wiki 페이지는 조사 결과 예상보다 훨씬 큰 범위의 작업으로 확인되어 이번 단계에서는 보류했다.

### 관련 문서

- `docs/spec/fruition-backend-mvp-erd.md` — `wiki_pages` 테이블 정의, 소유 주체를 "Spring Boot"로 표기
- `docs/backend-architecture-decision-spring-fastapi.md` — Spring Boot와 llmPipeline 역할 분리 결정

### 현재 상태

`wiki_pages` 테이블에 실제로 새 행을 만드는 주체는 Spring Boot가 아니라 **llmPipeline(Python)** 이다.

- `WikiService`(Spring)는 `wikiPageRepository.findAll/findById/findByPageTypeAndSlug/findAllById`만 호출한다. 기존 행을 읽고 rename 등으로 수정할 뿐, `new WikiPage(...)` 생성 후 저장하는 코드가 없다.
- 실제 INSERT는 `llmPipeline/app/modules/wiki_ingestion/infrastructure/postgres_wiki_ingestion_repository.py`의 `_upsert_wiki_page()`(raw SQL, psycopg)가 담당한다. 이 파일이 `CREATE TABLE IF NOT EXISTS wiki_pages (...)` DDL도 직접 소유하고 있어, Spring 쪽 JPA 엔티티/마이그레이션과 별개로 스키마가 관리된다.
- `_upsert_wiki_page()`와 이를 호출하는 `_persist_wiki_outputs()`에는 `workspace_id`/`user_id` 개념이 전혀 없다.

### 추가로 발견한 문제: concept 페이지 ID 전역 충돌

concept 타입 Wiki 페이지 ID(`concept:{slug}`)가 **시스템 전체에서 전역으로 유니크**하게 upsert(`ON CONFLICT (id) DO UPDATE`)되고 있다. 서로 다른 workspace의 사용자가 각자 업로드한 문서에 동일한 개념(예: "머신러닝")이 등장하면, 현재 구조상 **하나의 concept 페이지로 병합**된다.

이는 컬럼 하나 추가로 해결되지 않는다. concept 페이지 생성/조회 로직 자체를 workspace 단위로 재설계해야 한다 (예: ID를 `concept:{workspace_id}:{slug}`로 바꾸거나, 별도 조인 테이블로 workspace별 concept 인스턴스를 분리하는 방식 등).

### 필요한 작업 (다음 단계에서 진행)

1. `llmPipeline`의 `wiki_pages` DDL/`_upsert_wiki_page()`/`_persist_wiki_outputs()` 호출 체인에 `workspace_id`/`user_id` 추가
2. concept 페이지 ID 전역 충돌 문제 해결 방식 결정 및 구현 (workspace 단위 격리)
3. Java 쪽 `WikiPage` 엔티티/마이그레이션에 컬럼 추가, `WikiService`/`WikiController`를 workspace 인증 기준으로 전환
4. `wiki_embedding_units`, `wiki_page_embeddings` 등 wiki 관련 나머지 테이블도 동일한 workspace 격리 적용 여부 검토
