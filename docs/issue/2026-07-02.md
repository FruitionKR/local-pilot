# 2026-07-02 이슈 정리

## LLM Wiki cluster promotion/lint 연동 후속 작업

### 배경

이번 변경으로 llmPipeline의 wiki ingest/lint 흐름이 바뀌었다.

기존에는 section/mention 후보가 source/concept page 주변에만 남고, lint가 실질적인 유지보수 작업을 하지 못했다. 변경 후에는 section/mention/evidence 후보가 `clusters/active.md`에 누적되고, lint가 pending 상태를 읽어 promotion, archive 이동, relation materialization을 수행한다.

핵심 정책:

- section/mention/evidence 후보는 같은 ingest pass에서 즉시 core로 승격하지 않는다.
- 새 cluster는 promotion candidate가 될 수 없다.
- 기존 active cluster에 claim/source가 누적되고 LLM이 재사용 가능한 core로 판단한 경우에만 `Promotion.status: candidate`가 생긴다.
- lint dry-run은 proposal만 보여준다.
- lint 실행은 promotion concept page 생성, active cluster 제거, archive 이동, materializable relation link 생성을 수행한다.

### 현재 llmPipeline 변경 사항

### Backend 후속 작업

#### B1. wiki_pages schema를 llmPipeline과 맞춘다

현재 Spring domain은 `wiki_pages` unique key를 `(page_type, slug)`로 본다.

```java
@UniqueConstraint(
    name = "uq_wiki_pages_type_slug",
    columnNames = {"page_type", "slug"}
)
```

llmPipeline은 workspace/user 범위에서 slug uniqueness를 사용한다.

필요 변경:

- `wiki_pages`에 `user_id`, `workspace_id` 컬럼을 domain/migration에 반영한다.
- unique key를 `(user_id, workspace_id, page_type, slug)`로 맞춘다.
- `WikiPageRepository.findByPageTypeAndSlug(...)`는 workspace/user scope를 받도록 바꾼다.
- rename slug conflict 검사도 workspace/user scope 안에서만 수행한다.

검증:

- 같은 slug의 concept page가 서로 다른 workspace에 공존할 수 있다.
- 같은 workspace/user 안에서는 같은 page_type/slug 중복이 막힌다.
- `docs/spec/backend-mvp-erd.md`와 `docs/Fruition_MVP_API_Contract.md`의 `wiki_pages.id` 설명에서 `source:xxx`, `concept:xxx` 고정 prefix 전제를 제거한다.
- API 계약 문서에 `user_id`, `workspace_id`, scoped unique key를 반영한다.

#### B2. source page id를 `source:{documentId}`로 가정하는 코드를 제거한다

이번 llmPipeline은 wiki page id를 UUID 형태로 만든다.

```text
wiki_page_eade5a66-f23f-4da4-a3da-5fceb25b254e
```

현재 `DocumentService.delete()`는 source page id를 다음처럼 가정한다.

```java
wikiPageRepository.findById("source:" + documentId)
```

필요 변경:

- source page 삭제는 `document_wiki_links`에서 `document_id + relation_type=source_of`로 연결된 wiki page를 찾아 삭제한다.
- source page id 문자열 구조에 의존하지 않는다.
- concept page는 공유 가능하므로 문서 삭제만으로 삭제하지 않는다.

검증:

- UUID source page id에서도 문서 삭제 시 source page와 관련 link가 삭제된다.
- concept page는 삭제되지 않는다.

#### B3. processing request에 user_id/workspace_id를 포함한다

현재 `DocumentProcessingRequester`는 `/pipeline/runs` 요청 body를 JSON 문자열로 직접 조립한다.

```java
String body = "{\"document_id\":\"" + documentId + "\""
        + (callbackUrl != null ? ",\"log_callback_url\":\"" + callbackUrl + "\"" : "")
        + "}";
```

이 방식은 새 필드 추가와 escaping에 취약하므로 DTO/record 기반 request body로 바꾼다.

필요 변경:

- `PipelineRunRequest` record를 추가한다.
- request body에 `user_id`, `workspace_id`를 추가한다.
- 가능하면 `source_page_mode`, `concept_page_mode`, `provider`도 backend 설정값으로 명시한다.
- 임시 기본값을 쓰더라도 `DocumentProcessingRequester` 내부에 하드코딩하지 말고 config 또는 workspace resolver를 둔다.
- callback 저장 시 manifest의 `maintenance_summary`를 문서 상태 또는 별도 endpoint에서 조회 가능하게 할지 결정한다.

검증:

- pipeline run 생성 후 `wiki_pages.user_id/workspace_id`가 backend 기대 scope와 일치한다.
- `GET /api/wiki/graph`에서 해당 workspace의 page만 반환한다.

#### B4. lint proxy endpoint를 추가한다

Frontend가 FastAPI를 직접 호출하지 않도록 Spring backend가 proxy endpoint를 제공한다.

권장 endpoint:

```text
POST /api/wiki/maintenance/lint
```

역할:

- `POST dry_run=true`: proposal 조회
- `POST dry_run=false`: promotion/relation materialization 실행

Spring DTO:

- `WikiMaintenanceLintRequest`
- `WikiMaintenanceLintResponse`
- `WikiPromotionCandidate`
- `WikiRelationCandidate`
- `WikiMaterializedPromotion`
- `WikiMergedPromotion`
- `WikiMaterializedRelation`

검증:

- dry-run 호출은 DB graph를 바꾸지 않는다.
- 실행 호출 후 `GET /api/wiki/graph`의 concept node/link가 증가한다.
- FastAPI 장애 시 frontend에 표시 가능한 에러 메시지를 반환한다.
- 실제 실행 후 backend는 `GET /api/wiki/graph`를 재조회했을 때 새 concept node와 edge를 반환한다.

#### B5. graph API가 새 relation type을 그대로 노출하는지 확인한다

이번 lint는 다음 relation type을 만들 수 있다.

```text
part_of
child_of
uses_or_depends_on
contrasts_with
supports_or_enables
```

`related_evidence`는 기본 graph edge로 materialize하지 않는다.

필요 변경:

- `WikiGraphEdge.link_type`을 enum으로 제한하고 있다면 위 값을 허용한다.
- 현재처럼 string이면 그대로 통과해도 된다.
- frontend가 link type별 스타일/라벨을 만들 수 있도록 `label`, `confidence`를 유지한다.

검증:

- `uses_or_depends_on` link가 `/api/wiki/graph`에 노출된다.
- graph edge 클릭 또는 tooltip에서 label을 볼 수 있다.

#### B6. source/concept markdown URI scope를 확인한다

llmPipeline은 MinIO object를 다음 prefix에 저장한다.

```text
wiki/{user_id}/{workspace_id}/sources/{slug}.md
wiki/{user_id}/{workspace_id}/concepts/{slug}.md
wiki/{user_id}/{workspace_id}/clusters/active.md
wiki/{user_id}/{workspace_id}/clusters/archived.md
wiki/{user_id}/{workspace_id}/logs/{yyyy-mm-dd}.md
```

필요 변경:

- `WikiService.readMarkdown()`은 이미 `s3://bucket/...`와 object key를 처리하므로 대체로 유지 가능하다.
- 단, graph/detail API가 workspace/user scope 없이 `findAll()`을 쓰면 다른 workspace page가 섞일 수 있다.

검증:

- `GET /api/wiki/pages/{wiki_page_id}`가 `s3://bucket/wiki/{user}/{workspace}/...` markdown을 읽는다.
- graph/detail이 현재 workspace 범위만 반환한다.

#### B7. WikiGraphNode.source_document 계약을 유지한다

Spring `WikiGraphNode`는 source page에 대해 `source_document`를 내려줄 수 있다.

```java
@JsonProperty("source_document") SourceDocRef sourceDocument
```

Frontend가 UUID source page id를 쓰려면 이 값이 중요하다.

필요 변경:

- `GET /api/wiki/graph`에서 source node의 `source_document.id`가 채워지는지 테스트한다.
- `document_wiki_links`의 `source_of` relation이 UUID source page와 연결되어 있어야 한다.
- source page가 없는 문서는 raw document node만 보여줄 수 있도록 frontend fallback을 허용한다.

검증:

- `wiki_page_xxx` source page id와 document id를 `source_document.id`로 매핑할 수 있다.
- `source:` prefix가 없어도 raw document node에서 source wiki node로 edge를 만들 수 있다.

#### F5. UUID wiki page id를 전제로 한다

Frontend가 page id에서 `source:` 또는 `concept:` prefix를 파싱하면 안 된다.

현재 실제로 prefix를 가정하는 위치:

```text
frontend/app/_lib/graph.ts
- NODE_PREFIX.source = "source:"
- nodeIdToPageType()
- makeSourceId()
- buildGraphFromBackend(): node.id.startsWith("source:")
- rawSourceLinks target: source:${document.id}

frontend/app/_hooks/useTreeSelection.ts
- nodeIdToPageType(nodeId)로 pageType 판단
- openSourceBlockPreview()가 source:${documentId}에 focus

frontend/app/_components/agent-panel/AgentBody.tsx
- source_document_id -> makeSourceId(source_document_id)
```

필요 변경:

- page type은 `node.page_type`을 사용한다.
- source/concept 구분은 id가 아니라 `page_type`으로 한다.
- click/detail fetch는 opaque id 그대로 `GET /api/wiki/pages/{wiki_page_id}`에 넘긴다.
- `WikiGraphNodeResponse` 타입에 `source_document?: { id: string; filename?: string | null }`를 추가한다.
- `buildGraphFromBackend()`는 backend source node를 `source_document.id`로 찾아 raw document node와 연결한다.
- source wiki page가 아직 없을 때만 fallback node id로 `source:${document.id}` 같은 client-only id를 만들 수 있다. 이 fallback id는 backend wiki page id로 사용하면 안 된다.
- `nodeIdToPageType()`는 backend graph node map을 모르면 UUID page type을 판정할 수 없다. selection 로직은 graph node의 `kind` 또는 `page_type`을 함께 넘기는 구조로 바꾼다.
- chat related page는 `wiki_page_id`가 opaque UUID일 수 있으므로 graph node lookup으로 page type/title을 보강한다.

검증:

- `wiki_page_xxx` 형태 id인 source/concept page 모두 tree와 detail에서 열린다.
- raw document node 클릭은 document block/source preview로 열리고, source wiki node 클릭은 wiki page detail로 열린다.
- query answer의 related page card가 UUID wiki page id를 그대로 열 수 있다.
