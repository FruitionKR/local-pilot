## 미결 이슈

### 1. chat_message_references 테이블 설계: evidence_snippets만 저장, related_pages 처리 방식 미확정

**현황**

현재 `chat_message_references` 테이블은 Query API 응답의 `evidence_snippets`(답변 근거 문장) 기반으로만 구성되어 있다.
Query API 응답에는 `related_pages`(탐색된 Wiki page 목록, `relevance_score`/`role`/`depth` 포함)도 존재하는데, 이것을 `chat_message_references`에 함께 저장할지, 별도 테이블로 분리할지 결정되지 않았다.

**판단이 필요한 질문**

- `related_pages`를 `chat_message_references`에 `reference_type = "wiki_page"`로 함께 저장할 것인가, 아니면 별도 테이블(`chat_message_related_pages` 등)로 분리할 것인가?
- **같은 테이블에 두면**: `reference_type`으로 구분하되 evidence 전용 필드(`paragraph_index`, `sentence_index`, `quote`)와 related_page 전용 필드(`depth`)가 혼재해 nullable 컬럼이 늘어난다.
- **분리하면**: 테이블은 두 개가 되지만 각 테이블의 스키마가 명확해지고, 조회 시 JOIN 대상이 늘어난다.
- 현재 API 계약(`§ 8.1`)의 `references[]`는 `reference_type`으로 두 종류를 구분하는 단일 배열 구조다. DB 분리 여부와 API 응답 통합 여부를 함께 결정해야 한다.

**현재 구현 상태**

- `chat/domain/ChatMessageReference.java` — evidence snippet 기반 필드 구조 (현재 related_pages 필드 없음)
- `chat/repository/ChatMessageReferenceRepository.java` — 메시지 ID 기준 일괄 조회
- `ChatController` — `ChatMessageReferenceRepository` 조회 결과를 `ChatMessageReference` DTO로 반환
- Query API 응답의 `related_pages`는 현재 `chat_message_references`에 저장되지 않음

**참고 위치**

- API 계약 references 구조: `docs/Fruition_MVP_API_Contract.md` § 8.1
- Query 응답 related_pages 구조: `docs/Fruition_MVP_API_Contract.md` § 7.1
- ChatMessageReference 엔티티: `backend/src/main/java/fruition/chat/domain/ChatMessageReference.java`
- ChatMessageReference DTO: `backend/src/main/java/fruition/chat/dto/ChatMessageReference.java`
