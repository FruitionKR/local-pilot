## Skill 관리와 AgentRun 계획·승인 UI 구현

### 배경과 현재 상태

- 상세 설계는 `docs/spec/sdd/agent-skills-and-folder-organization.md`에 정의되어 있다.
- 구현 범위는 `docs/spec/sdd/tasks/agent-skills-and-folder-organization-tasks.md`의
  **TASK-012 Frontend Skill 관리**, **TASK-013 Frontend AgentRun 계획·승인 UI**를 기준으로 한다.
- 현재 Schema 관리 화면은 Wiki Schema 일부를 “스킬”로 표시하고 local mock API를 사용한다.
  Wiki Schema는 문서 구조/검증 규칙이고, 새 Agent Skill은 자연어 작업 절차·capability·허용 Tool을
  정의하므로 UI와 상태 모델을 분리해야 한다.
- 현재 `AgentPanel`은 Markdown 편집 context가 있을 때만 `/agent/turn`을 사용하며 문서가 없는
  일반 요청은 Query 흐름을 사용한다. 폴더 정리와 slash Skill 호출은 문서 선택 여부와 무관하게
  Agent endpoint로 보낼 수 있어야 한다.
- Backend 공개 API와 권한·Tool Gateway 구현 범위는
  `docs/issue/backend/2026-08-03.md`의
  **Agent Skill·폴더 정리 기능의 Spring 경계 구현**을 참조한다.
- Frontend는 Spring Backend만 호출해야 하며 llmPipeline URL, 내부 service token, 내부 Tool
  endpoint를 알거나 직접 호출하면 안 된다.

### UX 원칙

- 기존 Query, 문서 생성, Markdown 편집 흐름을 유지한다.
- 자연어 요청은 기본적으로 `skill_mode=auto`, 명시적 slash 호출은 `explicit`, 사용자가 Skill을
  사용하지 않겠다고 선택하면 `off`로 전송한다.
- 여러 Skill을 동시에 enabled할 수 있다. 하나의 전역 active Skill을 선택하는 UI를 만들지 않는다.
- 자동 선택 후보가 모호하면 임의로 하나를 실행하지 않는다. 후보와 설명을 보여주고 사용자가
  Skill 하나 또는 “Skill 없이 진행”을 선택하도록 한다.
- Agent는 사용자가 직접 할 수 있는 작업을 자동화할 뿐이다. UI에서 관리자 권한 상승, DB 작업,
  삭제, 범용 명령 실행이 가능한 것처럼 표시하지 않는다.
- 실제 변경은 계획 승인 전까지 발생하지 않으며, Frontend가 승인된 것처럼 낙관적으로 mutation
  결과를 만들거나 로컬 상태만 변경하지 않는다.

### 작업 1. Wiki Schema와 Agent Skill 화면·모델 분리

- 기존 `frontend/src/entities/schema/`와 `frontend/src/features/schema-manage/`의 Wiki Schema
  기능과 용어를 보존한다.
- “스킬”로 잘못 표시된 Wiki Schema 문구는 “Wiki Schema” 또는 제품에서 확정한 Schema 명칭으로
  정리하고, Agent Skill 전용 entity·API·feature를 별도로 추가한다.
- Agent Skill form에는 다음 필드를 제공한다.

  - scope: `personal` 또는 `team`
  - name, slug, description
  - instructions
  - capabilities
  - capability에서 허용된 범위 안의 `allowed_tools`

- Wiki Schema의 `active` 상태를 Skill에 재사용하지 않는다. Skill은 여러 개를 동시에 enabled할 수
  있고, 요청마다 selector가 하나를 선택한다.
- 개인 Skill과 팀 Skill을 목록에서 명확히 구분하고 동일한 이름이 있으면 scope와 owner/workspace를
  함께 표시한다.
- Backend가 반환한 현재 사용자 권한에 따라 생성·수정·게시·활성화 control을 표시한다.
  숨김만으로 보안을 구현하지 말고 `403` 응답도 정상 처리한다.
- 현재 Backend 역할이 `OWNER/MEMBER`뿐이라면 팀 Skill 관리 버튼은 확정된 Backend 정책과
  동일하게 제한한다. Frontend에서 존재하지 않는 `EDITOR` 역할을 임의로 가정하지 않는다.

### 작업 2. Skill 작성·검증·게시·활성화 흐름

- Spring Backend의 다음 API만 호출하는 Skill client를 추가한다.

```text
POST  /api/workspaces/{workspace_id}/skills/preview
POST  /api/workspaces/{workspace_id}/skills
GET   /api/workspaces/{workspace_id}/skills
GET   /api/workspaces/{workspace_id}/skills/{skill_id}
PATCH /api/workspaces/{workspace_id}/skills/{skill_id}
POST  /api/workspaces/{workspace_id}/skills/{skill_id}/publish
POST  /api/workspaces/{workspace_id}/skills/{skill_id}/enable
POST  /api/workspaces/{workspace_id}/skills/{skill_id}/disable
```

- 작성 중 `preview`로 문법, capability, allowed Tool 정책을 확인하되 preview 성공을 저장·게시·
  활성화 성공처럼 표시하지 않는다.
- draft 저장, 새 version 게시, enable, disable을 서로 다른 사용자 행동과 상태로 표현한다.
- published version은 UI에서 직접 덮어쓰지 않고 수정 시 새 draft/version을 만드는 Backend 계약을
  따른다.
- 목록 갱신 중에도 직전 데이터를 유지할지 skeleton을 표시할지 기존 UI 패턴에 맞추되, enable/
  disable 요청의 실패를 성공 상태로 낙관 확정하지 않는다.
- 접근 권한 상실, 이미 변경된 version, 존재하지 않는 Skill, feature disabled 오류에 각각 이해할 수
  있는 안내와 재시도 동작을 제공한다.
- 기존 Schema local mock을 Agent Skill 저장소로 확장하지 않는다. Skill 데이터는 Backend 응답을
  source of truth로 사용한다.

### 작업 3. 자연어·slash command Skill 호출

- Agent composer에 `/` 입력 시 현재 workspace와 사용자에게 접근 가능한 enabled Skill을 검색하는
  autocomplete를 제공한다.
- 항목에는 Skill name, 짧은 description, personal/team scope를 표시한다. 같은 name은 scope와
  owner/workspace 정보로 구분한다.
- 사용자가 slash 항목을 선택하면 정확한 `skill_id`와 `skill_mode=explicit`를 전송한다. 화면에
  보이는 name을 다시 문자열 검색해 실행 대상을 정하지 않는다.
- 일반 자연어는 `skill_mode=auto`로 전송하고 “Skill 없이 진행”은 같은 원래 요청을
  `skill_mode=off`로 다시 전송한다.
- 삭제되었거나 disable된 Skill을 최근 기록·캐시에서 선택한 경우 실행하지 않고 목록을 갱신한 뒤
  사용자에게 상태를 안내한다.
- 폴더 정리 또는 명시적 Skill 요청은 현재 문서가 없어도
  `POST /api/workspaces/{workspace_id}/agent/turn`으로 전송한다.
- 기존 질의가 불필요하게 AgentRun으로 바뀌지 않도록 Query와 Agent route 선택 조건을 명시적인
  함수/테스트로 고정한다.

### 작업 4. 모호한 Skill 후보 선택 카드

- Backend가 하나를 명확히 선택할 수 없는 후보를 반환하면 채팅에 선택 카드를 표시한다.
- 각 후보의 name, scope, description과 선택 결과를 보여준다.
- 사용자는 다음 중 하나를 선택할 수 있다.

  - 특정 Skill을 선택해 원래 요청을 `skill_mode=explicit`로 다시 제출
  - “Skill 없이 진행”을 선택해 원래 요청을 `skill_mode=off`로 다시 제출
  - 취소하고 아무 작업도 실행하지 않음

- 후보 선택 전에는 계획 생성·승인·mutation 진행 UI를 표시하지 않는다.
- 원래 자연어 요청을 카드 state에 보존하되 새 요청과 섞이지 않도록 message/turn 식별자와 연결한다.
- 후보가 선택 사이에 disable 또는 삭제되면 실행 실패를 안내하고 최신 후보를 다시 조회한다.

### 작업 5. AgentRun 계획 카드와 명시적 승인

- Agent turn이 `run_id`를 반환하면 message에 AgentRun 카드를 연결한다.
- 카드는 최소한 다음 내용을 표시한다.

  - 현재 run 상태와 선택된 Skill/version
  - plan version과 계획 요약
  - operation별 작업 종류, 현재 대상, 목적 위치/이름, 작업 이유
  - Backend가 제공하면 실행 후 예상 폴더 tree
  - 승인, 거절, 수정 요청, 취소 action

- 승인 버튼은 사용자가 보고 있는 정확한 `plan_version`과 `operation_hash`를 전송한다.

```text
POST /api/workspaces/{workspace_id}/agent/runs/{run_id}/approve
```

- 승인 중 Backend가 `409 Conflict`를 반환하면 stale 계획을 승인된 것으로 표시하지 않고 최신 run을
  다시 조회해 변경 내용을 보여준다.
- 자연어 “응”, “승인”, “진행”은 현재 대화에서 승인 대기 중인 계획이 정확히 하나일 때만 해당
  run의 승인 API 호출로 연결한다. 0개 또는 2개 이상이면 대상을 확인하고 실행하지 않는다.
- 수정은 operation JSON 편집기가 아니라 자연어 수정 요청으로 제공한다. revise 응답으로 새 plan
  version이 오면 이전 승인이 무효임을 표시하고 다시 승인받는다.
- 승인·거절·취소 버튼은 요청 처리 중 중복 제출을 방지하되, Backend idempotency와 conflict 응답을
  source of truth로 사용한다.

### 작업 6. 상태 polling·복원·결과 표시

- AgentRun 생성 후 아래 조회 API를 2초 간격으로 polling한다.

```text
GET /api/workspaces/{workspace_id}/agent/runs/{run_id}
```

- 상태는 최소한 계획 생성, 사용자 확인, 승인 대기, 실행, 검증, 종료 단계를 구분한다. Backend의
  실제 enum을 UI 표시 모델에 명시적으로 매핑하고 알 수 없는 값을 성공으로 취급하지 않는다.
- terminal 상태인 `completed`, `partial_failed`, `failed`, `conflicted`, `rejected`,
  `cancelled`에서는 polling을 중단한다.
- panel을 닫았다 다시 열거나 route를 이동했다 돌아와도 대화에 저장된 `run_id`로 진행 중 run을
  복원한다. timer 자체를 전역에 영구 유지하는 방식보다 run_id와 서버 상태를 기준으로 복구한다.
- workspace 변경, logout, component unmount 시 기존 polling을 정리해 다른 workspace run이 현재
  화면에 섞이지 않게 한다.
- 일시적 network 오류는 제한적으로 재시도하되 `401/403/404`와 terminal 상태에서는 무한 polling을
  하지 않는다.
- operation별 `pending/running/completed/failed/skipped` 상태와 오류 이유를 표시한다.
- `partial_failed`에서는 성공한 작업과 실패·skipped 작업을 구분하고 자동 rollback되지 않았음을
  명확히 안내한다.
- 최종 검증에서 hierarchy가 계획과 달라 `conflicted`가 되면 “완료”로 표시하지 않고 새 계획 또는
  수동 확인으로 이어질 수 있게 한다.

### 작업 7. Feature flag와 기존 기능 회귀 방지

- `AGENT_SKILLS_ENABLED=false` 또는 Backend의 feature-disabled 응답일 때 Skill 관리, slash Skill,
  AgentRun 생성 UI를 숨기거나 비활성화한다.
- 기능 비활성 상태에서도 기존 Query, 문서 생성, Markdown 편집, Wiki Schema 화면은 기존대로
  동작해야 한다.
- Frontend가 독자적으로 feature enabled를 가정하지 않고 Backend 상태와 배포 설정이 불일치할 때
  안전하게 기존 경로로 남는다.
- 새 API가 준비되지 않은 환경에서 mock 성공 응답이나 로컬 폴더 변경으로 기능을 흉내 내지 않는다.

### 테스트 시나리오

- Wiki Schema 화면과 Agent Skill 화면·용어·상태가 섞이지 않는 component 테스트
- 개인/team Skill 목록, 동일 이름의 scope 표시, 권한별 관리 control 테스트
- preview → draft 저장 → publish → enable/disable 상태 전이 테스트
- 자연어 `auto`, slash `explicit`, “Skill 없이 진행” `off` 요청 payload 테스트
- disabled/deleted Skill 선택과 접근 권한 상실 오류 처리 테스트
- 문서가 없는 상태의 폴더 정리 요청이 Agent endpoint로 가는 테스트
- 기존 일반 Query와 Markdown create/edit route가 유지되는 회귀 테스트
- 모호한 후보에서 특정 Skill 선택, Skill 없이 진행, 취소 동작 테스트
- 후보 선택 전 AgentRun과 mutation이 시작되지 않는 테스트
- 계획 카드가 plan version/hash와 operation 정보를 정확히 표시하는 테스트
- stale plan 승인 `409`, 중복 클릭, revise 후 재승인 테스트
- 승인 대기 run이 0개/1개/여러 개인 경우 자연어 승인 처리 테스트
- 2초 polling, terminal 상태 중단, unmount/workspace 변경 timer 정리 테스트
- panel 재진입 시 run_id 복원과 operation 진행 상태 표시 테스트
- `partial_failed`, `conflicted`, `cancelled`를 성공과 구분하는 테스트
- feature disabled 상태에서 기존 Query/create/edit/Schema 기능의 회귀 테스트

### 완료 조건

- [ ] Wiki Schema와 Agent Skill이 화면, entity, API, 상태 용어에서 분리된다.
- [ ] 사용자는 개인·팀 Skill을 권한 범위 안에서 작성·preview·게시·enable/disable할 수 있다.
- [ ] 여러 enabled Skill을 유지하면서 자연어 자동 선택과 slash 명시 선택을 모두 사용할 수 있다.
- [ ] 모호한 후보는 사용자 선택 전 실행되지 않고 “Skill 없이 진행”도 선택할 수 있다.
- [ ] 폴더 정리 요청은 현재 문서가 없어도 Agent endpoint로 전달된다.
- [ ] 계획의 operation과 변경 이유를 확인한 뒤 정확한 plan version/hash를 승인한다.
- [ ] revise된 계획은 재승인 전 실행되지 않는다.
- [ ] 진행 중 run을 2초 간격으로 조회하고 terminal 상태에서 polling을 중단한다.
- [ ] panel 재진입 시 run_id로 상태를 복원한다.
- [ ] 부분 실패·충돌·취소를 성공과 구분하며 operation별 결과를 표시한다.
- [ ] Frontend는 Spring만 호출하고 로컬에서 승인이나 folder/document mutation을 위조하지 않는다.
- [ ] feature disabled 상태에서 기존 Query/create/edit/Wiki Schema 기능에 회귀가 없다.
- [ ] lint, typecheck, 관련 테스트, production build가 통과한다.

## AI 작업 로그 연동

AI 작업 로그(저장·조회·변경분·되돌리기) Backend 구현이 끝났습니다. **프론트 연동이 없어 로그가 하나도 쌓이지 않는 상태**입니다.

두 가지 작업이 있고 **순서가 중요합니다.** 1번을 안 하면 2번 화면을 만들어도 빈 목록만 나옵니다.

---

### 1. [최우선] AI 편집 적용 시 `apply_operation_id` 전달

**2줄짜리 변경이고, 이것만 하면 AI 편집 로그가 쌓이기 시작합니다.**

### 배경 — `source=agent`는 더 이상 쓰지 않습니다

`docs/issue/frontend/2026-07-27.md`의 "AI 편집 저장 시 `source=agent` 전송" 항목을 **대체합니다.**

`source` 문자열은 클라이언트가 임의로 넣을 수 있어, 수동 편집을 AI 작업으로 위장할 수 있습니다. 위조된 로그를 지목해 되돌리면 엉뚱한 내용이 복원됩니다. 그래서 **Backend가 발급한 일회용 표**를 대조하는 방식으로 바꿨습니다.

`source` 파라미터는 기존 호출을 깨지 않으려고 받기만 하고 **아무 데서도 읽지 않습니다.** 계속 보내도 무해하지만 효과가 없습니다.

### 흐름

```
① POST .../agent/turn 응답에 applyOperationId 가 들어 있다   ← 지금 프론트가 무시 중
② 사용자가 "적용"을 누르면
③ PUT .../documents/{id}/content 의 multipart 에 apply_operation_id 로 그대로 실어 보낸다
④ Backend 가 검증하면 AI 작업 로그가 남는다
```

표는 **30분간 유효**하고, 발급받은 사용자·문서에서만 씁니다. 한 번 쓰면 소멸하므로 재사용할 수 없습니다.

### 변경 ① — 응답 타입에 필드 추가

`frontend/src/features/agent-chat/lib/markdownAgent.ts`

```ts
export type AgentTurnResponse = {
  documentId: string;
  baseVersion: number;
  requestId: string;
  applyOperationId: string;   // ← 추가. camelCase 입니다
  result: AgentTurnResult;
};
```

> 이 응답만 camelCase입니다. 기존 필드와 맞추느라 그대로 뒀습니다. 아래 로그 API들은 전부 snake_case입니다.

편집안을 화면에 들고 있는 동안 이 값을 같이 보관해야 합니다 (`useChatThread` 등).

### 변경 ② — 저장 요청에 파트 추가

`PUT /api/workspaces/{workspace_id}/documents/{document_id}/content` (`multipart/form-data`)

| 파트 | 필수 | 설명 |
|---|---|---|
| `markdown` | 필수 | 저장할 전체 Markdown 본문 |
| `base_version` | 필수 | 클라이언트가 조회한 현재 version(정수) |
| `apply_operation_id` | **AI 편집 적용 시 필수** | `agent/turn` 응답의 `applyOperationId` 를 그대로 |
| `source` | 선택 | 무시됨. 보내도 되고 안 보내도 됨 |

- **AI 편집 적용**: `apply_operation_id` 를 실어 보낸다
- **수동 저장(Ctrl+S 등)**: 보내지 않는다

### 동작 규칙

| 상황 | 결과 |
|---|---|
| 표가 유효 | 저장 + AI 작업 로그 1건 + 변경내역 1건 |
| 표 없음 / 만료 / 위조 | **저장은 성공.** 로그만 안 남음 (에러 아님) |
| 내용이 원본과 동일 | 저장 no-op. 로그 없음. **표는 소비되지 않음** |
| `base_version` 불일치 | 409 `DOCUMENT_VERSION_CONFLICT`. 문서는 그대로. **`conflict` 로그만 남음** |
| 다른 사용자가 편집 중 | 423 |

> 표가 틀려도 저장을 실패시키지 않습니다. 사용자가 쓴 글을 잃게 하지 않기 위해서입니다.
> 서버가 재시작하면 발급된 표가 무효가 됩니다(메모리 보관). 그때는 편집을 다시 요청하면 됩니다.

### 2. 작업 로그 화면

#### 2.1 목록

```http
GET /api/workspaces/{workspace_id}/ai-operation-logs?type=&status=&cursor=&size=
```

| query | 값 |
|---|---|
| `type` | `document_edit` \| `ingest` \| `lint` \| `restore` |
| `status` | `processing` \| `applying` \| `notify_pending` \| `rebuilding` \| `succeeded` \| `partially_succeeded` \| `failed` \| `conflict` |
| `cursor` | 이전 응답의 `next_cursor` 를 그대로. 첫 페이지는 생략 |
| `size` | 기본 20, 최대 100 |

```json
{
  "logs": [
    { "operation_id": "op_7Kd3", "operation_type": "document_edit", "status": "succeeded",
      "target_document_id": "doc_A", "summary": "AI 편집을 문서에 반영했습니다.",
      "changed_resource_count": 1, "restored_from": null,
      "created_at": "2026-08-03T14:20:00Z", "completed_at": "2026-08-03T14:20:00Z" }
  ],
  "next_cursor": "2026-08-03T14:20:00Z"
}
```

- 최신순입니다. `next_cursor` 가 `null` 이면 마지막 페이지입니다.
- 페이지 번호가 아니라 커서입니다. 그 사이 새 작업이 생겨도 항목이 밀리지 않습니다.
- **`changed_resource_count` 와 줄 수는 저장된 값**이라 목록 조회에 diff 계산이 없습니다.

#### 2.2 상세

```http
GET /api/workspaces/{workspace_id}/ai-operation-logs/{operation_id}
```

목록 항목의 필드에 `changes[]` 가 붙습니다.

```json
{
  "operation_id": "op_a2", "operation_type": "ingest", "status": "succeeded",
  "changes": [
    { "id": 1, "resource_type": "wiki_page", "resource_id": "wp_C3",
      "before_revision": 3, "after_revision": 4, "change_type": "updated",
      "change_summary": null, "additions": 8, "deletions": 1,
      "hunks": [ { "old_start": 12, "old_lines": 3, "new_start": 12, "new_lines": 10,
                   "lines": [ { "type": "context", "text": "..." } ] } ] }
  ]
}
```

**`hunks` 가 여기 들어 있으므로 상세 한 번으로 변경분까지 그릴 수 있습니다.** 별도 diff 호출이 필요 없습니다.

| 상황 | `hunks` | `diff_too_large` |
|---|---|---|
| 갱신·복원·재작성 | 있음 | 없음 |
| 생성·삭제·위임·재작성실패 | **없음** (비교할 짝이 없음) | 없음 |
| 두 본문 차이가 너무 큼 | **없음** | `true` |

`diff_too_large: true` 인 항목은 개별 diff 엔드포인트로도 볼 수 없습니다. "변경분이 너무 커서 표시할 수 없습니다" 정도로 안내하면 됩니다. **그 항목만 그렇고 나머지는 정상입니다.**

`change_type` 별 의미:

| 값 | 뜻 | `after_revision` |
|---|---|---|
| `created` | 새로 만듦 | 있음 (`before` 는 null) |
| `updated` | 갱신 | 있음 |
| `deleted` | 받치는 기여가 없어 삭제 | **null** |
| `restored` | 예전 내용으로 되돌림 | 있음 |
| `delegated` | 재작성을 llmPipeline에 맡김 | **null** |
| `rebuilt` | 재작성 성공 | 있음 |
| `rebuild_failed` | 재작성 실패. 사유는 `change_summary` | **null** |

#### 2.3 변경분

```http
GET .../wiki/pages/{wiki_page_id}/diff?from=3&to=4                 ← 위키 (신규)
GET .../documents/{document_id}/diff?from_version=5&to_version=6   ← 문서 (기존)
```

> ⚠️ **쿼리 파라미터 이름이 다릅니다.** 위키는 `from`·`to`, 문서는 `from_version`·`to_version` 입니다.
> 문서 쪽은 기존 API라 응답 스키마를 깨지 않으려고 그대로 뒀습니다.

`hunks` 구조는 문서와 위키가 **동일**합니다. 계산기를 공유하고 감싸는 필드만 다릅니다.

```json
// 위키
{ "page_id": "wp_C3", "from_revision": 3, "to_revision": 4,
  "additions": 8, "deletions": 1,
  "hunks": [ { "old_start": 12, "old_lines": 3, "new_start": 12, "new_lines": 10, "lines": [...] } ] }

// 문서 — 식별자와 버전 필드 이름이 다릅니다
{ "document_id": "doc_A", "from_version": 5, "to_version": 6,
  "additions": 12, "deletions": 3, "hunks": [ ... ] }
```

- 404 `WIKI_PAGE_VERSION_NOT_FOUND` / `DOCUMENT_CONTENT_VERSION_NOT_FOUND` — 그 버전이 없음
- 422 `MARKDOWN_DIFF_TOO_LARGE` — 두 본문 차이가 너무 커서 계산 거부

> **결정됨(2026-08-03)**: **상세 응답이 변경분을 함께 담습니다.** 2.2의 `changes[]` 각 항목에 `hunks` 가 들어 있으므로,
> 목록에서 한 건을 고르면 상세 한 번으로 화면을 그릴 수 있습니다. 이 절의 개별 diff 엔드포인트는
> 버전 목록 화면처럼 임의의 두 버전을 비교할 때만 쓰면 됩니다.

#### 2.4 되돌리기 — 미리보기 먼저

```http
GET  .../ai-operation-logs/{operation_id}/restore-preview
POST .../ai-operation-logs/{operation_id}/restore     { "preview_token": "..." }
```

**되돌리기는 반드시 미리보기를 거쳐야 합니다.** 미리보기 응답의 `preview_token` 을 실행에 그대로 넘겨야 하며, 그 사이 대상이 바뀌면 409로 거절됩니다.

미리보기 응답은 **작업 종류에 따라 모양이 다릅니다.** 둘 중 하나만 찹니다.

```json
// AI 문서 편집을 지목한 경우
{ "operation_id": "op_7Kd3",
  "delete_count": 0, "restore_count": 1, "rebuild_count": 0,
  "pages": [],
  "document": { "document_id": "doc_A", "from_version": 6, "to_version": 5 },
  "preview_token": "..." }

// 위키 ingest 를 지목한 경우
{ "operation_id": "op_a2",
  "delete_count": 1, "restore_count": 1, "rebuild_count": 1,
  "pages": [
    { "page_id": "wp_C6", "action": "delete",  "target_revision": null, "contribution_count": 0 },
    { "page_id": "wp_S_A","action": "restore", "target_revision": 3,    "contribution_count": 1 },
    { "page_id": "wp_C3", "action": "rebuild", "target_revision": null, "contribution_count": 2 }
  ],
  "preview_token": "..." }
```

실행 응답:

```json
{ "operation_id": "op_restore_9a2b", "restored_from": "op_a2",
  "delete_count": 1, "restore_count": 1, "rebuild_count": 1,
  "rebuilding": true, "status": "rebuilding" }
```

| `status` | 화면 |
|---|---|
| `succeeded` | 끝났습니다. **문서 편집 되돌리기만 여기서 바로 나옵니다** |
| `rebuilding` | llmPipeline 처리 중. 상세를 폴링해 완료를 확인 |
| `notify_pending` | 되돌리기는 반영됐고 llmPipeline 통지가 보류됨. 재시도 필요 |

> Wiki 되돌리기는 `rebuild_count`가 0이어도 `rebuilding`으로 옵니다. 재작성할 페이지가 없어도 llmPipeline이 링크·임베딩을 정리한 뒤 결과를 보내오기 때문입니다. `rebuild_count`로 완료 여부를 판단하지 말고 `status`를 보세요.

에러:

| status | code | 상황 |
|---|---|---|
| 400 | `INVALID_RESTORE_REQUEST` | 되돌릴 수 없는 작업, 되돌릴 대상 없음, 이미 그 버전 |
| 404 | `AI_OPERATION_NOT_FOUND` | |
| 409 | `RESTORE_PREVIEW_STALE` | **미리보기 이후 대상이 변경됨. 미리보기를 다시 받아야 함** |
| 423 | | 다른 사용자가 문서 편집 중 (문서 되돌리기만) |

### UX 상 반드시 알려야 할 것

**지목한 작업 하나가 아니라 그 이후까지 전부 취소됩니다.** 예를 들어 `A1 → A2 → A3` 순으로 ingest한 문서에서 A2를 지목하면 **A2와 A3이 함께** 취소되고, 그 과정에서 만들어진 위키 페이지는 삭제됩니다. 미리보기의 `delete_count` 를 눈에 띄게 보여줘야 합니다.

A2까지는 살리고 싶다면 그다음 작업인 A3을 지목하면 됩니다.

**되돌려도 버전은 앞으로 갑니다.** 버전 6에서 5로 되돌리면 5가 되는 게 아니라 5의 내용을 담은 **버전 7**이 생깁니다.

**위키 되돌리기는 무를 수 없습니다.** 문서와 달리 한 방향입니다. 확인 단계를 문서보다 강하게 두는 것이 좋습니다.
