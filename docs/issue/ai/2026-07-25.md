# 2026-07-25 AI/Pipeline 이슈

## Query 후보 조회가 DB에서 제한되지 않음

`source_related_to` 전체 Source 조합 생성과 원본 DB 저장은 제거했다. 해결 내용은
`docs/backlog/issue-2026-07-25.md`의
`AI/Pipeline — source_related_to 전체 조합 저장 제거`를 참조한다.

### 실제 문제

- `AnswerQueryUseCase._score_wiki_candidates()`가
  `list_active_pages(workspace_id)`와 `list_active_links(workspace_id)`로 활성
  Workspace의 page와 link 전체를 먼저 읽은 뒤 후보 수를 제한한다.
- `source_candidate_limit`와 `concept_candidate_limit`는 Python 메모리에서 점수를
  계산한 뒤 적용되므로 DB 조회량과 link materialization 비용을 줄이지 못한다.
- Workspace의 Wiki page/link 수가 늘면 질문과 무관한 row까지 매 요청마다
  역직렬화하고 점수 계산 대상으로 올린다.

### 필요한 작업

1. `WikiRepositoryPort`에 질문 후보 page 조회와 선택된 page 주변 link 조회
   경계를 정의한다.
2. PostgreSQL text search 또는 저장된 embedding 검색에서 Source/Concept 후보
   수를 먼저 제한한다.
3. 선택된 후보 page id를 기준으로 필요한 link만 조회하고 traversal을 수행한다.
4. Source 수를 늘린 fixture에서 DB가 반환하는 page/link row 수와 latency를
   측정한다.

### 완료 조건

- Query가 Workspace 전체 page·link를 메모리에 올리지 않는다.
- DB에서 반환되는 후보 page와 주변 link 수에 명시적인 상한이 있다.
- page/link 수가 증가해도 질문 한 건의 조회량이 Workspace 전체 크기에 비례하지 않는다.
- 기존 답변의 evidence, related page, traversal path 계약이 유지된다.

### 확인 위치

- 전체 page/link 조회:
  `llmPipeline/app/modules/query/application/answer_query.py`의
  `_score_wiki_candidates`
- PostgreSQL 조회:
  `llmPipeline/app/modules/query/infrastructure/postgres_wiki_repository.py`의
  `list_active_pages`, `list_active_links`
- Query 저장소 계약:
  `llmPipeline/app/modules/query/application/ports.py`의 `WikiRepositoryPort`

## Legacy `source_related_to` 정리와 계약 문서 불일치

### 실제 문제

- 새 Wiki 산출물을 저장할 때는 해당 Workspace의 legacy `source_related_to` row를
  삭제하지만, 재ingest하지 않은 Workspace의 기존 row는 DB에 남는다.
- Query는 legacy row를 읽지 않으므로 답변 결과에는 사용되지 않지만 불필요한
  저장 공간과 운영 혼동이 남는다.
- `docs/spec/query-engine.md`와
  `docs/spec/llmpipeline-backend-output-contract.md`는
  `source_related_to`를 저장·반환하는 계약을 설명하지만 현재 구현은 생성과
  Query 사용을 제거했다.
- 현재 backend/frontend에는 관련 Source 전용 API 또는 소비 화면이 확인되지 않아
  어느 계산 방식을 구현해야 하는지 제품 요구가 없다.

### 결정

- 관련 Source Top-K나 threshold materialization은 현재 구현하지 않는다.
- 소비 API와 사용자 시나리오가 생길 때 별도 계약을 먼저 확정한다.
- 지금 필요한 작업은 legacy row 일괄 정리와 현재 동작에 맞춘 계약 문서 정합화다.

### 필요한 작업

1. 전체 Workspace의 legacy `source_related_to` row를 제거하는 Flyway migration
   또는 검증 가능한 일회성 운영 절차를 추가한다.
2. `docs/spec/query-engine.md`와
   `docs/spec/llmpipeline-backend-output-contract.md`에서
   `source_related_to`를 원본 link로 저장한다는 옛 계약을 제거한다.
3. 관련 Source 기능은 실제 소비 endpoint, 결과 상한, 정렬 기준이 정의될 때
   새 이슈로 작성한다.

### 완료 조건

- 재ingest하지 않은 Workspace에도 legacy `source_related_to` row가 남지 않는다.
- 현재 계약 문서가 `source_related_to`를 Wiki 원본 link로 안내하지 않는다.
- 관련 Source materialization을 요구사항 없이 미리 구현하지 않는다.

### 확인 위치

- 현재 Workspace 단위 삭제:
  `llmPipeline/app/modules/wiki_ingestion/infrastructure/postgres_wiki_writer.py`의
  `delete_source_related_links`
- Query 제외:
  `llmPipeline/app/modules/query/infrastructure/postgres_wiki_repository.py`의
  `list_active_links`
- 충돌 문서:
  `docs/spec/query-engine.md`의 `source_related_to`,
  `docs/spec/llmpipeline-backend-output-contract.md`의 `link_type`

## Multi-provider 실환경 E2E 검증

`LLM_PROVIDER`와 `LLM_*` 설정 일원화, ingestion·markdown 편집·query·agent
router의 공통 provider 해석, Claude Messages API 변환은 구현했다. 해결 내용은
`docs/backlog/issue-2026-07-25.md`의
`AI/Pipeline — Multi-provider 설정과 Claude Messages API 지원`을 참조한다.

남은 작업은 provider별 실제 API를 사용한 통합 검증이다.

### 현재 상태

- 공통 설정 resolver와 Claude Messages 요청·응답 변환의 단위 계약은 검증됐다.
- OpenAI, Gemini, Claude의 실제 credential을 사용하는 네트워크 E2E는 실행하지
  않았으므로 provider 지원 완료로 단정할 수 없다.
- 이 작업은 credential과 외부 API 접근이 준비돼야 실행할 수 있다.

### 필요한 작업

- OpenAI, Gemini, Claude의 유효한 테스트 credential을 준비한다.
- provider마다 `LLM_PROVIDER`, `LLM_API_KEY`, `LLM_MODEL`을 바꾸고 pipeline을
  재시작한다.
- 문서 업로드→Wiki ingestion 완료와 agent의 `chat_answer`,
  `markdown_edit`, `markdown_create`를 실행한다.
- Claude에서 JSON 응답, 일반 text 응답, `max_tokens`, 오류 응답 변환을 확인한다.
- provider별 성공 여부와 사용한 model을 변경 기록에 남긴다. 비밀키와 원문
  provider 응답은 기록하지 않는다.

### 완료 조건

- OpenAI, Gemini, Claude 각각에서 ingestion과 agent 대표 action이 정상 응답한다.
- 한 실행에서 모든 LLM 경로가 동일한 `LLM_PROVIDER` 설정을 사용한다.
- Claude의 구조화 출력이 기존 JSON 계약 검증을 통과한다.
- credential 누락과 provider 오류가 비밀값을 노출하지 않고 실패한다.

### 확인 위치

- 공통 설정:
  `llmPipeline/app/core/llm_env.py`의 `resolve_llm_provider_defaults`,
  `provider_api_endpoint`
- 공통 client:
  `llmPipeline/app/modules/wiki_generation/infrastructure/chat_completions_llm.py`의
  `ChatCompletionsJsonClient`
- ingestion:
  `llmPipeline/run_lab.py`의 `resolve_api_defaults`, `load_api_client`
- 계약 테스트:
  `llmPipeline/tests/modules/wiki_generation/test_chat_completions_client.py`,
  `llmPipeline/tests/modules/test_llm_env.py`,
  `llmPipeline/tests/test_run_lab_args.py`
