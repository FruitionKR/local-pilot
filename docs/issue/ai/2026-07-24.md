# AI 파이프라인 이슈 (2026-07-24)

## 채팅→원본문서 편입 시 wiki 생성(ingestion) 크래시 — UPSTAGE_API_KEY 강제

### 증상
채팅을 원본 문서로 편입하면 문서(`chatdoc_*`)는 생성되지만(202), **wiki 생성 파이프라인이 크래시**해 wiki 페이지가 만들어지지 않는다. 결과적으로 `GET /api/workspaces/{id}/wiki/graph`가 계속 `nodes:0`.

파이프라인 컨테이너 로그:
```
run_lab.py:233 load_api_client
  → SystemExit: Missing API key. Set UPSTAGE_API_KEY=... or pass --api-key
```

### 원인
LLM을 Upstage → Gemini로 전환하며 `infra/.env`에서 `UPSTAGE_API_KEY/UPSTAGE_BASE_URL/UPSTAGE_MODEL`을 비우고 `LLM_API_KEY/LLM_BASE_URL/LLM_MODEL`(Gemini)로 옮겼다.

파이프라인 LLM 클라이언트 경로가 **2개**인데 API 키 해석 방식이 다르다:
- **chat_completions 경로**(markdown 편집·query·agent router): `app/core/llm_env.py`의 env 우선순위에 `LLM_API_KEY` 폴백이 있어 Gemini로 정상 동작.
- **ingestion 경로**(`llmPipeline/run_lab.py`, 편입 후 wiki 생성): `resolve_api_defaults`(run_lab.py:184-)의 `provider == "upstage"` preset이 **base_url·model은 `LLM_*` 폴백을 보지만 API 키만 `UPSTAGE_API_KEY`로 고정**(LLM_API_KEY 폴백 없음). ingestion route provider 기본값도 `"upstage"`(`app/modules/wiki_ingestion/application/models.py:15,47`).

→ `UPSTAGE_API_KEY`가 비어 `load_api_client`(run_lab.py:229-233)가 즉시 `SystemExit`.

관련 코드:
- `llmPipeline/run_lab.py:184-214` `resolve_api_defaults` (upstage preset이 api_key_env를 UPSTAGE_API_KEY로 고정)
- `llmPipeline/run_lab.py:229-233` `load_api_client` (키 없으면 SystemExit)
- `llmPipeline/app/modules/wiki_ingestion/application/models.py:15,47` (`provider: str = "upstage"` 기본값)
- `llmPipeline/app/modules/wiki_ingestion/interfaces/http/routes.py:241,250` (`provider=payload.provider`)

### 프론트에서 처리 불가
프론트엔드 코드로는 해결 불가. LLM 키 해석은 파이프라인(`run_lab.py`)/인프라(`infra/.env`, docker-compose) 영역. `frontend/CLAUDE.md`상 파이프라인·인프라 코드는 프론트 작업 범위 밖.

### 해결 방안 (택1)
1. **(config만, 파이프라인 코드 미수정)** `infra/.env`의 `UPSTAGE_API_KEY/UPSTAGE_BASE_URL/UPSTAGE_MODEL`을 비우지 말고 Gemini 값으로 채운다.
   ```
   UPSTAGE_API_KEY=<Gemini 키>
   UPSTAGE_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai
   UPSTAGE_MODEL=gemini-flash-latest
   ```
   upstage preset도 Gemini를 쓰게 되어 ingestion 통과. chat 경로도 우선순위상 동일 Gemini(변화 없음). 이후 pipeline 컨테이너 재생성 필요.
2. **(근본 수정)** `run_lab.py resolve_api_defaults`의 upstage preset api 키 해석에 `LLM_API_KEY` 폴백 추가, 또는 ingestion route가 `LLM_PROVIDER` env 기준으로 `provider`를 `generic`으로 넘기도록 변경.

### 담당
AI/pipeline(run_lab.py) 또는 infra(.env/compose 설정). 프론트 무관.

## 멀티 LLM provider 지원 — OpenAI(ChatGPT) / Gemini / Claude 전환 가능하게

### 목표
`infra/.env`의 provider 설정 하나로 **OpenAI(ChatGPT)·Gemini·Claude(Anthropic)** 중 택1해 파이프라인 전 경로(ingestion·markdown 편집·query·agent router)가 동일 provider로 동작하도록 만든다. 위 UPSTAGE_API_KEY 크래시의 근본 원인(경로별 키/엔드포인트 해석 불일치 + provider 하드코딩)을 제거한다.

### 현재 구조 (문제)
LLM 클라이언트 경로가 2개인데 provider/키 해석이 제각각:
- **chat_completions 경로**(`llmPipeline/app/core/llm_env.py`): 키/모델/base_url을 `MARKDOWN_EDIT_* → QUERY_* → UPSTAGE_* → LLM_*` 우선순위로 해석. OpenAI 호환 `/chat/completions` 고정.
- **ingestion 경로**(`llmPipeline/run_lab.py:184- resolve_api_defaults`): `provider`(`upstage`/`generic`) preset으로 분기. `upstage`는 키를 `UPSTAGE_API_KEY`로 **하드코딩**(LLM_API_KEY 폴백 없음). route provider 기본값도 `"upstage"`(`app/modules/wiki_ingestion/application/models.py:15,47`).

→ 두 경로가 같은 env를 서로 다르게 읽어, 한쪽만 Gemini로 전환하면 다른 쪽이 깨진다.

### provider별 API 호환성 (핵심 난점)
전 경로가 **OpenAI `/chat/completions` 스키마**를 전제로 짜여 있음. 그래서:
| provider | 엔드포인트 | OpenAI `/chat/completions` 호환 | 비고 |
|---|---|---|---|
| OpenAI(ChatGPT) | `https://api.openai.com/v1` | ✅ native | 그대로 동작 |
| Gemini | `https://generativelanguage.googleapis.com/v1beta/openai` | ✅ OpenAI 호환 엔드포인트 제공 | `gemini-flash-latest` 등 |
| Upstage | `https://api.upstage.ai/v1` | ✅ | 기존 기본값(solar-pro2) |
| **Claude(Anthropic)** | `https://api.anthropic.com/v1/messages` | ❌ **미호환** | 아래 참조 |

**Claude가 유일한 난점.** Anthropic은 OpenAI `/chat/completions`를 제공하지 않고 **Messages API**를 씀:
- endpoint: `POST https://api.anthropic.com/v1/messages`
- 헤더: `x-api-key: <key>`, `anthropic-version: 2023-06-01` (OpenAI식 `Authorization: Bearer` 아님)
- 요청: `system`이 messages 밖 top-level 필드, `max_tokens` **필수**, messages는 user/assistant만
- 응답: `content`가 블록 배열(`[{type:"text", text:...}]`) — `choices[0].message.content` 아님
- JSON 강제: OpenAI/Gemini의 `response_format` 대신 **tool_use 또는 assistant prefill** 사용
- 모델 예: `claude-opus-4-8`, `claude-sonnet-5`, `claude-haiku-4-5-20251001`

즉 Claude는 base_url/key만 바꿔선 안 되고 **요청·응답 변환 계층이 필요**하다.

### 접근안 (택1)

**A. OpenAI 호환 게이트웨이 방식 (파이프라인 코드 최소 변경, 권장 시작점)**
- LiteLLM proxy 같은 OpenAI 호환 게이트웨이를 인프라에 두고, 파이프라인은 `LLM_BASE_URL`을 게이트웨이로만 향하게 함. 게이트웨이가 provider별(OpenAI/Gemini/Claude Messages) 변환을 담당.
- 장점: `run_lab.py`/`llm_env.py` 스키마 변환 코드 안 건드림. Claude 포함 3종을 base_url·model·key 설정만으로 전환.
- 단점: 게이트웨이 컨테이너 1개 추가(compose), 운영 요소 증가.

**B. 파이프라인 내부 provider 추상화 (근본 수정)**
1. 키/엔드포인트 해석을 **단일 소스로 통합**: 두 경로가 `LLM_PROVIDER` + `LLM_API_KEY`/`LLM_BASE_URL`/`LLM_MODEL`(+ provider별 override)만 읽게. `resolve_api_defaults`의 upstage 하드코딩 제거, ingestion route `provider` 기본값을 `LLM_PROVIDER` env 기준으로.
2. **Anthropic 어댑터** 추가: 기존 `ChatCompletionsJsonClient`와 동일 인터페이스로, 내부에서 `/v1/messages` 요청/응답 및 JSON(tool_use/prefill) 변환. `LLM_PROVIDER=claude`일 때 이 어댑터를 주입.
3. OpenAI/Gemini/Upstage는 기존 chat_completions 클라이언트 재사용(엔드포인트/모델만 preset).
- 장점: 외부 게이트웨이 불필요, provider 전환이 순수 env. 단점: 어댑터·통합 리팩터 작업량 큼.

### 통합 env 설계(안)
```
LLM_PROVIDER=openai|gemini|claude|upstage
LLM_API_KEY=<provider 키>
LLM_BASE_URL=<provider 엔드포인트>   # claude는 게이트웨이(A) 또는 어댑터가 내부 고정(B)
LLM_MODEL=<provider 모델>
```
경로별 `UPSTAGE_*`/`MARKDOWN_EDIT_*`/`QUERY_*` override는 유지하되 **최종 폴백을 `LLM_*` 단일 소스로 일원화**.

- 3종(OpenAI/Gemini/Claude) 각각에서 문서 업로드→wiki 생성(ingestion) 완료 + 채팅 편집(markdown_edit) 정상.
