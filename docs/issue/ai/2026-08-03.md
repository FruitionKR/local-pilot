# AI(llmPipeline) 이슈 — 2026-08-03

AI 작업 로그(저장·조회·변경분·되돌리기) Backend 구현이 끝났습니다. **llmPipeline 연동이 없어 위키 작업이 이력에 남지 않고 되돌릴 수도 없습니다.**

Backend는 받을 준비가 다 돼 있고 상대편 코드만 기다립니다. 아래 순서대로 진행하면 됩니다.

> **L2가 가장 급합니다.** ingest 시점에 기여 조각을 남기지 않으면 그 기간에 쌓인 데이터는 **나중에 어떤 방법으로도 되돌릴 수 없습니다.** 하루 늦어질수록 복구 불가능한 구간이 하루씩 늘어납니다.

---

## L1. 요청 스키마에 필드 2개 추가

**이게 없으면 Backend가 호출 자체를 못 합니다.**

`app/modules/wiki_ingestion/interfaces/http/schemas.py` — `_PipelineRunBase`

```python
class _PipelineRunBase(BaseModel):
    model_config = ConfigDict(extra="forbid")   # ← 모르는 필드가 오면 422
    ...
    operation_id: str | None = None
    result_callback_url: str | None = None
```

`extra="forbid"` 때문에 지금 Backend가 `operation_id`를 보내면 **ingest 요청 전체가 422로 깨집니다.** 그래서 Backend는 `app.aihistory.ingest-logging-enabled=false`로 꺼둔 상태입니다.

이 두 필드를 받아 **실행 전 구간에 전달**해 주세요. L2의 object key와 L3의 콜백에 씁니다.

- 완료 조건: `extra="forbid"` 상태에서 Backend 요청이 422 없이 수용됨

## L2. [최우선] 본문 key 체계 변경 · 기여 조각 저장 · `wiki_pages` 갱신 제거

세 가지가 한 덩어리입니다. **되돌리기가 성립하기 위한 최소 조건**입니다.

### 2-1. 작업별 불변 key로 쓰기 (덮어쓰지 않기)

현재는 slug/document_id 기준 경로에 **매번 덮어씁니다.**

| 위치 | 현재 key |
|---|---|
| `postgres_wiki_output_persistence.py:99` | `wiki/{user_id}/{workspace_id}/sources/{document_id}.md` |
| `postgres_wiki_output_persistence.py:164` | `wiki/{user_id}/{workspace_id}/concepts/{slug}.md` |
| `postgres_wiki_ingestion_repository.py:621` | 동일 패턴 |

바꿀 형태:

```
wiki/{workspace_id}/pages/{page_id}/ops/{operation_id}.md     본문
wiki/{workspace_id}/pages/{page_id}/ops/{operation_id}.json   기여 조각
```

**덮어쓰지 않아야 하는 이유**: 되돌리기는 "그때 그 본문"을 다시 가리키는 방식으로 동작합니다. 예전 파일이 남아 있으면 Backend가 저장소에 아무것도 쓰지 않고 포인터만 옮기면 끝납니다. 덮어쓰면 예전 본문이 사라져 복원이 불가능합니다.

**`slug`가 아니라 `page_id`를 쓰는 이유**: slug는 rename으로 바뀝니다. 바뀌면 예전에 쓴 파일 경로를 다시 찾을 수 없습니다.

Backend는 이 경로를 **정확히 대조**한 뒤에만 읽습니다. 형식이 다르면 422로 거절합니다.

### 2-2. 기여 조각 저장 (신규)

`.json`에 **"이 문서가 이 페이지에 보탠 부분"** 을 남겨 주세요.

개념 페이지는 여러 원문 문서의 내용이 한 편의 글로 합쳐진 결과입니다. 문서 A를 되돌리려 해도 A 부분만 오려낼 수 없습니다. 그래서 되돌리기는 **남은 조각들을 다시 붙여 새로 쓰는** 방식입니다(L4).

조각이 없으면 재작성 자체가 불가능합니다. 형식은 llmPipeline이 재조립에 쓸 수 있으면 되고, Backend는 **경로만 보관**하고 내용을 해석하지 않습니다.

- 완료 조건: 저장한 조각만으로 페이지 재구성이 가능함

### 2-3. `wiki_pages` 갱신 제거 ← **이번에 발견된 항목**

`postgres_wiki_writer.py:176~188`

```sql
INSERT INTO wiki_pages (..., status, ...) VALUES (..., 'active', ...)
ON CONFLICT (user_id, workspace_id, page_type, slug) DO UPDATE SET
    ...
    markdown_uri = EXCLUDED.markdown_uri,   -- ← 제거해야 함
    status = 'active',                      -- ← 제거해야 함
    updated_at = now()
```

**두 컬럼 모두 Backend 소유입니다.**

`markdown_uri`는 Backend가 콜백을 받아 **경로를 검증하고 본문 해시를 대조한 뒤에** 옮깁니다. llmPipeline이 먼저 갱신하면, 쓰다가 끊긴 파일을 페이지가 가리키게 됩니다.

`status`는 되돌리기의 소프트 삭제에 쓰입니다. `wiki_pages.status`에 `deleted`가 추가됐습니다(Backend `V17`).

> **지금 상태로 두면 되돌리기가 깨집니다.**
> ```
> ① 되돌리기로 페이지 삭제        status = deleted
> ② 같은 개념이 다시 추출됨        ON CONFLICT → status = 'active' 로 되살아남
> ③ 결과                          기여는 전부 꺼진 채로 페이지만 살아 있음
> ```
> 받치는 문서가 하나도 없는 페이지가 화면에 나오고, 되돌리기를 다시 하면 또 지웁니다.

`INSERT`의 신규 생성은 그대로 두고, **`ON CONFLICT DO UPDATE`에서 `markdown_uri`와 `status`만 빼면** 됩니다.

- 완료 조건
  - [ ] 같은 페이지를 두 번 처리해도 이전 object가 유지됨
  - [ ] `wiki_pages.markdown_uri`·`status`가 llmPipeline에서 갱신되지 않음
  - [ ] slug rename 이후에도 경로가 어긋나지 않음

## L3. 결과 콜백

작업이 끝나면 `result_callback_url`로 POST 해 주세요.

```http
POST {result_callback_url}
X-Internal-Token: {INTERNAL_CALLBACK_TOKEN}
```

```json
{
  "operation_id": "op_a2_7f3c9",
  "operation_type": "ingest",
  "status": "succeeded",
  "workspace_id": "ws_1",
  "user_id": "user_1",
  "target_document_id": "doc_A",
  "summary": "위키 페이지 3개를 갱신했습니다.",
  "changed_pages": [
    { "page_id": "wp_C2",
      "page_type": "concept",
      "markdown_key": "wiki/ws_1/pages/wp_C2/ops/op_a2_7f3c9.md",
      "contribution_key": "wiki/ws_1/pages/wp_C2/ops/op_a2_7f3c9.json",
      "content_hash": "sha256:3c4d..." }
  ]
}
```

**본문은 싣지 않습니다.** 어디에 썼는지와 지문만 보내면 Backend가 검증 후 읽습니다.

| 필드 | 없으면 |
|---|---|
| `operation_id` | 멱등 불가 |
| `page_id` | 기여 이력 누락 → 버전 계산이 어긋남 |
| `markdown_key` | 그 작업의 본문을 특정 못 함 |
| `contribution_key` | **재조립 불가** |
| `content_hash` | 쓰기가 잘렸는지 확인 불가 |

`workspace_id`·`user_id`·`target_document_id`는 **권한 근거로 쓰이지 않습니다.** 요청 등록 때 저장한 값과 일치하는지 대조만 합니다. 생략하면 대조하지 않습니다.

### 응답별 대응

| 응답 | 할 일 |
|---|---|
| 200 | 없음 |
| 200 (같은 `payload_hash` 재전송) | 없음 |
| 401 `INVALID_CALLBACK_TOKEN` | 토큰 확인 |
| 409 `AI_OPERATION_PAYLOAD_CONFLICT` | **중단.** 같은 작업에 다른 결과를 보냈음 |
| 422 `INVALID_CALLBACK_PAYLOAD` | 경로·해시 검증 실패. **다시 쓰고 재전송** |

응답 body는 `{ "operation_id", "status", "recorded_changes" }`입니다. `status`는 Backend가 실제로 확정한 값이라, 부분 실패면 `partially_succeeded`가 옵니다.

### 부분 실패도 만든 것은 보내주세요

`status: "failed"`로 보내더라도 **이미 만들어진 페이지는 `changed_pages`에 담아야 합니다.** 안 보내면 위키에는 페이지가 있는데 이력에 없어서, 그 페이지만 영영 복구 대상에서 빠집니다.

- 완료 조건: 성공·부분 실패·실패 각각에서 콜백 발송 / 안 바뀐 페이지는 `changed_pages`에 미포함 / 재전송 시 동일 payload

## L4. 재조립 엔드포인트 `POST /wiki/restore-runs` (신규)

Backend가 되돌리기를 실행하면 **자기가 못 하는 것만** 넘깁니다.

```json
{
  "operation_id": "op_restore_9a2b",
  "restored_from": "op_a2",
  "workspace_id": "ws_1",
  "user_id": "user_1",
  "result_callback_url": "http://backend/api/ai-operations/op_restore_9a2b/result",
  "excluded_operations": ["op_a3", "op_a4"],
  "rebuild_pages": [
    { "page_id": "wp_C3",
      "contribution_count": 2,
      "keep_contributions": [
        { "operation_id": "op_a2", "document_id": "doc_A", "object_key": "wiki/.../op_a2.json" },
        { "operation_id": "op_b",  "document_id": "doc_B", "object_key": "wiki/.../op_b.json" }
      ] }
  ],
  "restored_pages": [ { "page_id": "wp_S_A", "revision": 4 } ],
  "deleted_pages": ["wp_C8"]
}
```

| 항목 | 성격 |
|---|---|
| `rebuild_pages` | **요청** — `keep_contributions`를 **순서대로** 붙여 페이지를 다시 써 주세요. 순서가 결과를 바꿉니다 |
| `restored_pages` · `deleted_pages` | **통보** — 이미 끝난 사실입니다. 임베딩·링크 정리에 쓰세요 |

- `keep_contributions`가 1개면 조립이 아니라 그 조각을 그대로 쓰면 되므로 **LLM 호출이 필요 없습니다.**
- 지시된 조각만 쓰고, `excluded_operations`의 조각은 **절대 쓰지 마세요.**
- 결과는 L3과 **같은 엔드포인트**로 보내되 `failed_pages`를 더합니다.

```json
{
  "operation_id": "op_restore_9a2b",
  "operation_type": "restore",
  "status": "partially_succeeded",
  "changed_pages": [ { "page_id": "wp_C3", "markdown_key": "...", "content_hash": "..." } ],
  "failed_pages": [ { "page_id": "wp_C6", "reason": "contribution_missing" } ]
}
```

- **`contribution_count`를 다시 계산하지 마세요.** Backend가 지시서에 담아 보낸 값이 목표치입니다. Backend도 그 값을 `restore_manifest`에서 꺼내 씁니다.
- 지시서의 `rebuild_pages`에 없는 페이지를 결과에 담으면 **422로 거절**됩니다.
- 조각이 유실됐으면 그 페이지만 `failed_pages`로 보고하세요. Backend가 `rebuild_failed`로 기록하고 본문은 건드리지 않습니다.

- 완료 조건: 지정한 조각만 사용 / 조각 유실 시 해당 페이지만 `failed_pages` / `deleted_pages`의 임베딩 정리

## L5. lint 확장

`POST /wiki/maintenance/lint` 요청에 `operation_id`, 응답에 `changed_pages`를 더해 주세요.

lint는 **기여를 만들지 않습니다.** 이미 있는 글을 다듬는 것이라 새로 보태는 문서가 없습니다. 그래서 `contribution_key`가 없고 `contribution_count`도 올라가지 않습니다. 버전만 하나 올라갑니다.

`dry_run=true`면 `changed_pages`는 빈 배열입니다.

> 현재 Backend의 lint 연동도 없습니다(`WikiMaintenanceService`가 권한만 확인하고 그대로 위임). 응답에 `changed_pages`가 생기면 Backend가 로그 기록을 붙입니다.

- 완료 조건: `dry_run=true`면 빈 배열 / 실제 변경 시 페이지 목록과 `content_hash` 반환

## L6. workspace별 ingest 직렬 실행 보장

같은 워크스페이스의 ingest 2건이 동시에 실행되면, 같은 페이지에 대한 콜백이 동시에 도착해 revision 채번이 겹칠 수 있습니다.

> Backend 쪽에도 같은 성격의 미구현 항목이 있습니다(ingest 적재 시 행 잠금). 양쪽 중 하나만 있어도 대부분 막히지만, 1차 구현에서는 llmPipeline의 직렬 실행이 더 단순합니다.

- 완료 조건: 같은 workspace의 ingest 2건이 동시에 실행되지 않음
