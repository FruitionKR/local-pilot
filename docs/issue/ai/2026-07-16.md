# 2026-07-16 AI/Pipeline 이슈

2026-07-16 backend + llmPipeline 전체 API 호출 점검 중 발견한 버그와 PDF 복원 개선 작업을 기록합니다.

## 1. llmPipeline의 직접 documents 생성 경로가 backend DB 계약과 충돌

- `POST /pipeline/runs`에 `input_markdown` 또는 `input_path`를 직접 넘기면 llmPipeline이 `documents` row를 생성하면서 `content_hash NOT NULL` 제약을 충족하지 못해 500 응답이 발생했다.
- 실제 backend 흐름은 파일·채팅 Markdown을 저장하고 `documents` transaction을 커밋한 뒤 처리 큐를 통해 llmPipeline을 호출한다. 따라서 정상 실행 시 llmPipeline이 `documents`를 생성할 필요가 없다.
- 일반 `/pipeline/runs`는 backend가 먼저 생성한 `document_id`만 입력으로 받도록 제한하고, 직접 `input_markdown`·`input_path` 경로와 `create_pipeline_input_document`를 제거한다.
- `/chat-wiki/runs`의 `input_markdown`은 기존 source page에 새 대화만 누적하기 위한 delta 입력이므로 유지한다. 단, 해당 `document_id`가 backend에 의해 이미 생성되어 있지 않으면 새 row를 만들지 않고 404를 반환한다.
- Wiki 저장에 필요한 `user_id`, `workspace_id`는 `document_id`로 기존 `documents` row에서 조회한다. 현재 Backend가 보내는 동명 필드는 호환 목적으로 수신만 하고 사용하지 않으며, 제거 협의는 `docs/issue/backend/2026-07-16.md` 이슈 2에 기록한다.
- 이 변경은 DB 책임 충돌과 `content_hash` 오류를 해결하지만 FastAPI 직접 접근 자체를 차단하지는 않는다. 운영 배포에서는 llmPipeline을 private VPC에 두고 backend에서만 접근하도록 제한할지, 별도 서비스 인증을 추가할지 backend·infra와 협의해야 한다.

## 2. 같은 문서 pipeline 재실행 시 uq_wiki_pages_type_slug 중복 위반으로 run failed

- 이미 처리된 문서를 `POST /pipeline/runs`(document_id 지정)로 재실행하면 LLM 처리는 끝났는데 wiki page 저장 단계에서 실패.
  `duplicate key value violates unique constraint "uq_wiki_pages_type_slug" DETAIL: Key (page_type, slug)=(source, doc_...) already exists.`
- 원인: DB `wiki_pages`에 unique constraint가 2개 공존.
  - `uq_wiki_pages_workspace_type_slug (user_id, workspace_id, page_type, slug)` — 현행 설계. pipeline upsert의 `ON CONFLICT` 대상 (`postgres_wiki_ingestion_repository.py:1288` 부근).
  - `uq_wiki_pages_type_slug (page_type, slug)` — 과거 스키마 잔재. 현재 backend `WikiPage.java`(`fruition/wiki/domain/WikiPage.java:9`)에는 정의 없음. JPA `ddl-auto=update`는 constraint를 삭제하지 않아 DB에만 남아 있음.
  - user_id/workspace_id가 다르거나 비어 있는 재실행에서 upsert의 conflict 대상이 아닌 잔재 constraint가 먼저 걸려 실패.
- 조치: 잔재 constraint drop은 backend/DB 스키마 소관 → `docs/issue/backend/2026-07-16.md` 이슈 1 참조. drop 후에도 같은 user/workspace 재실행이 upsert로 자연 해소되는지 pipeline 쪽 재실행 시나리오 검증 필요.

## 3. PDF 복원 흐름 개선과 평가 결과 문서화

### 배경

- 참고문헌이 Docling group 내부에 포함된 경우 primary manifest에서 누락될 수 있었다.
- 표와 수식 모두 Text SLLM을 거치는 방식은 표 복원 정확도와 처리시간에 불리했다.
- Vision 결과의 거절 표현과 전체 evaluator 처리시간이 일관되게 기록되지 않았다.
- 현재 코드의 PDF → Markdown 흐름, prompt, 정확도와 처리시간을 AI 멘토가 처음 읽어도 이해할 수 있는 문서가 필요했다.

### 변경 내용

- Docling `body.children`의 중첩 group을 문서 순서대로 탐색하고 `list_item`의 Docling text를 보존한다.
- Text SLLM은 코드만으로 복원하지 못한 수식에만 사용하고, 표는 규칙 기반 코드 처리 후 Vision SLLM으로 검토한다.
- 대괄호 유무와 대소문자가 다른 Vision 거절 결과를 동일하게 판정한다.
- 복원 시간, evaluator 이번 실행시간·누적시간, 최종 평가 Markdown까지의 합산 처리시간을 기록한다.
- 사용하지 않는 표·그림용 Text SLLM prompt를 제거한다.
- 현재 처리 흐름, prompt 원문과 한글 주석, PDF 4개 실험 결과를 `docs/pdf-to-markdown-mentor-guide.md`에 정리한다.

### 관련 위치

- 흐름·실험·prompt 설명: `docs/pdf-to-markdown-mentor-guide.md`
- Docling group과 참고문헌 처리: `llmPipeline/app/modules/document_restoration/infrastructure/build_docling_primary_manifest.py`, `ordered_body_refs`
- 표·수식별 SLLM 사용 조건: `llmPipeline/app/modules/document_restoration/infrastructure/recover_blocks_with_ocr_sllm.py`, `should_use_sllm`
- Vision 거절 판정: `llmPipeline/app/modules/document_restoration/infrastructure/review_blocks_with_vision.py`, `is_rejected_result`
- evaluator 시간 기록: `llmPipeline/app/modules/document_evaluation/infrastructure/local_document_evaluator.py`, `record_evaluation_timing`
