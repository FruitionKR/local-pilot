# 2026-07-20 이슈

## dev-up backend readiness 확인 실패

### 문제

사용자용 Document API는 `/api/workspaces/{workspace_id}/documents`로 이동했지만 `scripts/dev-up.sh`는 예전 `GET /api/documents`를 계속 backend readiness URL로 사용했다. 현재 `/api/documents`에는 pipeline callback용 `PATCH`와 `POST`만 있어 GET 요청은 `405 Method Not Allowed`를 반환한다.

이 때문에 백엔드가 정상 기동해도 `dev-up.sh`가 60초 후 실패하고 EXIT trap으로 백엔드를 종료했으며, 이후 단계인 프론트엔드 시작까지 도달하지 못했다.

첫 문제를 수정한 뒤 빈 PostgreSQL volume에서 smoke test하자, 먼저 시작된 pipeline API가 Flyway보다 앞서 `document_wiki_links` 등 공용 테이블을 생성하는 두 번째 문제가 확인됐다. Flyway는 schema를 기존 DB로 판단해 V1 baseline schema를 건너뛰었고, V3가 존재하지 않는 `workspaces` 테이블을 참조하면서 실패했다.

### 반영

- backend에 Spring Boot Actuator를 추가하고 `GET /actuator/health`를 비인증 health endpoint로 노출한다.
- `dev-up.sh`를 PostgreSQL/MinIO → backend Flyway → pipeline API → frontend 순서로 바꿔 공용 스키마는 backend가 먼저 생성하게 한다.
- `dev-up.sh`의 backend readiness 확인을 `GET /actuator/health`로 변경한다.
- 로컬 실행 문서와 backend README의 확인 URL을 갱신한다.
- 현재 기술 문서에 남아 있던 사용자용 Document API 경로를 workspace 기반 경로로 정정한다.
- 통합 테스트에서 비인증 health 요청의 `200 OK`, `{"status":"UP"}` 응답을 검증한다.

### 확인 위치

- 실행 스크립트: `scripts/dev-up.sh`의 `start_backend`, `GET /actuator/health`
- health 의존성과 공개 정책: `backend/build.gradle`의 `spring-boot-starter-actuator`, `backend/src/main/java/fruition/security/SecurityConfig.java`의 `/actuator/health`
- 통합 테스트: `backend/src/test/java/fruition/BackendApplicationTests.java`의 `health_unauthenticated_returnsUp`
- 로컬 실행 절차: `docs/local-runbook.md`의 `한 번에 실행`, `수동 실행 순서 > 2. 백엔드 시작`
- backend 문서: `backend/README.md`의 `Health check`, `Documents`
- API 기술 문서: `docs/spec/document-upload.md`의 `API 계약`, `docs/spec/backend-mvp-erd.md`의 `document_blocks`

## documents.content_hash 전역 UNIQUE 제약의 워크스페이스 격리 위반

### 문제

`documents.content_hash`가 전체 DB 범위의 `UNIQUE`로 정의되어 있어 서로 다른 워크스페이스라도 내용이 같은 문서를 저장할 수 없다. 문서 중복 판정이 워크스페이스 경계를 무시하므로, 한 워크스페이스에 이미 존재하는 내용을 다른 워크스페이스에 업로드하면 `DuplicateDocumentException`이 발생한다.

워크스페이스 생성 시 모든 곳에 동일한 `# 새 노트`를 저장하면 이 제약과 충돌한다. 현재 구현은 임시 우회로 초기 Markdown 본문에 다음 식별 주석을 포함해 콘텐츠 해시를 워크스페이스마다 다르게 만든다.

```markdown
<!-- fruition-workspace: ws_... -->
# 새 노트
```

이 주석은 문서 내용이 아니지만 원본 Markdown과 pipeline 입력에 섞인다. 프론트의 `splitMarkdownBlocks`도 HTML 주석을 일반 Markdown block으로 처리해 미리보기에서 내부 워크스페이스 ID가 노출되고, 이후 block ID가 한 칸씩 밀릴 수 있다.

### 해결 방향

- 새 Flyway migration에서 기존 전역 `content_hash` unique constraint를 제거한다.
- `(workspace_id, content_hash)` 복합 unique constraint를 추가해 같은 워크스페이스 안에서만 중복을 차단한다.
- `Document` entity의 `contentHash` 단일 `unique = true` 선언을 제거하고 복합 unique constraint와 일치시킨다.
- `DocumentRepository.findByContentHash`를 workspace 범위 조회로 변경하고 일반 업로드와 채팅 export 중복 검사에 동일하게 적용한다.
- `DocumentService.createInitialNote`의 `fruition-workspace` 주석을 제거하고 본문을 `# 새 노트`로 저장한다.
- 이미 생성된 초기 노트는 원본 오브젝트에 주석이 남아 있으므로, 미리보기에서 해당 내부 주석을 숨기는 하위 호환 처리 또는 저장 오브젝트·`content_hash` 정리 migration 정책을 결정한다.

### 완료 조건

- 서로 다른 워크스페이스에는 내용이 동일한 문서를 각각 저장할 수 있다.
- 같은 워크스페이스의 동일 문서는 기존처럼 중복으로 거부된다.
- 새 워크스페이스의 초기 노트 원본과 미리보기에 `fruition-workspace` 주석이 나타나지 않는다.
- 기존 초기 노트의 내부 주석도 사용자 화면에 노출되지 않는다.
- 일반 업로드, 채팅 export, 초기 노트 생성 관련 단위·통합 테스트가 통과한다.

### 확인 위치

- DB 제약: `backend/src/main/resources/db/migration/V1__baseline_schema.sql`의 `documents.content_hash`, constraint `ukeafca5s6k4behm6am8avmcik3`
- JPA mapping: `backend/src/main/java/fruition/document/domain/Document.java`의 `contentHash`
- 중복 조회: `backend/src/main/java/fruition/document/repository/DocumentRepository.java`의 `findByContentHash`
- 업로드·초기 노트·채팅 export: `backend/src/main/java/fruition/document/service/DocumentService.java`의 `upload`, `createInitialNote`, `createChatExportDocument`
- Markdown block 분리: `frontend/app/_components/MarkdownViewer.tsx`의 `splitMarkdownBlocks`
