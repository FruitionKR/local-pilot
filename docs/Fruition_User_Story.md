# Fruition User Story

Fruition의 요구사항을 사용자가 직접 수행하거나 확인하는 **사용자 스토리**와, 이를 보장하기 위한 **시스템 조건**으로 구분한다.

## 1. 사용자

### 사용자 스토리

- 사용자는 이메일 인증번호를 요청하고 인증할 수 있다.
- 사용자는 인증된 이메일, 비밀번호, 닉네임으로 회원가입할 수 있다.
- 사용자는 이메일과 비밀번호로 로그인할 수 있다.
- 사용자는 Google, Naver, Kakao OAuth 로그인을 사용할 수 있다.
- 사용자는 로그인 상태를 유지하기 위해 인증 토큰을 갱신할 수 있다.
- 사용자는 이메일 인증을 거쳐 비밀번호를 재설정할 수 있다.
- 사용자는 로그아웃할 수 있다.
- 사용자는 자신의 프로필 정보를 조회할 수 있다.

### 시스템 조건

- 이메일 회원가입은 인증이 완료된 이메일만 허용한다.
- 토큰 재발급 시 기존 refresh token을 폐기하고 새로운 access token과 refresh token을 발급한다.
- OAuth 로그인 결과는 만료되는 일회용 code를 서비스의 access token과 refresh token으로 교환한다.
- 로그아웃과 비밀번호 재설정 시 기존 refresh token을 폐기한다.
- 회원가입 또는 최초 OAuth 가입 시 기본 워크스페이스를 자동 생성한다.
- 기본 워크스페이스에는 초기 Markdown 문서를 자동 생성한다.
- 인증되지 않은 요청은 보호된 사용자·워크스페이스 데이터에 접근할 수 없다.

## 2. 워크스페이스

### 사용자 스토리

- 사용자는 여러 워크스페이스를 생성할 수 있다.
- 사용자는 자신이 소유하거나 멤버로 참여한 워크스페이스 목록을 조회할 수 있다.
- 워크스페이스 소유자는 워크스페이스 이름을 변경할 수 있다.
- 워크스페이스 소유자는 워크스페이스를 소프트 삭제할 수 있다.
- 사용자는 자신이 삭제한 워크스페이스 목록을 조회하고 복구할 수 있다.
- 워크스페이스 소유자는 다른 사용자를 멤버로 초대할 수 있다.

### 시스템 조건

- 새 워크스페이스에는 초기 Markdown 문서를 생성한다.
- 워크스페이스는 `OWNER`와 `MEMBER` 역할을 구분한다.
- 이름 변경·삭제·복구 등 소유자 전용 작업은 `OWNER`만 실행할 수 있다.
- 삭제된 워크스페이스는 일반 목록과 내부 콘텐츠 접근에서 제외한다.
- 워크스페이스 복구 시 기존 콘텐츠와 멤버십을 다시 접근할 수 있게 한다.
- 일반 멤버에게 소유자 전용 작업 권한을 부여하지 않는다.

## 3. 문서

### 3.1 업로드 및 생성

#### 사용자 스토리

- 사용자는 Markdown 파일을 선택하거나 드래그해서 업로드할 수 있다.
- 사용자는 여러 파일을 한 번에 선택하거나 드롭할 수 있다.
- 사용자는 PDF와 Markdown 파일을 업로드할 수 있다.
- 사용자는 빈 Markdown 문서를 생성할 수 있다.
- 사용자는 AI가 생성한 Markdown 초안을 새 문서로 저장할 수 있다.
- 사용자는 업로드한 Markdown을 확인하거나 수정한 뒤 Wiki ingest를 시작할 수 있다.

#### 시스템 조건

- 지원하지 않는 파일은 업로드 대상에서 제외한다.
- 업로드 및 생성 요청은 멱등 키로 중복 실행을 방지한다.
- 파일 업로드는 원본과 문서 정보만 저장하고 Wiki ingest를 자동 실행하지 않는다.
- PDF와 Markdown 업로드 문서는 `uploaded` 상태로 저장한다.
- 업로드한 Markdown은 편집 상태를 함께 생성해 즉시 편집할 수 있게 한다.
- PDF 등 읽기 전용 원본은 변환 기능이 제공되기 전까지 저장·조회·다운로드만 지원한다.
- 같은 멱등 키와 같은 요청이 재전송되면 기존 결과를 반환한다.
- 같은 멱등 키에 다른 요청이 전달되면 충돌로 거절한다.

### 3.2 조회 및 탐색

#### 사용자 스토리

- 사용자는 워크스페이스의 폴더와 문서를 전체 계층 구조로 조회할 수 있다.
- 사용자는 최상위 항목을 조회하고 폴더를 열어 하위 항목을 탐색할 수 있다.
- 사용자는 문서 이름으로 검색할 수 있다.
- 사용자는 문서 상세 정보와 연결된 Wiki 페이지를 조회할 수 있다.
- 사용자는 원본 파일을 조회하거나 내려받을 수 있다.
- 사용자는 Markdown 문서를 export할 수 있다.
- 사용자는 인용 근거 확인을 위해 원본 문서의 block 목록을 조회할 수 있다.
- 사용자는 문서 이름을 변경할 수 있다.

#### 시스템 조건

- 전체 트리 조회는 활성 폴더와 문서를 중첩 구조로 반환한다.
- 프론트엔드는 전체 트리 조회와 폴더별 지연 조회 중 필요한 방식을 사용할 수 있다.
- 폴더와 문서는 같은 부모 안에서 `sort_order`, ID 순으로 정렬한다.
- 폴더와 문서 조회 결과에 동시 변경 검사용 `current_version`을 포함한다.
- 소프트 삭제된 폴더와 문서는 일반 목록과 문서 트리에서 제외한다.
- 검색 결과는 요청한 워크스페이스 범위를 벗어나지 않는다.

### 3.3 폴더 및 배치

#### 사용자 스토리

- 사용자는 폴더와 하위 폴더를 생성할 수 있다.
- 사용자는 폴더 이름을 변경할 수 있다.
- 사용자는 폴더를 다른 폴더로 이동할 수 있다.
- 사용자는 문서를 드래그해 폴더 또는 최상위로 이동할 수 있다.
- 사용자는 삭제된 폴더와 문서를 복구할 수 있다.

#### 시스템 조건

- 폴더를 자기 자신이나 자신의 하위 폴더로 이동할 수 없다.
- 폴더를 삭제하면 모든 하위 폴더와 문서를 같은 삭제 작업으로 소프트 삭제한다.
- 폴더를 복구하면 같은 삭제 작업에 포함된 복구 대상 하위 폴더와 문서도 복구한다.
- 원래 부모가 복구되지 않은 항목은 최상위로 복구한다.
- 이동·삭제·복구 시 `version`을 검사해 동시 변경 충돌을 방지한다.
- 문서와 폴더의 형제 순서를 이동 결과에 맞춰 저장한다.

### 3.4 편집 및 저장

#### 사용자 스토리

- 사용자는 Markdown 원문 편집기를 사용할 수 있다.
- 사용자는 Notion과 유사한 WYSIWYG Markdown 편집기를 사용할 수 있다.
- 사용자는 업로드한 Markdown 파일을 Markdown 문서로 편집할 수 있다.
- 사용자는 저장 버튼 또는 `Ctrl+S`로 문서를 저장할 수 있다.
- 사용자는 채팅에서 AI에게 선택 영역 또는 문서 전체 편집을 요청할 수 있다.
- 사용자는 AI 편집 결과와 diff를 확인하고 적용하거나 취소할 수 있다.
- 사용자는 AI가 생성한 문서를 적용하기 전에 직접 수정할 수 있다.
- 사용자는 다른 멤버가 문서를 편집 중인지 확인할 수 있다.
- 사용자는 다른 멤버가 편집 중인 문서를 읽기 전용으로 열람할 수 있다.

#### 시스템 조건

- 일반 문서 편집은 자동 저장하지 않는다.
- 수동 저장 시 현재 문서 `version`을 검사한다.
- 다른 변경이 먼저 저장됐다면 오래된 저장 요청을 거절하고 충돌 상태를 표시한다.
- 현재 본문과 같은 본문은 새 `version`으로 저장하지 않는다.
- AI 편집 결과를 적용하면 별도 저장 동작 없이 즉시 저장한다.
- 사용자가 편집을 시작하면 문서 편집 잠금을 획득하고 편집 중 heartbeat로 잠금을 연장한다.
- 편집 잠금이 만료되거나 상실되면 추가 저장을 차단한다.
- 편집을 종료하면 사용자가 보유한 잠금을 멱등하게 해제한다.
- 다른 사용자가 유효한 편집 잠금을 보유하면 쓰기 작업을 거절한다.

### 3.5 변경 이력과 복원

#### 사용자 스토리

- 사용자는 문서 콘텐츠 version 목록을 조회할 수 있다.
- 사용자는 특정 version의 Markdown 본문을 조회할 수 있다.
- 사용자는 두 문서 version 사이의 변경 내용을 GitHub와 유사한 형식으로 비교할 수 있다.
- 사용자는 version 사이에 추가·삭제된 줄과 변경 위치를 확인할 수 있다.
- 사용자는 과거 version을 현재 문서의 새 version으로 복원할 수 있다.

#### 시스템 조건

- 본문이 실제 변경될 때 변경 전·후 전체 Markdown 스냅샷을 저장한다.
- 동일한 본문을 저장하면 새 스냅샷을 생성하지 않는다.
- version diff는 줄 단위 `CONTEXT`, `DELETE`, `ADD` 유형과 이전·이후 줄 번호를 반환한다.
- 변경 전 스냅샷이 없는 기존 version은 diff를 제공하지 않는다.
- 과거 version 복원은 기존 이력을 삭제하지 않는 비파괴 방식으로 처리한다.
- 복원 시 현재 `version`을 검사해 오래된 요청을 거절한다.
- 복원된 본문은 현재 문서의 새 `version`으로 저장한다.
- 복원은 diff를 역적용하지 않고 저장된 이전 전체 Markdown 본문을 사용한다.

### 3.6 Wiki 생성

#### 사용자 스토리

- 사용자는 업로드한 파일을 Wiki로 만들 수 있다.
- 사용자는 직접 생성하거나 편집한 Markdown 문서를 Wiki로 만들 수 있다.
- 사용자는 편집 가능한 Markdown 문서를 최신 편집본으로 다시 ingest할 수 있다.
- 사용자는 처리 상태와 pipeline 진행 단계를 확인할 수 있다.

#### 시스템 조건

- Markdown 업로드만으로 Wiki pipeline을 시작하지 않는다.
- 사용자가 명시적으로 ingest를 요청한 시점의 최신 편집본을 사용한다.
- ingest가 시작되면 문서 상태를 `processing`으로 변경한다.
- 이미 처리 중인 문서의 중복 ingest 요청은 거절한다.
- 다른 사용자가 해당 문서를 편집 중이면 ingest 요청을 거절한다.
- pipeline 진행 상태와 처리 단계를 문서 조회 결과에 반영한다.

### 3.7 문서 복제

#### 사용자 스토리

- 사용자는 편집 가능한 Markdown 문서를 복제할 수 있다.

#### 시스템 조건

- 복제본은 원본과 같은 폴더의 마지막 위치에 생성한다.
- 이름이 중복되면 충돌하지 않는 복제 이름을 생성한다.
- PDF 등 읽기 전용 원본 문서는 복제할 수 없다.
- 복제 요청은 멱등 키로 중복 실행을 방지한다.

### 3.8 문서 삭제 및 복구

#### 사용자 스토리

- 사용자는 자신이 소유한 문서를 소프트 삭제할 수 있다.
- 사용자는 휴지통에서 삭제된 문서를 조회할 수 있다.
- 사용자는 삭제된 문서를 복구할 수 있다.

#### 시스템 조건

- 문서 삭제·복구 시 `version`과 멱등 키를 검사한다.
- 삭제된 문서는 일반 목록과 문서 트리에서 제외한다.
- 문서를 삭제하면 해당 문서에서 생성된 source Wiki 페이지도 삭제 대상에 포함한다.
- 복구된 문서는 정해진 복구 위치와 순서로 다시 배치한다.

## 4. Wiki

### 4.1 조회

#### 사용자 스토리

- 사용자는 워크스페이스의 Wiki 그래프를 조회할 수 있다.
- 사용자는 Wiki 페이지의 제목, 요약, Markdown 본문을 조회할 수 있다.
- 사용자는 Wiki 페이지와 연결된 원본 문서를 확인할 수 있다.
- 사용자는 관련 Wiki 페이지와 그래프 연결 관계를 확인할 수 있다.

#### 시스템 조건

- Wiki 그래프와 페이지 조회는 요청한 워크스페이스 범위로 제한한다.
- Wiki 페이지 상세에는 연결된 원본 문서와 관련 페이지 정보를 포함한다.
- 원본 Markdown을 읽지 못하더라도 조회 가능한 페이지 메타데이터는 반환한다.

### 4.2 이름 및 slug 변경

#### 사용자 스토리

- 사용자는 Wiki 페이지 이름을 변경할 수 있다.
- 사용자는 이름 변경 시 기존 slug를 유지할 수 있다.
- 사용자는 필요한 경우 제목에 맞춰 slug도 함께 변경할 수 있다.

#### 시스템 조건

- Backend는 요청 사용자의 워크스페이스 멤버십을 확인한다.
- llmPipeline은 Wiki 페이지의 워크스페이스 소속과 변경 가능 여부를 확인한다.
- slug 변경 요청은 제목으로 새 slug를 생성한다.
- 같은 사용자·워크스페이스·페이지 유형에서 slug가 충돌하면 요청을 거절한다.
- 이름과 slug 변경은 하나의 작업으로 처리해 일부 값만 변경되는 상황을 방지한다.

### 4.3 Schema 및 유지보수

#### 사용자 스토리

- 사용자는 Wiki schema를 미리보기할 수 있다.
- 사용자는 Wiki schema를 draft로 저장하고 활성화할 수 있다.
- 사용자는 워크스페이스에 현재 활성화된 Wiki schema를 조회할 수 있다.
- 사용자는 Wiki maintenance lint를 실행할 수 있다.

#### 시스템 조건

- Wiki schema와 maintenance 작업은 요청한 사용자와 워크스페이스 범위에서 처리한다.
- llmPipeline 오류는 Backend API에서 정의한 오류 응답으로 전달한다.

## 5. 채팅

### 5.1 세션

#### 사용자 스토리

- 사용자는 워크스페이스 안에서 여러 채팅 세션을 생성할 수 있다.
- 사용자는 자신이 생성한 채팅 세션 목록과 메시지 기록을 조회할 수 있다.
- 사용자는 자신의 채팅 세션을 삭제할 수 있다.

#### 시스템 조건

- 채팅 세션은 워크스페이스가 아니라 생성한 멤버에게 귀속한다.
- 세션 목록은 `workspace_id`와 `user_id`가 모두 일치하는 세션만 최근 메시지 순으로 반환한다.
- 세션 조회·삭제 시 `session_id`, `workspace_id`, `user_id`를 함께 검사한다.
- 같은 워크스페이스의 다른 멤버가 만든 세션은 조회하거나 삭제할 수 없다.
- 세션 최대 개수 제한은 워크스페이스 멤버별로 적용한다.
- 워크스페이스 삭제 시 해당 워크스페이스의 모든 채팅 세션에 대한 접근을 차단한다.

### 5.2 Wiki 편입

#### 사용자 스토리

- 사용자는 채팅 세션 전체를 Markdown 문서로 변환해 Wiki pipeline에 편입할 수 있다.
- 사용자는 원하는 질문·답변 범위를 선택해 Wiki pipeline에 편입할 수 있다.
- 사용자는 편입 전에 생성될 Markdown을 미리 확인할 수 있다.
- 사용자는 이미 편입한 전체 세션에 새 대화가 추가되면 기존 export 문서를 갱신할 수 있다.

#### 시스템 조건

- 사용자가 소유한 채팅 세션만 Wiki에 편입할 수 있다.
- 동일한 내용의 중복 Wiki export를 생성하지 않는다.
- 전체 세션 갱신 시 기존 export 문서를 재사용한다.
- 부분 편입은 사용자가 선택한 질문·답변 범위만 포함한다.

## 6. AI 질의

### 사용자 스토리

- 사용자는 자신의 채팅 세션에서 자연어로 AI 질의를 할 수 있다.
- 사용자는 AI 답변과 관련 Wiki 페이지를 확인할 수 있다.
- 사용자는 답변에 사용된 원본 문서와 block 근거를 확인할 수 있다.
- 사용자는 답변에 사용된 그래프 탐색 경로를 확인할 수 있다.
- 사용자는 질의 진행 상태를 확인할 수 있다.

### 시스템 조건

- 질의 전에 채팅 세션의 `workspace_id`와 `user_id` 소유권을 확인한다.
- 다른 멤버의 채팅 세션에는 메시지를 추가하거나 질의를 실행할 수 없다.
- AI 답변에는 관련 Wiki 페이지, 원본 문서, block 근거와 그래프 탐색 경로를 연결한다.
- 비동기 질의의 진행 상태를 사용자가 확인할 수 있게 제공한다.

## 7. 활동 로그와 시점 복구

### 사용자 스토리

- 사용자는 워크스페이스에서 수행된 활동 내역을 시간순으로 조회할 수 있다.
- 사용자는 AI 편집, Wiki ingest, Wiki maintenance lint 활동을 확인할 수 있다.
- 사용자는 특정 활동에서 변경된 문서 또는 Wiki 페이지를 확인할 수 있다.
- 사용자는 특정 활동의 변경 전·후 diff를 확인할 수 있다.
- 사용자는 특정 활동 이전 상태로 문서 또는 Wiki를 복원할 수 있다.

### 시스템 조건

- 활동에는 수행자, 작업 유형, 대상, 수행 시각과 처리 상태를 기록한다.
- 하나의 ingest 또는 lint에서 발생한 여러 Wiki 페이지·block·link·embedding 변경은 같은 활동으로 묶는다.
- Backend는 활동 목록과 diff 조회에 필요한 데이터를 제공하며, 조회를 위해 llmPipeline을 호출하지 않는다.
- 문서와 Wiki 데이터의 복원은 각 canonical data 소유자가 처리한다.
- 복원은 과거 이력을 덮어쓰지 않고 이전 상태를 참조하는 새로운 revision을 생성한다.
- 복원 요청은 현재 revision을 검사해 오래된 요청이나 동시 변경 충돌을 거절한다.
- diff는 조회와 확인에만 사용하며 실제 복원은 저장된 전체 snapshot 또는 revision artifact를 사용한다.
